FoW — design state & corrected PR

cortex-modern's contribution to upstream's dynamic-fow-negative-distance-test branch. After Causeless flagged a misread in our headline commit (“the intent was only to reveal FoW in the direction that the actor was looking”), digging into the engine source revealed the directional reveal he wanted is already implemented in AHuman::Look() — we'd accidentally bypassed it by rewriting Actor::CastSeeRays() as a hardcoded 360° fan that skipped the virtual dispatch. PR narrowed in response with a 5th commit reverting the two design-misread changes. This page documents what was found, what was fixed, what still holds, and the genuine future-design TBDs.

tl;dr — the corrected story

What we missed: the directional reveal Causeless wanted is already implemented in AHuman::Look() — a 32-ray body bubble (36 px radius) plus a directional aim-cone (FOVSpread / 0.5 rays centered on m_AimAngle, angle-quantized to avoid flicker as the aim slides). ooaaaoaoao's February commit 32f667559 "ahuman vision bubble now centered on body, not aimpos" set up the bubble; Causeless's e5d6b0e11 "Stop flickering when changing aim angle..." added the angle quantization on the cone. Both already in the branch we built on.

What we did wrong: our headline commit be8734ec4 rewrote Actor::CastSeeRays() as a 36-ray 360° fan calling CastSeeRay directly — bypassing the virtual Look() dispatch entirely. AHuman::Look() and ACrab::Look() never ran when our code was in place. Same commit also gated engine CastSeeRaysFromSky to Editing-only, misreading 4ae962455 "Killed script sky rays" as "all sky rays unwanted" — the "script" qualifier meant Lua-script-driven sky-ray spawns (e.g., SetupFogOfWar in SkirmishDefense.lua), not the engine dispatch that produces the outdoor-vs-bunker differentiation.

What we fixed: a 5th commit on the PR reverts both. Actor::CastSeeRays() goes back to its Look(...) dispatcher form (now that we understand AHuman::Look() does the right thing). MovableMan::Update's sky-ray dispatch is restored to fire during both Editing and gameplay. Everything else in the PR still holds — the crash fix, the wrap-class-of-bug fixes, the IsUnseen /IsCurrentlyUnseen split, the C++ DrawHUD callsite switches, the useOneStageFoW = false render path, the MakeAllUnseen sentinel fallback, and the bg-layer maskReady gating are all real fixes independent of the reveal direction.

What's still ahead: the headline P0 (vanilla AI Lua callsites still call IsUnseen and get the new ever-unseen semantic — AI shoots through dimmed memory) survives the redesign and needs the ~30 callsite rewrite. Plus genuine future design work that the March transcript and Causeless's recent hints make explicit: cameras (stationary vision sources), doors as dynamic apertures, splitscreen FoW, the pre-SDF smoothing step Causeless wants, the double-buffering hack, and team-owned bunker permanent vision. Full audit in §7–§8.

1  ·  AHuman::Look() — the directional reveal already exists

This is the section that changes everything about how to read the rest of the PR. The implementation Causeless described in his review (“reveal FoW in the direction the actor was looking”) is already on the branch — we just didn't see it because we were reading Actor::CastSeeRays(), which is the dispatcher, not the implementation. The real work happens in the virtual Look() override, which AHuman implements with two distinct ray-cast passes.

The two-pass design in AHuman::Look()

Located in Source/Entities/AHuman.cpp at line 1347. Fires once per actor per frame via the Actor::CastSeeRays() → Look(FOVSpread, range) dispatch chain. Both passes use strength = c_PathFindingDefaultDigStrength (matches the pathfinding dig-strength so see-rays pass through light debris and corpses but stop at solid walls).

1.1   The body bubble — 32 rays in 360° at 36 px around body

Short-range omnidirectional reveal around the actor's body position (not eye, not aim). Gives the actor immediate awareness of the space they physically occupy, regardless of where they're facing. ooaaaoaoao introduced this with commit 32f667559 “ahuman vision bubble now centered on body, not aimpos. fix for prev” — they'd briefly tried aim-position-centered and switched to body-centered. Earlier commit be8889316 framed it: “less rays, wider fow, removed see-through-terrain box around ahumans, now a bubble of rays”.

AHuman.cpp:1393–1400 — the body bubble
const float bubblePixelRadius = 36.0f; static int bubbleRayNum = 32; const Vector bubbleCenterPos = GetPos(); Vector bubbleAroundActorLookVector(bubblePixelRadius, 0); for (int i = 0; i < bubbleRayNum; ++i) { g_SceneMan.CastSeeRay(m_Team, bubbleCenterPos, bubbleAroundActorLookVector, ignored, strength, 0); bubbleAroundActorLookVector.RadRotate(2 * PI / bubbleRayNum); }

1.2   The directional aim-cone — FOVSpread / 0.5 rays, angle-quantized

The directional reveal Causeless was asking us to preserve. Cast from aimPos (eye position if a head attachable exists, else body), extending m_AimDistance + range pixels (further when aiming sharp through a barrel). Cone is centered on m_AimAngle, spans FOVSpread degrees, contains FOVSpread / degreesPerRotationSegment rays (with degreesPerRotationSegment = 0.5 → 200 rays for a 100° spread). The aim angle is quantized to fixed angular divisions per Causeless's e5d6b0e11 “Stop flickering when changing aim angle by ensuring that rays are cast at the same angle divisions” — so the rays don't shift visibly as the actor's aim slides smoothly.

AHuman.cpp:1369–1407 — the directional cone (condensed)
float aimDistance = m_AimDistance + range; if (m_Controller.IsState(AIM_SHARP) && m_pFGArm && m_pFGArm->IsAttached() && m_pFGArm->GetHeldDevice()) { aimDistance += m_pFGArm->GetHeldDevice()->GetSharpLength(); // extend when aiming sharp } // Cone span = FOVSpread degrees, centered on m_AimAngle (H-flip handled). float aimAngle = m_AimAngle - RTE::DegreesToRadians(FOVSpread * (m_HFlipped ? -0.5f : 0.5f)); // Angle-quantize so rays don't flicker as the aim slides smoothly (Causeless's e5d6b0e11). static float degreesPerRotationSegment = 0.5f; const float numRotationalSegmentsPerSide = 180.0f / degreesPerRotationSegment; const float quantization = numRotationalSegmentsPerSide / c_PI; aimAngle = std::round(aimAngle * quantization) / quantization; Matrix aimMatrix(m_HFlipped ? -aimAngle : aimAngle); aimMatrix.SetXFlipped(m_HFlipped); Vector lookVector(aimDistance, 0); lookVector *= aimMatrix; const int rayNum = FOVSpread / degreesPerRotationSegment; // 200 rays for FOVSpread=100° for (int i = 0; i < rayNum; ++i) { g_SceneMan.CastSeeRay(m_Team, aimPos, lookVector, ignored, strength, 0, MOIDsToIgnore); lookVector.DegRotate(FOVSpread / (rayNum - 1)); }

1.3   Per-subclass dispatch

Different actor types have different Look() overrides. Actor::CastSeeRays() calls Look(100, screenWidth * 0.7 * m_Perceptiveness) once per frame; virtual dispatch routes to the appropriate override based on actor class.

ClassWhat Look() doesRays/frame (FOVSpread=100)
AHuman 32-ray body bubble (36 px) plus 200-ray directional aim-cone centered on m_AimAngle ~232
ACrab Single aim-direction ray from GetCPUPos() (or mounted-weapon position if aiming sharp) with random ±FOVSpread/2 spread 1
ACraft Inherits Actor::Look() base — no override 1 (velocity-direction)
Actor base (fallback) Single velocity-direction ray with FOVSpread spread; if velocity is near-zero, random 360° angle 1

Asymmetry note: ACrab's vision is much weaker than AHuman's per-frame (1 ray vs ~232). That's consistent with the design framing — crabs are creatures, humans are intel-gathering soldiers with proper situational awareness. Tuning this further (more crab rays? wider crab arc?) is open design territory.

1.4   The clue we missed in the source itself

SceneMan::CastSeeRaysFromSky in SceneMan.cpp at line 1070 has an explicit comment: “These are the same as for AHuman::Look()” — referring to the strength and skip values. The sky-ray system literally treats AHuman::Look() as the canonical see-ray reference. Had we read that comment, we'd have followed the breadcrumb to AHuman.cpp:1347 and avoided the whole misread. Process lesson for next time: when overriding a virtual function in a base class, grep all subclass overrides before rewriting the base.

2  ·  Our misreads & the fix

Two specific changes inside the headline commit be8734ec4 went against the upstream design. Both fixed by the 5th commit on the PR branch. Everything else in be8734ec4 is intact — crash fixes, wrap fixes, IsUnseen split, render-path fixes, all real bugs unrelated to reveal direction.

Misread #1 — rewrote Actor::CastSeeRays() as a 360° fan

What we wrote: replaced the function body (which was Look(100, ...) calling once per frame) with a hardcoded 36-ray (later scaled with radius via cd17a0466) 360° fan calling CastSeeRay directly. Bypassed the virtual Look() dispatch entirely.

What we missed: AHuman::Look() is the directional implementation (§1). Actor::CastSeeRays() is the dispatcher; rewriting it without calling Look() means AHuman::Look() and ACrab::Look() never run. We disabled the existing directional reveal across all actor classes in one stroke.

What Causeless saw: “this is a pretty big departure from what we had planned and intended. The intent was only to reveal FoW in the direction that the actor was looking.” He was looking at our 360° fan replacement and pointing out we'd thrown out the directional cone in AHuman::Look(). Not asking us to design a new system — asking us to call the one already there.

Misread #2 — gated engine CastSeeRaysFromSky to Editing-only

What we wrote: in MovableMan::Update, wrapped the CastSeeRaysFromSky thread-pool dispatch in if (gameActivity->GetActivityState() == Activity::Editing). During gameplay, sky rays no longer fired. The commit message framed this as “During RUNNING, Actor::CastSeeRays drives all vision exclusively” — making sky rays an Editing-mode helper for brain placement only.

What we missed: Causeless's 4ae962455 “Killed script sky rays” — the word "script" matters. He killed the Lua-script-driven sky-ray spawns (e.g., SetupFogOfWar(...) calls in SkirmishDefense.lua), not the engine-side CastSeeRaysFromSky dispatch. The engine dispatch is the mechanism producing the outdoor desaturation + noise + scanline visual on never-seen sky-illuminated terrain — without it, outdoor and bunker areas look the same (both black).

What Causeless saw: “Also the sky rays are intentional, so that there's a difference between outdoors and bunker gameplay.” He was pointing out exactly this — the differentiation mechanism we'd removed.

The fix — the 5th commit on the PR branch

Both reverts are in a single follow-up commit. Actor::CastSeeRays() goes back to its dispatcher form (single Look(100, screenWidth * 0.7f * m_Perceptiveness) call), now with an explanatory comment naming the AHuman/ACrab overrides so the next reader doesn't repeat our mistake. MovableMan::Update's CastSeeRaysFromSky dispatch is restored to fire during both Editing and gameplay, with a comment naming the "script-only" qualifier on Causeless's kill commit.

Result: AHuman vision is now directional aim-cone + body bubble (~232 rays/frame), ACrab vision is single aim-directed ray, sky rays fire engine-side during gameplay producing the outdoor desat+noise+ scanline visual on never-seen sky-illuminated terrain. Same as the state of the branch before our PR — the design Causeless and ooaaaoaoao iterated on in February-March.

What cd17a0466 "Actor::CastSeeRays: scale rayCount with sightRadius for smooth perimeter" becomes after the revert: dead code. The rayCount field it adjusted is gone now that we're back to calling Look(). The commit itself is harmless (it doesn't compile any code that runs), and removing it cleanly would mean rebasing. For the PR we're leaving it in place; if you'd prefer it dropped, that's a force-push away and we'll iterate.

3  ·  The visual model — mostly already implemented

The other thing the misread obscured: the visual completeness Causeless described in his review (outdoor differentiated from bunker via sky rays + desat + noise + scanline) is largely already in place on the branch. The March transcript between Causeless and ooaaaoaoao spent hours tuning it — SDF thresholds, smoothing distances, bunker-wall calibration, scanline blend. What our PR did was accidentally break the differentiation (misread #2). With the sky-ray dispatch restored, the visual model returns to its pre-PR state.

3.1   Four FoW states per tile

The branch implements a four-state visibility model. State transitions are driven by sky-ray reachability and per-actor see-ray hits, evaluated tile-by-tile.

StateTriggerVisual treatment
Visible Tile is currently in any actor's see-ray hit set this frame Full terrain + MOs render normally; no FoW overlay
Memory (dim) Tile was in UnseenLayerMask previously, but not this frame Saved terrain pixels (rteTextureLastSeen) rendered with dim/desat; live MOs hidden — this is what useOneStageFoW = false enables (the two-stage memory branch)
Never-seen, outdoor Tile never in any see-ray hit set, but sky rays reached it SDF shader applies the desat + noise + scanline outdoor visual (Causeless: "the outside fow is desaturated, has noise, and also a scanline effect")
Never-seen, bunker Tile never in any see-ray hit set and no sky ray reached it Black FoW — the original CC FoW look, the claustrophobic bunker interior

3.2   Why the sky-ray dispatch is the differentiator

SceneMan::CastSeeRaysFromSky casts rays from the top of the screen downward, clearing the sky-ray mask wherever a ray reaches. Tiles reachable from the sky end up in the "outdoor never-seen" state; tiles unreachable (covered by terrain above) stay in "bunker never-seen". The SDF shader samples this sky-ray mask and switches the visual treatment based on it. This is the mechanism Causeless meant by "difference between outdoors and bunker gameplay" — not a separate detection pass, but a direct consequence of which tiles sky rays reach.

Our PR's Editing-only gate disabled this entire mechanism during gameplay, collapsing both never-seen states into one. Restoring the dispatch puts the outdoor/bunker differentiation back.

3.3   Bunker wall calibration is already done

From the March 2 transcript — Causeless: “I pretty specifically tuned this so that the see-through distance was just about the width of a bunker wall.” The negative-distance SDF on this branch was chosen explicitly to fix the over-penetration problem that earlier positive-SDF + large-revealsize attempts had. The branch name (dynamic-fow-negative-distance-test) is a settled solution to a known visual problem, not a speculative experiment.

3.4   Wrap handling is fixed by our PR

One of the real bugs be8734ec4 caught and fixed: the SDF shader and sky-ray dispatch both treated scenes as toroidal unconditionally, with no check on WrapsX/WrapsY. On non-wrapping scenes (most CC scenes) the sky rays wrapped to off-screen positions when the camera panned near an edge, leaving camera-dependent dim/bright bands. Our fix added uniform vec2 uWrapsXY to SDF_3_UnsignedSDF.frag and matching guard logic to SceneMan::CastSeeRaysFromSky. Survives the revert — the wrap fix is in a different region of the codebase than the design misreads.

3.5   The 6 tunable static floats Causeless exposed

From the March transcript — Causeless made these six values static float rather than constants specifically so they could be adjusted live in-game during tuning:

FrameMan.cpp (or shader uniforms area) — live-tunable smoothing knobs
static float usdfThresoldForFoV = 0.02f; // how aggressive the current-FoV SDF mask is static float usdfOpacitySmoothingDistanceForFoV = 0.02f; // FoV edge softness static float usdfThresoldForNeverSeen = 0.015f; // memory-vs-never-seen boundary static float usdfOpacitySmoothingDistanceForNeverSeen = 0.01f; // memory-edge softness static float scanlineAndNoiseOpacitySmoothingDistance = 0.015f; // outdoor scanline blend distance static float unseenNoiseIntensity = 0.02f; // outdoor noise opacity

Our PR didn't touch these (intentionally — they're his tuning surface). The first two (usdfThresoldForFoV and usdfThresoldForNeverSeen) are what Causeless told ooaaaoaoao to play with for "how much pass-through of vision there is" through walls. The smoothing distances control edge softness. Real settings UI would surface these (per §8.7); for now they're debug-only.

3.6   What's pending in the visual model

From the same transcript — Causeless said: “the solution is to do both: some amount of pushing INTO FoW mask (like in this branch), and also a pre-smoothing step where we sample the FoW mask with bilinear interpolation.” The pre-SDF smoothing step is acknowledged as a TBD in his head; the branch as-is uses SDF distance for smoothing rather than a pre-blur pass. Not blocking on this for the PR — the existing SDF approach works, the pre-smoothing is a nice-to-have improvement that lives in the future-design bucket (§7).

5  ·  The IsUnseen split — the design call worth your eyes

The decision

Your bdb3c9bbd ("Unseen is now 'ever unseen', not current FoW") repointed SceneMan::IsUnseen at GetUnseenLayerTerrainMask — the ever-unseen memory mask — with explicit "OR has seen the space" comments on the HDFirearm/HeldDevice DrawHUD callsites you added in the same commit. That's the right semantic going forward, but it changes the contract every existing caller was written against.

Rather than revert your rename, we added a second method: IsCurrentlyUnseen(), which checks the current-FoV mask (the old IsUnseen semantic). Mods (and the renderer's two-stage shader path) can now choose:

  • IsUnseen() → ever-unseen / memory layer (your new semantic, unchanged)
  • IsCurrentlyUnseen() → current FoV (the old IsUnseen semantic, restored)

One new method on the Lua API surface. The old name keeps working. Reviewer call: is this the right API shape, or do you want the names reversed (IsUnseen = current, IsEverUnseen = memory)? Either is implementable in five minutes — we chose this one because bdb3c9bbd already shipped the new semantic and your in-source comments on the DrawHUD callsites read most naturally with it.

6  ·  The AI callsite P0 — survives the redesign

The headline P0 we caught and need to ship

The vanilla AI Lua scripts still call IsUnseen and get the new ever-unseen semantic — so they think every patch of terrain ever scouted is currently visible. Result: AI shoots through the dimmed memory layer at targets you can't see. The IsCurrentlyUnseen() method this PR added solves the API-level mod-compat (the method exists), but the callsite-level fix — updating ~30 vanilla AI callsites from IsUnseen → IsCurrentlyUnseen — is still ahead. This P0 is orthogonal to the directional-reveal misread; it survives the redesign because it's about the API contract, not the ray-cast direction.

Detail audit lives in §8.1. Estimated effort: ~2–4 hours of focused work given the callsite table in §5.1. The change is mechanical — IsUnseen → IsCurrentlyUnseen at each perception/visibility callsite, leaving any "has the team ever seen this" callsites alone. The VoidWanderers Tactics.lua:1065 savegame line is the most consequential single fix (silent save corruption if missed).

7  ·  What's genuinely TBD as future design

Per the March 2–3 transcript between Causeless, ooaaaoaoao, Naitor, Jeff, HeliumAnt, Bebomonky, bad.beaver, easter cherkov, and Fairyartos — here's the design conversation that establishes what's still ahead. None of these block the PR landing; all of them are upstream-owned design calls that we'd happily implement to spec once the design lands but won't drive ourselves.

7.1   Cameras — stationary vision sources

Naitor: “there should be a new building type that lets you see things constantly inside your base” — ooaaaoaoao replied “cameras, yes! will be done”. The design fit: each camera has its own position, arc, range, and team affiliation. Implementation-wise it'd mirror AHuman::Look() — same SeeRay primitives, just dispatched from a stationary entity rather than an actor. Could be a new Camera entity class or a property on existing emplaced entities (turrets, sensors, etc.). Tunability question: per-camera FOVSpread / arc, or fixed?

7.2   Doors as dynamic FoW apertures

Jeff (joking): “Every door will now be a new chance to die horribly to something surprising and unforeseen. Suggestion: install more doors.” — Causeless: “It should be adjustable in the same way.” Doors as opening / closing apertures that affect FoW propagation. Sky rays that pass through an open doorway should illuminate the room beyond (until next sky-ray frame after the door closes). The "adjustable in the same way" line suggests per-door tunable parameters analogous to per-camera / per-actor — arc width, range, opacity contribution.

7.3   Pre-SDF smoothing step

Causeless: “the solution is to do both: some amount of pushing INTO FoW mask (like in this branch), and also a pre-smoothing step where we sample the FoW mask with bilinear interpolation.” The current branch uses negative-distance SDF for smoothing; Causeless's idea is to add a pre-blur pass that smooths the raw FoW mask before SDF computation. Goal: reduce the "stepping effect" that comes from raw pixel-position distances being discontinuous.

7.4   Team-owned bunker permanent vision

Causeless's idea from the same transcript — “team-owned bunkers could have permanent vision while enemy bunkers are FoW. The idea being that to breach an enemy bunker would require adequate equipment and tooling.” trulythepawn proposed “recon grenades” as the breach tool. Mechanics-wise: a permanently-revealed region centered on each team-owned bunker module; enemy-bunker FoW behaves normally. New gameplay mechanic, not a rendering fix — deliberate design.

7.5   The double-buffering hack

Causeless's 031a77b6d “hack until double-buffering is in” — the branch currently has a stopgap waiting for proper double-buffered FoW mask updates. ooaaaoaoao noticed in the March transcript that FillUnseenLayerMask was allocating + filling an entirely new bitmap every frame — Causeless: “We have tracked scenelayers btw, where it double-buffers and clears in the background.” The double-buffering integration is the proper fix; current state is the hack.

7.6   Splitscreen FoW

The TODO- this needs to be done above, per screen! Right now splitscreen is fucked comment in FrameMan::Draw is Causeless's own marker. Per-screen FoW state for multiple local players isn't wired up. Not a regression from our PR — pre-existing TBD. Audit in §8.2.

7.7   Scene reentry / MetaGame transitions

Per branches.html's audit, scene-reentry FoW (leave + return to scene) doesn't preserve FoW state cleanly. MetaGame mission transitions, mid-mission saves, and activity restarts all need verification. Partially handled by our PR's be8734ec4 sentinel fallback for the MakeAllUnseen path, but not exhaustively tested. Audit in §8.3.

7.8   Per-actor FOVSpread configurability

Currently Actor::CastSeeRays() hardcodes Look(100, ...) — 100° spread for AHumans, identically for everyone. Different actor classes / per-actor tuning would let dropships have narrow forward cones, scouts have wider cones, snipers extend the cone with sharp-aim (m_AimDistance + SharpLength already does this, but only the range, not the spread). Open question: tie spread to existing m_Perceptiveness, or introduce a separate m_FOVSpread field?

7.9   The GPU rendering migration ooaaaoaoao started

March 3 transcript — ooaaaoaoao + HeliumAnt collaborated on moving the per-frame CPU tri-blits onto the FoW mask to GPU rendering via raylib render targets. HeliumAnt reported dropping from 2000fps to 1500fps when drawing every MO every frame (vs blitting the MO layer) — meaningful perf headroom.
