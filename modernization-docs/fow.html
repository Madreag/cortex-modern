2  ·  The IsUnseen split — the design call worth your eyes

The decision

Your bdb3c9bbd ("Unseen is now 'ever unseen', not current FoW") repointed SceneMan::IsUnseen at GetUnseenLayerTerrainMask — the ever-unseen memory mask — with explicit "OR has seen the space" comments on the HDFirearm/HeldDevice DrawHUD callsites you added in the same commit. That's the right semantic going forward, but it changes the contract every existing caller was written against.

Rather than revert your rename, we added a second method: IsCurrentlyUnseen(), which checks the current-FoV mask (the old IsUnseen semantic). Mods (and the renderer's two-stage shader path) can now choose:

  • IsUnseen() → ever-unseen / memory layer (your new semantic, unchanged)
  • IsCurrentlyUnseen() → current FoV (the old IsUnseen semantic, restored)

One new method on the Lua API surface. The old name keeps working. Reviewer call: is this the right API shape, or do you want the names reversed (IsUnseen = current, IsEverUnseen = memory)? Either is implementable in five minutes — we chose this one because bdb3c9bbd already shipped the new semantic and your in-source comments on the DrawHUD callsites read most naturally with it.

3  ·  CastSeeRays scaling for smooth perimeter

At large sightRadius (the 600+ HUDs we have in some larger scenes), the fixed rayCount was producing visible perimeter gaps — the rays were spaced too sparsely along the arc, so the FoW circle looked like a many-pointed star instead of a circle. Easy fix: scale the rayCount with the radius so the arc-gap between rays stays roughly constant.

rayCount = max(36, 2π × sightRadius / 6)

That gives a per-ray arc-gap of ~6 px regardless of sightRadius. At the default radii (~80–120 px) the formula clamps at max(36, ...) and behaves identically to the previous fixed count. At larger radii it scales up linearly. Visual result: smooth circle at any zoom / perceptiveness.

Cost: more rays = more CPU per actor. For a typical scene this is invisible; for the worst case (50-bot scene with snipers at large sightRadius), the per-actor cost goes up linearly with radius. See §5 for the perf disclosure.

Touch-points: Source/Entities/Actor.cpp — CastSeeRays() body. Two-line diff in the rayCount calculation; the rest of the function (the ray-casting loop) is unchanged.

4  ·  The crash fix — null deref in CommitToLastSeenTerrainWithFowMask

Repro per cortex-modern build-audit (2026-05-17, documented on Upstream Issues): start a standard Skirmish Defense match with FoW enabled on a scene that doesn't pre-create the unseen layer for every participating team. The game crashes immediately on activity start with a null deref in SceneMan::CommitToLastSeenTerrainWithFowMask.

4.1   Root cause

The two-stage FoW shader path was added with an implicit assumption that every team participating in a FoW-enabled activity has had its unseen layer constructed. That assumption holds during normal play once each team's first actor spawns — but it does not hold at the moment CommitToLastSeenTerrainWithFowMask first runs, which is before the layer-create path has run for teams that don't have any actors yet (e.g., empty AI side at activity start).

4.2   The fix

Null-check the unseen layer pointer before dereferencing it. If the team's layer hasn't been created yet, skip the commit for that team this tick — on the next tick (after the team's first actor spawns and triggers layer creation) the path runs normally. Behavior: no observable change to FoW visuals; no more crash on activity start.

Touch-points: Source/Managers/SceneMan.cpp — CommitToLastSeenTerrainWithFowMask entry. Three-line guard, no functional changes to the rest of the function.

5  ·  Performance — what's tested, what isn't

Honest disclosure

I did not profile this. The CastSeeRays scaling is a per-actor cost that grows linearly with sightRadius — at default radii it's identical to before, but at large radii (the 600+ HUDs we sometimes use), the per-actor ray-cast cost is higher than baseline.

What I did test: ran several scenarios on my machine (a few campaign missions on Metra Plains + a couple of skirmishes) and saw no perceptible frame-time impact. But my PC is overspecced, so this isn't a meaningful test. The worst-case scene (50+ bots with snipers at large sightRadius, on a Steam Deck or older mid-range desktop) was not exercised.

What I'd love: if you have a Tracy capture from a known FoW perf-hotspot scene, send it and I'll A/B against the pre-scaling rayCount. If the scaling is too aggressive, the easy lever is the denominator in the formula (currently / 6 for ~6 px arc-gap) — bumping to / 8 or / 10 gives ~33% to ~67% fewer rays at the same radius. Or we can cap rayCount at, say, 256 to bound the worst case while keeping the visual win at moderate radii.
