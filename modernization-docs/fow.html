FoW — design state & corrected PR

cortex-modern's contribution to upstream's dynamic-fow-negative-distance-test branch. After Causeless flagged three design-intent misreads in our review (one on Discord, two on the PR issue thread), digging into the engine surfaced that the directional reveal he wanted is already implemented in AHuman::Look() — we'd accidentally bypassed it. The PR has been narrowed across two follow-up commits (now 6 total) addressing all three misreads plus the comment-verbosity feedback. This page documents what was found, what was fixed, what still holds, and the genuine future-design TBDs.

tl;dr — the corrected story

What we missed: the directional reveal Causeless wanted is already implemented in AHuman::Look() — a 32-ray body bubble (36 px radius) plus a directional aim-cone (FOVSpread / 0.5 rays centered on m_AimAngle, angle-quantized to avoid flicker as the aim slides). ooaaaoaoao's February commit 32f667559 "ahuman vision bubble now centered on body, not aimpos" set up the bubble; Causeless's e5d6b0e11 "Stop flickering when changing aim angle..." added the angle quantization on the cone. Both already in the branch we built on.

The three design misreads (now all reverted):

  1. 360° fan in Actor::CastSeeRays() — we rewrote the function body instead of calling Look(), bypassing the virtual dispatch and disabling AHuman/ACrab directional vision entirely. Reverted in commit #5 — back to the Look(...) dispatcher.
  2. CastSeeRaysFromSky gated to Editing-only — we misread 4ae962455 "Killed script sky rays" as "all sky rays unwanted." Causeless on GH: "the script rays deletion was a different thing entirely really." Reverted in commit #5 — engine sky rays fire during both Editing and gameplay, producing the outdoor desat + noise + scanline visual differentiation.
  3. useOneStageFoW = false — we overrode the GLSL default true thinking it would hide live MOs from the memory layer. Causeless on GH: "useOneStageFoW = true is set because right now the committing of currently-seen to the terrain mask isn't great... the intent was to move this over to where we can use the actual SDF mask." Reverted in commit #6 — back to the GLSL default until upstream's SDF-mask-based terrain commit lands.

Plus the comment-verbosity feedback: Causeless on GH: "AI comments WAY too much... in-depth comments actually confuse the situation further." Commit #6 trims ~74 lines of explanatory comments throughout the touched files; only the briefest notes for non-obvious invariants remain.

What still holds: the crash fix (CommitToLastSeenTerrainWithFowMask null guard), the MovableMan dynamic_cast null guards, the SDF + sky-ray wrap-class-of-bug fixes (uWrapsXY uniform + sky-ray X-wrap guard), the IsUnseen/IsCurrentlyUnseen split with C++ DrawHUD callsite switches, the MakeAllUnseen (1,1) sentinel fallback, the bg-layer maskReady gating, and the FrameMan FogOfWarSetup palette-stripe fix are all real fixes independent of the reveal direction or render path.

What's still ahead: the headline P0 (vanilla AI Lua callsites still call IsUnseen and get the new ever-unseen semantic — AI shoots through dimmed memory) survives the redesign and needs the ~30 callsite rewrite. Plus genuine future design work the March transcript and Causeless's recent hints make explicit: cameras (stationary vision sources), doors as dynamic apertures, splitscreen FoW, the pre-SDF smoothing step, the double-buffering hack, the SDF-mask-based terrain-commit (which will then unlock useOneStageFoW = false), and team-owned bunker permanent vision. Full audit in §7–§8.

1  ·  AHuman::Look() — the directional reveal already exists

The implementation Causeless described in his Discord review (“reveal FoW in the direction the actor was looking”) is already on the branch — we just didn't see it because we were reading Actor::CastSeeRays(), which is the dispatcher, not the implementation. The real work happens in the virtual Look() override, which AHuman implements with two distinct ray-cast passes.

The two-pass design in AHuman::Look()

Located in Source/Entities/AHuman.cpp at line 1347. Fires once per actor per frame via the Actor::CastSeeRays() → Look(FOVSpread, range) dispatch chain. Both passes use strength = c_PathFindingDefaultDigStrength (matches the pathfinding dig-strength so see-rays pass through light debris and corpses but stop at solid walls).

1.1   The body bubble — 32 rays in 360° at 36 px around body

Short-range omnidirectional reveal around the actor's body position (not eye, not aim). Gives the actor immediate awareness of the space they physically occupy, regardless of where they're facing. ooaaaoaoao introduced this with commit 32f667559 “ahuman vision bubble now centered on body, not aimpos. fix for prev” — they'd briefly tried aim-position-centered and switched to body-centered. Earlier commit be8889316 framed it: “less rays, wider fow, removed see-through-terrain box around ahumans, now a bubble of rays”.

AHuman.cpp:1393–1400 — the body bubble
const float bubblePixelRadius = 36.0f; static int bubbleRayNum = 32; const Vector bubbleCenterPos = GetPos(); Vector bubbleAroundActorLookVector(bubblePixelRadius, 0); for (int i = 0; i < bubbleRayNum; ++i) { g_SceneMan.CastSeeRay(m_Team, bubbleCenterPos, bubbleAroundActorLookVector, ignored, strength, 0); bubbleAroundActorLookVector.RadRotate(2 * PI / bubbleRayNum); }

1.2   The directional aim-cone — FOVSpread / 0.5 rays, angle-quantized

The directional reveal Causeless was asking us to preserve. Cast from aimPos (eye position if a head attachable exists, else body), extending m_AimDistance + range pixels (further when aiming sharp through a barrel). Cone is centered on m_AimAngle, spans FOVSpread degrees, contains FOVSpread / degreesPerRotationSegment rays (with degreesPerRotationSegment = 0.5 → 200 rays for a 100° spread). The aim angle is quantized to fixed angular divisions per Causeless's e5d6b0e11 “Stop flickering when changing aim angle by ensuring that rays are cast at the same angle divisions” — so the rays don't shift visibly as the actor's aim slides smoothly.

AHuman.cpp:1369–1407 — the directional cone (condensed)
float aimDistance = m_AimDistance + range; if (m_Controller.IsState(AIM_SHARP) && m_pFGArm && m_pFGArm->IsAttached() && m_pFGArm->GetHeldDevice()) { aimDistance += m_pFGArm->GetHeldDevice()->GetSharpLength(); // extend when aiming sharp } float aimAngle = m_AimAngle - RTE::DegreesToRadians(FOVSpread * (m_HFlipped ? -0.5f : 0.5f)); static float degreesPerRotationSegment = 0.5f; const float numRotationalSegmentsPerSide = 180.0f / degreesPerRotationSegment; const float quantization = numRotationalSegmentsPerSide / c_PI; aimAngle = std::round(aimAngle * quantization) / quantization; Matrix aimMatrix(m_HFlipped ? -aimAngle : aimAngle); aimMatrix.SetXFlipped(m_HFlipped); Vector lookVector(aimDistance, 0); lookVector *= aimMatrix; const int rayNum = FOVSpread / degreesPerRotationSegment; // 200 rays for FOVSpread=100° for (int i = 0; i < rayNum; ++i) { g_SceneMan.CastSeeRay(m_Team, aimPos, lookVector, ignored, strength, 0, MOIDsToIgnore); lookVector.DegRotate(FOVSpread / (rayNum - 1)); }

1.3   Per-subclass dispatch

Different actor types have different Look() overrides. Actor::CastSeeRays() calls Look(100, screenWidth * 0.7 * m_Perceptiveness) once per frame; virtual dispatch routes to the appropriate override based on actor class.

ClassWhat Look() doesRays/frame (FOVSpread=100)
AHuman 32-ray body bubble (36 px) plus 200-ray directional aim-cone centered on m_AimAngle ~232
ACrab Single aim-direction ray from GetCPUPos() (or mounted-weapon position if aiming sharp) with random ±FOVSpread/2 spread 1
ACraft Inherits Actor::Look() base — no override 1 (velocity-direction)
Actor base (fallback) Single velocity-direction ray with FOVSpread spread; if velocity is near-zero, random 360° angle 1

Asymmetry note: ACrab's vision is much weaker than AHuman's per-frame (1 ray vs ~232). That's consistent with the design framing — crabs are creatures, humans are intel-gathering soldiers with proper situational awareness. Tuning this further (more crab rays? wider crab arc?) is open design territory.

1.4   The clue we missed in the source itself

SceneMan::CastSeeRaysFromSky in SceneMan.cpp at line 1070 has an explicit comment: “These are the same as for AHuman::Look()” — referring to the strength and skip values. The sky-ray system literally treats AHuman::Look() as the canonical see-ray reference. Had we read that comment, we'd have followed the breadcrumb to AHuman.cpp:1347 and avoided the whole misread. Process lesson: when overriding a virtual function in a base class, grep all subclass overrides before rewriting the base.

2  ·  The misreads & the fix

Causeless flagged three design-intent misreads in our PR — one on Discord (the directional reveal), two on GH (sky rays + useOneStageFoW). Plus a fourth piece of feedback (excessive comment verbosity). All addressed in two follow-up commits (#5 and #6).

Misread #1 — rewrote Actor::CastSeeRays() as a 360° fan

What we wrote: replaced the function body (which was Look(100, ...) calling once per frame) with a hardcoded 36-ray (later scaled with radius via cd17a0466) 360° fan calling CastSeeRay directly. Bypassed the virtual Look() dispatch entirely.

What we missed: AHuman::Look() is the directional implementation (§1). Actor::CastSeeRays() is the dispatcher; rewriting it without calling Look() means AHuman::Look() and ACrab::Look() never run. We disabled the existing directional reveal across all actor classes in one stroke.

What Causeless flagged in Discord: that the change was a departure from the planned and intended design — vision should reveal only in the direction the actor is looking, not as a 360° fan.

Fix (commit #5): Actor::CastSeeRays() back to its dispatcher form.

Misread #2 — gated engine CastSeeRaysFromSky to Editing-only

What we wrote: in MovableMan::Update, wrapped the CastSeeRaysFromSky thread-pool dispatch in if (gameActivity->GetActivityState() == Activity::Editing). During gameplay, sky rays no longer fired.

What we missed: Causeless's 4ae962455 “Killed script sky rays” — the word "script" matters. He killed the Lua-script-driven sky-ray spawns (e.g., SetupFogOfWar(...) calls in SkirmishDefense.lua), not the engine-side CastSeeRaysFromSky dispatch. The engine dispatch is the faux-lighting mechanism: sky rays reach all outdoor tiles every frame, keeping them in the Visible state, while indoor (sky-blocked) tiles fall into Memory or Never-seen. Without it, ALL terrain looks the same — no outdoor vs. bunker visual distinction.

What Causeless saw (GH issue thread): “CastSeeRaysFromSky() is intended for gameplay, not just editing. The intent is to give a clear difference in gameplay between outdoors fighting and indoors bunker clearing. When in an enclosed area or tunnel, we'll have the two-stage FoW whereas outdoors is always bright and visible... a faux lighting system (as underground areas are naturally darker when unseen). The script rays deletion was a different thing entirely really.”

Fix (commit #5): MovableMan::Update's sky-ray dispatch restored to fire during both Editing and gameplay.

Misread #3 — useOneStageFoW = false override

What we wrote: in FrameMan::BackgroundShaderSetUniforms, added static bool useOneStageFoW = false; backgroundShader.SetBool("useOneStageFoW", useOneStageFoW); — flipping the shader from "darken current frame in memory area" to "render saved lastSeenTerrain in memory area." Framing in our commit message: "so live MOs no longer bleed through the dim memory layer."

What we missed: the saved lastSeenTerrain bitmap is built from the CPU mask, but the CPU mask doesn't reflect what the SDF actually renders. The SDF "digs into the terrain" — meaning the visible sight area extends further than the CPU mask records. So when our useOneStageFoW = false kicked in, the memory layer rendered incomplete/wrong terrain pixels. Causeless's `= true` default was intentional precisely because the SDF-mask-based commit hasn't landed yet.

What Causeless saw (GH issue thread): “useOneStageFoW = true is set because right now the committing of currently-seen to the terrain mask isn't great. This is being done with the raw CPU mask, which doesn't properly update everything in the sight area (as the actual rendered sight area digs into the terrain). The intent was to move this over to where we can use the actual SDF mask to copy the exact pixels that are currently visible.”

Fix (commit #6): removed our override entirely; the GLSL default uniform bool useOneStageFoW = true; in Background.frag takes effect. Side effect to know about: with useOneStageFoW = true, live enemy actor sprites will render through the memory layer (darkened) until upstream's SDF-mask-based terrain-commit lands — this is the limitation Causeless observed in his underground screenshot ("actor looking left, enemies still showing up in dimmed FoW"). Documented in §3.7 as a known limitation pending upstream's planned commit; not something for our PR to "fix."

Feedback #4 — excessive comment verbosity

What we wrote: 112 added comment lines across the PR delta, including multi-paragraph blocks explaining null-deref guards, dispatcher functions, maskReady-gated calls, and sky-ray dispatch.

What Causeless saw (GH issue thread): “AI comments WAY too much. It very much confused and muddies the code when the AI feels the need to add several paragraphs explaining things as mundane as a null dereference fix or other minor adjustments. These things are self-explanatory and if anything, the in-depth comments actually confuse the situation further (especially when it's unclear if the comment is referring to an old problem or an extant one).”

Fix (commit #6): aggressive trim — ~74 lines of comments removed across Actor.cpp, FrameMan.cpp, MovableMan.cpp, SceneMan.cpp, and the SDF shader. Kept only short single-line notes for the non-obvious invariants (the bg-layer FBO gate one-liner, the (1,1) sentinel rationale, the wrap-class-of-bug short note). Multi-paragraph explanations of self-evident code are gone.

Two minor housekeeping items rolled into commit #6:

  • SkirmishDefense.lua initial-reveal radius shrink reverted. The rationale was tied to the 360° fan we reverted in misread #1; with AHuman::Look() driving directional vision, leave upstream Lua content alone.
  • cd17a0466 "CastSeeRays scaling" is now dead code (the rayCount field it scaled is gone with misread #1's revert). Commit kept in history for traceability; runtime cost zero. Easy to drop via force-push if you'd prefer a tighter diff.

3  ·  The visual model — mostly already implemented

The visual completeness Causeless described (outdoor differentiated from bunker via sky rays + desat + noise + scanline) is largely already in place on the branch. The March transcript between Causeless and ooaaaoaoao spent hours tuning it — SDF thresholds, smoothing distances, bunker-wall calibration, scanline blend. What our PR did was accidentally break the differentiation (misread #2) and override an intentional default (misread #3). With both reverts applied, the visual model returns to its pre-PR state.

3.1   Three FoW states per tile (the faux-lighting model)

Sky rays and actor see-rays feed the same per-team current-FoV mask. The shader samples that mask plus the ever-seen mask, giving three possible states per tile. Outdoor tiles are perpetually in the Visible state because sky rays reveal them every frame — Memory and Never-seen only really materialize indoors / underground. This is the "faux lighting" Causeless described.

StateTriggerVisual treatmentIn practice
Visible Tile currently reached by an actor see-ray OR a sky ray this frame Full terrain + MOs render normally; no FoW overlay All outdoor tiles every frame (sky rays); indoor tiles inside an actor's body bubble or aim cone
Memory Tile was Visible previously, but is not currently reached Darken=0.68 + desat=0.8 + scanline + noise overlay (the shader's ApplyDarkenAndDesat + ApplyScanlineAndNoise path — the desaturated, noisy, scanline visual treatment Causeless designed for non-Visible areas). With useOneStageFoW = true the current frame is darkened in place; once upstream's SDF-mask-based terrain-commit lands and useOneStageFoW flips to false, rteTextureLastSeen (saved terrain bitmap, no live units) takes over. Indoor corridors you walked through then turned away from
Never-seen Tile never reached by any see-ray Darken=0 (full black) + scanline+noise (effectively invisible due to darken). The claustrophobic bunker interior. Indoor areas no actor has ever scouted; covered alcoves below terrain

3.2   Why the sky-ray dispatch is the differentiator

SceneMan::CastSeeRaysFromSky casts rays from the top of the screen downward every frame, calling the same CastSeeRay primitive AHuman::Look() uses. Each ray clears the per-team current-FoV mask wherever it reaches. Outdoor tiles (nothing above to block) get a sky-ray reach + clear every frame, so they're perpetually Visible — the "outdoors is always bright and visible" Causeless described. Indoor tiles (below terrain) don't get sky-ray coverage, so they're only revealed by actor see-rays and fall into Memory when actors leave, or stay Never-seen if no actor ever reaches them. That's the mechanism behind "difference between outdoors and bunker gameplay" — not a separate detection pass, just a direct consequence of which tiles sky rays reach. Our misread #2 disabled sky rays during gameplay, collapsing the differentiation; commit #5 restored it.

3.3   Bunker wall calibration is already done

The see-through distance through walls was specifically tuned by Causeless to be about the width of a typical bunker wall. The negative-distance SDF on this branch was chosen to fix the over-penetration problem that earlier positive-SDF + large-revealsize attempts had. The branch name (dynamic-fow-negative-distance-test) is a settled solution to a known visual problem, not a speculative experiment.

3.4   Wrap handling is fixed by our PR

One of the real bugs be8734ec4 caught and fixed: the SDF shader and sky-ray dispatch both treated scenes as toroidal unconditionally, with no check on WrapsX/WrapsY. On non-wrapping scenes (most CC scenes) the sky rays wrapped to off-screen positions when the camera panned near an edge, leaving camera-dependent dim/bright bands. Our fix added uniform vec2 uWrapsXY to SDF_3_UnsignedSDF.frag and matching guard logic to SceneMan::CastSeeRaysFromSky. Survives the reverts — the wrap fix is in a different region of the codebase than the design misreads.

3.5   The 6 tunable static floats Causeless exposed

From the March transcript — Causeless made these six values static float rather than constants specifically so they could be adjusted live in-game during tuning:

FrameMan.cpp — live-tunable smoothing knobs (upstream)
static float usdfThresoldForFoV = 0.02f; // how aggressive the current-FoV SDF mask is static float usdfOpacitySmoothingDistanceForFoV = 0.02f; // FoV edge softness static float usdfThresoldForNeverSeen = 0.015f; // memory-vs-never-seen boundary static float usdfOpacitySmoothingDistanceForNeverSeen = 0.01f; // memory-edge softness static float scanlineAndNoiseOpacitySmoothingDistance = 0.015f; // outdoor scanline blend distance static float unseenNoiseIntensity = 0.02f; // outdoor noise opacity

Our PR didn't touch these (intentionally — they're his tuning surface). The first two (usdfThresoldForFoV and usdfThresoldForNeverSeen) are what Causeless told ooaaaoaoao to play with for "how much pass-through of vision there is" through walls. Real settings UI would surface these (per §8.7); for now they're debug-only.

3.6   Pre-SDF smoothing is acknowledged TBD

Causeless has described the planned approach as combining the current "push into the FoW mask" technique with an additional pre-smoothing step (bilinear interpolation sample of the FoW mask before SDF computation). The branch as-is uses SDF distance for smoothing rather than a pre-blur pass. Future work in §7.3.

3.7   Known limitation — enemy sprites visible (dimmed) in memory layer underground

Causeless's underground observation

Causeless flagged this on Discord with a screenshot: actor underground looking left, but enemies still showing up in the dimmed FoW area (i.e., visible despite being outside the actor's current cone). This is the limitation Causeless's useOneStageFoW = true default acknowledges.

Why it happens: with useOneStageFoW = true, the shader path for the memory layer renders the current frame darkened (terrain + live MOs from moColor) rather than the saved lastSeenTerrain bitmap. Live MOs — including enemy actors — are visible but dimmed in memory areas. There's no per-MO FoW gate at the sprite-render layer (only at the HUD-overlay layer, which our PR did wire up via IsCurrentlyUnseen).

Why useOneStageFoW = false isn't the fix: Causeless explained this is exactly why the GLSL default is true. With = false, the memory layer renders the saved lastSeenTerrain bitmap — but that bitmap is built from the raw CPU mask, which doesn't reflect what the SDF actually rendered (the SDF "digs into the terrain"). So = false produces incorrect terrain in memory areas. Currently a worse bug than the enemy-sprites-dim issue.

The proper fix is upstream's: move the commit-to-lastSeenTerrain step over to use the actual SDF mask, so the saved bitmap matches what's rendered. Once that lands, useOneStageFoW flips to false naturally and enemy sprites stop bleeding through the memory layer. Our PR's role is to not block that future flip — commit #6 removed our override so the GLSL default takes effect today, and the eventual flip-to-false will work cleanly when upstream lands the SDF-mask commit.

Alternative for the interim: a per-MO sprite-render IsCurrentlyUnseen gate (like the HUD-overlay checks we added, but on the sprite-draw path) would hide enemy actors in memory areas independent of the shader path. This is a meaningful gameplay change — not just a render fix — so it belongs in upstream's design hands, not as a contributor patch.

5  ·  The IsUnseen split — the design call worth your eyes

The decision

Your bdb3c9bbd ("Unseen is now 'ever unseen', not current FoW") repointed SceneMan::IsUnseen at GetUnseenLayerTerrainMask — the ever-unseen memory mask — with explicit "OR has seen the space" comments on the HDFirearm/HeldDevice DrawHUD callsites you added in the same commit. That's the right semantic going forward, but it changes the contract every existing caller was written against.

Rather than revert your rename, we added a second method: IsCurrentlyUnseen(), which checks the current-FoV mask (the old IsUnseen semantic). Mods (and the renderer's two-stage shader path) can now choose:

  • IsUnseen() → ever-unseen / memory layer (your new semantic, unchanged)
  • IsCurrentlyUnseen() → current FoV (the old IsUnseen semantic, restored)

One new method on the Lua API surface. The old name keeps working. Reviewer call: is this the right API shape, or do you want the names reversed (IsUnseen = current, IsEverUnseen = memory)? Either is implementable in five minutes — we chose this one because bdb3c9bbd already shipped the new semantic.

6  ·  The AI callsite P0 — survives the redesign

The headline P0 we caught and need to ship

The vanilla AI Lua scripts still call IsUnseen and get the new ever-unseen semantic — so they think every patch of terrain ever scouted is currently visible. Result: AI shoots through the dimmed memory layer at targets you can't see. The IsCurrentlyUnseen() method this PR added solves the API-level mod-compat (the method exists), but the callsite-level fix — updating ~30 vanilla AI callsites from IsUnseen → IsCurrentlyUnseen — is still ahead. This P0 is orthogonal to the three reveal-direction misreads; it survives the corrections because it's about the API contract, not the ray-cast direction.

Detail audit lives in §8.1. Estimated effort: ~2–4 hours of focused work given the callsite table in §5.1. The change is mechanical — IsUnseen → IsCurrentlyUnseen at each perception/visibility callsite, leaving any "has the team ever seen this" callsites alone. The VoidWanderers Tactics.lua:1065 savegame line is the most consequential single fix (silent save corruption if missed).

7  ·  What's genuinely TBD as future design

Per the March 2–3 transcript between Causeless, ooaaaoaoao, Naitor, Jeff, HeliumAnt, Bebomonky, bad.beaver, easter cherkov, and Fairyartos — here's the design conversation that establishes what's still ahead. None of these block the PR landing; all of them are upstream-owned design calls that we'd happily implement to spec once the design lands but won't drive ourselves.

7.1   Cameras — stationary vision sources

Acknowledged as planned upstream — community asked about a building type for permanent interior base vision; ooaaaoaoao confirmed cameras are on the roadmap. Implementation-wise it'd mirror AHuman::Look() — same SeeRay primitives, dispatched from a stationary entity. Could be a new Camera entity class or a property on existing emplaced entities (turrets, sensors). Per-camera arc / range / team would mirror per-actor tunables.

7.2   Doors as dynamic FoW apertures

Causeless has indicated doors will be tunable in the same way as other vision sources. Doors as opening / closing apertures affecting FoW propagation; sky rays that pass through an open doorway illuminate the room beyond, closing the door cuts that off. Per-door tunable parameters analogous to per-camera / per-actor.

7.3   Pre-SDF smoothing step

Per Causeless's stated approach, the eventual rendering pipeline combines the current push-into-FoW-mask technique with an additional pre-smoothing step (bilinear-interpolation sample of the FoW mask before SDF computation). Goal: reduce the "stepping effect" from raw pixel-position distances being discontinuous. Current branch uses SDF distance for smoothing without the pre-blur pass — works, the pre-smoothing is a refinement.

7.4   SDF-mask-based commit to lastSeenTerrain

The big one Causeless flagged in his GH review — the current commit-to-lastSeenTerrain is done with the raw CPU mask, which doesn't reflect what the SDF actually rendered. The plan is to move this over to use the SDF mask so the saved lastSeenTerrain bitmap matches what's rendered. Unlocks useOneStageFoW = false — once this lands, the two-stage memory layer renders the saved terrain bitmap (no live MOs bleeding through) and the underground enemy-visibility issue in §3.7 goes away automatically.

7.5   Team-owned bunker permanent vision

Causeless has floated the idea that team-owned bunkers would have permanent vision while enemy bunkers stay FoW — breaching an enemy bunker requiring proper tooling (e.g., recon equipment). Mechanics-wise: a permanently-revealed region centered on each team-owned bunker module; enemy-bunker FoW behaves normally. New gameplay mechanic, not a rendering fix — deliberate design direction.

7.6   The double-buffering hack

Causeless's commit 031a77b6d (title: "hack until double-buffering is in") flagged that the branch currently has a stopgap waiting for proper double-buffered FoW mask updates. CC already has a tracked-scenelayers mechanism that double-buffers and clears in the background; the plan is to wire FoW into that.

7.7   Splitscreen FoW

The TODO- this needs to be done above, per screen! Right now splitscreen is fucked comment in FrameMan::Draw is Causeless's own marker. Per-screen FoW state for multiple local players isn't wired up. Not a regression from our PR — pre-existing TBD. Audit in §8.2.

7.8   Scene reentry / MetaGame transitions

Per branches.html's audit, scene-reentry FoW (leave + return to scene) doesn't preserve FoW state cleanly. MetaGame mission transitions, mid-mission saves, and activity restarts all need verification. Partially handled by our PR's be8734ec4 sentinel fallback for the MakeAllUnseen path, but not exhaustively tested. Audit in §8.3.

7.9   Per-actor FOVSpread configurability

Currently Actor::CastSeeRays() hardcodes Look(100, ...) — 100° spread for AHumans, identically for everyone. Different actor classes / per-actor tuning would let dropships have narrow forward cones, scouts have wider cones, snipers extend the cone with sharp-aim. Open question: tie spread to existing m_Perceptiveness, or introduce a separate m_FOVSpread field?

7.10   The GPU rendering migration ooaaaoaoao started

March 3 transcript — ooaaaoaoao + HeliumAnt collaborated on moving the per-frame CPU tri-blits onto the FoW mask to GPU rendering via raylib render targets. HeliumAnt reported dropping from 2000fps to 1500fps when drawing every MO every frame — meaningful perf headroom. Unclear from the transcript whether this work landed or was abandoned mid-iteration. Worth grepping upstream/gpu-renderer and upstream/interpolated-render-redux for the actual state.

7.11   HUD / FX visibility design calls (P1)

Per-element visibility through dim/memory areas needs to settle: muzzle flashes, explosions, particle effects, sound propagation, HUD indicators, damage numbers, waypoints, aim reticle. The original FoW was just-black; the new branch has texture-aware visual treatment that lets these questions be answered case-by-case. Per-element table in §8.6.
