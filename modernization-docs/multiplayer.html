Networking · No-Compromise Edition

Multiplayer

Cortex Command's networked multiplayer was removed in January 2025. This page is the committed plan to rebuild it as the best possible multiplayer CC can have: how the old netcode worked from a direct read of the source; why it cannot simply be switched back on; the architecture being built in its place; the C++ engine work in detail; what it means for existing mods; the milestones from determinism foundation through Controller wire/replay, playable lockstep, snapshot/resync/replay, optional rollback gating, and public hosting; and how every step is validated automatically. It is written to be built from — an engineer or an AI coding agent should be able to read this page and start.

Current plan — 2026-06-16 · Controller-sync lockstep first, rollback gated

Current source of truth: D:/Projects/MULTIPLAYER_BEST_PLAN.md. The active Stage 2 plan is: build the Controller wire/replay synctest first, ship playable Controller-sync deterministic lockstep next, add snapshot/resync/replay infrastructure after that, and only implement bounded rollback if playtests plus snapshot/re-sim measurements prove it is needed and feasible. Older sections on this page that describe online co-op as server-auth prediction or PvP as mandatory GGPO rollback are historical design notes, not the current implementation sequence.

Status — 2026-06-05 · Stage 1 foundation DONE & cross-platform GREEN; Stage 2 (this page) is next

The project runs on clean stage trunks per Causeless's 2026-05-25 review feedback. Stage 1 — the deterministic simulation foundation that all of this multiplayer rides on — is now BUILT and verified bit-identical on Windows + Linux + macOS (a multi-core run replays identically to a single-core run; that was the entire hard problem of Stage 1, and it is finished). The foundation is packaged into 8 small, per-concern PRs (#3–#10) on determinism-revamp; PRs 3–9 are built and determinism-GREEN in the integrated build, PR 10 (the CI safety-net) is being built now, and nothing is upstream yet beyond the two LuaJIT PRs already merged (#279, #280). Once those ship to Causeless one at a time, Stage 2 — the multiplayer this page plans — begins on multiplayer-revamp (cut from the Stage-1 tip), milestones M6→M10. The canonical foundation status is D:/Projects/PRs/PR_ROADMAP.html; the master is D:/Projects/HANDOFF.md.

The architecture this page builds on, as settled by that work:

  • Controller-sync MP architecture (ADR-018) — the deterministic boundary is the Controller wire. Each machine runs its own AI (with async pathfinding, in its own Lua state pool) for the actors it owns; only Controllers cross the network. ADR-016 originally rejected this; Causeless's clarification of the async-pathfinding rationale + lockstep/rollback being implementable on the Controller wire reverses that. M7+ ships Controller-sync from day one. The pathfinder serial-epilogue and Race A architectural fix are never reapplied to revamp trunks.
  • FPU + libm standardization for cross-platform (not M3 Q40.24 fixed-point) — the chosen path, proven by the cross-platform-GREEN result. Standardize the libm choice + -ffp-contract=off everywhere. M3 Q40.24 was rejected ("really no benefit" given Lua-float cross-platform determinism); it stays in modernization-effort only and is never reapplied.
  • Smaller per-concern PRs — Causeless's review feedback applied to every revamp PR. No more bundled mega-PRs.
  • Separate AI Lua states at M8 — Causeless's stated upstream design intent: AI runs per-machine in a non-deterministic AI Lua pool; sim Lua remains deterministic; only Controllers cross the network.

The end goal is best-possible MP across PvE, PvP, and PvPvE. Rollback remains an optional later tool, not the definition of Stage 2 completion. See ADR-018, ADR-019, and ADR-024 in the Decision Log; Stage 2 detail: D:/Projects/MULTIPLAYER_REVAMP_PLAN.md and the current plan D:/Projects/MULTIPLAYER_BEST_PLAN.md.

The headline

Networked play was one of Cortex Command's most-wanted features and one of its worst-executed: the 2019 open-source release shipped a server-side screen-streaming model so bandwidth-brutal and laggy that upstream deleted it in January 2025 — the changelog reads “the existing multiplayer implementation was terrible and broken.” Players still improvise around the gap with Steam Remote Play, Radmin VPN and raw IP entry. ADR-013 reopened the question; ADR-015 chose state-replication co-op as the build; this page's ADR-016 pivot revises the order to determinism-first, with per-mode netcode shipping above it.

cortex-modern will rebuild multiplayer as a fully deterministic simulation core with four netcode modes layered on top: LAN lockstep (the Factorio ceiling), online co-op (server-auth + client prediction + reconciliation, the Teardown shipped path), PvP arena (GGPO-style rollback netcode), and public hosting (server-auth + interest management). All four ride one engine; the determinism contract is what makes them cheap to layer.

1  ·  How Cortex Command's multiplayer worked

Before rebuilding it, see it clearly. Everything below is from a direct read of the networking source still in the tree: Source/Managers/NetworkServer.cpp/.h, NetworkClient.cpp/.h, Source/System/NetworkMessages.h, the commented-out Source/Activities/Multiplayer*.cpp, and the vendored external/sources/RakNet. The shape that emerges explains both why it was removed and why the replacement is a rebuild, not a revival.

1.1   The model — server-side screen-streaming

Networking was retrofitted onto the 2001-era engine and shipped only with the 2019 open-source release. It was not netcode in the modern sense — it was remote rendering. The server ran the entire simulation and, for each connected client, rendered that client's viewport into a private 8-bit framebuffer, compressed it, and streamed the picture. Clients were thin display terminals. The per-frame server loop:

Server RunGameLoop → one fixed sim tick
The server runs the whole simulation — MovableMan::Update, terrain, every actor and particle — once, for everyone. There is one authoritative sim.
Server NetworkServer::m_BackBuffer8[player]
For each client, the server renders that player's screen into a private 8-bit BITMAP — a full per-player render pass on top of the simulation.
Server LZ4 compress → boxes / lines
The frame is diffed against the previous one (m_UseDeltaCompression), split into rectangular boxes sized under the ~1500-byte MTU, LZ4-compressed, and optionally interlaced to halve bandwidth at the cost of visible degradation.
Server BackgroundSendThreadFunction → RakNet
A dedicated std::thread per client ships ID_SRV_FRAME_* packets over RakNet, with NAT punch-through. Terrain edits go separately as ID_SRV_TERRAIN.
Client NetworkClient → decompress → blit
The client decompresses the boxes and blits them straight to its screen. It simulates nothing. It is a video player.
Client MsgInput → ID_CLT_INPUT
The client sends back only input — mouse position, buttons, the packed InputElementState bitfield. Nothing else ever leaves the client.

The cost was what you would expect of streaming a video feed per player: 6–10 Mbit/s and roughly 0.75 of a CPU core per client, on top of the simulation, at a 30 fps encode rate, with a hard c_MaxClients cap. Even the terrain half was the worst possible design — MsgTerrainChange ships a rectangle of raw bitmap bytes (X, Y, W, H plus a compressed pixel blob), not the meaning of the edit. It worked on a LAN; it was miserable over the internet.

1.2   Why it will not just switch back on

Upstream's removal (commit 91fe85dd8, PR #179, “RIP Multiplayer 2019-2025”) did not delete the networking files — but reviving them is not an option, for three independent reasons:

The old code is a useful reference — the protocol shape, the message-ID set, the connection and NAT handling, the list of integration points — not a revivable artifact. Its terrain handling is a worked example of what not to do (§9). RakNet itself is abandonware (last release 2014) and is retired with it.

2  ·  The core problem — determinism is the foundation

There are only two ways to keep two machines showing the same game. You can ship the state — every object's position, every frame — which costs bandwidth and needs an authority to arbitrate. Or you can ship the inputs and have every machine recompute the state, which is nearly free on the wire but demands that every machine computes bit-identically. That property is determinism, and in the pivoted plan it is the foundation, not a feature added later.

Non-deterministic today — but closer to determinism-ready than it looks

Upstream-dev review (Causeless) corrected an earlier, gloomier reading here. CC is not deterministic today — but the engine was partly built with determinism in mind. Verified against the source, the honest state:

  • The RNG is closer to ready than feared. The global g_RandomGenerator is seeded by SeedRNG() with a constant compile-time seed (its own comment: “Use a constant seed for determinism” — RTETools.cpp:14), re-applied at every activity start; each Lua script state additionally has its own math.random RNG. Per upstream-dev review none is environment-seeded. The residual is call-ordering under threads — plus one named structural fix, below.
  • The threaded sim has a designed determinism boundary. Lua ThreadedUpdate runs in arbitrary thread order, but scripts that touch simulation state are meant to do so through the SyncedUpdate pass (RequestSyncedUpdate() → MovableMan's synced pass) — a boundary the threading was designed around. The fence exists; it is opt-in, so the residual risk is mods that bypass it.
  • Floating-point is the classic fear — but modern x86 is SSE, not x87, and same-build FP is consistent. The residual is cross-compiler / cross-architecture, handled by FPU + libm standardization (one bundled libm + -ffp-contract=off everywhere) — not by fixed-point. Same-architecture cross-OS bit-identity is already proven GREEN on Windows + Linux + macOS; libm standardization (a later PR) closes the cross-arch / Rosetta gap.
  • Unordered iteration — MovableMan walks objects in registry order; anything that feeds a checksum needs a stable order. Mechanical — sim passes iterate MOID-ordered.
  • Lua pairs() — ~53,000 lines of community Lua iterate tables in hash order. The real residual risk, and it touches mods nobody controls. Fixed engine-side, invisibly, by building LuaJIT with LUAJIT_SECURITY_STRID=0 so stock pairs() iterates string-keyed tables deterministically (string-ids become allocation-ordered); object-keyed sim tables key by UniqueID. No mod-author action; no pairs() replacement.
  • Wall-clock reads in a few sim paths — mechanical to tick-base. Fixed in M1 Block D.

The engine itself names the one structural blocker — a TODO in RTETools.h:85: “Or, in future, a render-thread random, as right now determinism isn't viable because framerate affects sim updates per draw”. The sim and render paths share the one global RNG, so draw rate perturbs the sim's RNG stream; the comment's own fix is to split a sim-thread RNG from a render-thread RNG. That is M1 Block B.

The key idea — full determinism is the foundation, not a feature

The original ADR-015 plan treated determinism as something you grow: a small terrain-only island first, a whole-sim island later. Co-op shipped on the small island; PvP shipped on the total. The pivot reverses this: finish the determinism island before any networking ships. M1–M5 build the deterministic core; M6–M10 layer four netcode modes on top.

The unlock: once the core is fully deterministic, the netcode for each mode becomes a thin adapter, not a separate architecture. Lockstep is a Factorio-class lookup table over a deterministic sim. Online co-op is server-authoritative state replication over the same sim. PvP rollback is GGPO over the same sim. Public hosting is interest-managed snapshot streaming over the same sim. One engine, four modes, each best-in-class for its latency budget.

3.2   The decision — settled

Per-mode netcode on a fully-deterministic core. One sim engine, made deterministic from line one of this build (M1–M5). Above it, four network adapters share a common INetTransport seam (GameNetworkingSockets, the OpenSoldat-validated choice): lockstep for LAN (M7), server-auth + prediction for online co-op (M8), GGPO rollback for PvP arena (M9), interest-managed snapshot for public hosting (M10). Terrain destruction crosses the wire as semantic commands (carve radius R at x,y) regardless of mode — never as pixels — because the destruction math is deterministic and every machine applies it identically.

The pivot trades ~6 months to first MP ship for uncapped scaling of simultaneous actors, physics, and terrain destruction. The current plan capped throughput at one host's CPU (state-replication's structural limit). The pivot uncaps it: every client runs the full sim in parallel.

3.3   What the comparable games prove

Teardown — the blueprint, with a twist

A fully-destructible voxel physics game that shipped MP in March 2026. Their shipped model: destruction replicated as a deterministic command stream, everything else state-synced unreliable with eventual consistency, host-is-server, 12 players, 20 Hz, client-side prediction. But the same blog post ends with a recantation: "Early on, I dismissed the idea of full determinism for the entire engine (a view I have since reevaluated)... we're now trying out simplified approaches [full determinism] in the new engine." The Teardown team is moving past the hybrid. cortex-modern should not lock into yesterday's solution.

Factorio — the lockstep ceiling, validated

Deterministic lockstep, ships only inputs (~500 kbit/s/client), a desync forces a full resync. Works because it was built deterministic — and even then a threading-determinism bug hid for 7 years (FFF-415). Proof the M7 ceiling is real and reachable, and proof that threading is where determinism bites. M4's deterministic-merge work is the named risk-mitigation.

Noita — the cautionary twin

The same per-pixel non-deterministic engine; the studio never shipped MP. The community's true-co-op mod is openly buggy; the popular one sidesteps world sync entirely (separate worlds, shared items). Per-pixel world replication is unsolved by brute force — replicate commands, not pixels. Noita also proves the value of going deterministic-first: if Noita's engine had been deterministic from line one, MP would have shipped.

OpenSoldat — the closest comparable, ships on GNS

2D side-view soldiers, weapons, body physics, long-lived community. Reworked netcode around GameNetworkingSockets v1.4.1, MIT-licensed, active into 2025. CC vault audit documents the architecture: server-first run model, snapshot/delta vocabulary, demo recorder integrated with networking. Validates the GNS transport choice for CC's scope.

Corefall — the determinism-first sibling, now the playbook

The sister project Corefall locked the per-mode netcode architecture in DR-052 (2026-05-06): "Hybrid network model per match mode: server-authoritative simulation + client-side prediction with reconciliation + rollback netcode for PvP arenas + deterministic lockstep for LAN co-op + snapshot interpolation for online co-op + bit-deterministic replay across all platforms." Authority taxonomy: Truth (server-auth), Prediction (client predicted), Presentation (cosmetic, freely diverging), Advisory (hints). Per-tick checksum; cross-platform float pinned at the compiler. cortex-modern adopts the same authority contract — with its own mechanisms: a built-in integer per-tick hash in SimChecksum (not BLAKE3), and FPU + libm standardization (not fixed-point) for cross-platform FP. Where corefall builds it from line one in Rust, cortex-modern retrofitted it into 220K LOC of C++ as the Stage-1 determinism foundation (PRs 3–10, now built + cross-platform GREEN) — substantial work, done; the contract is settled.

4.2   The authority model (Corefall taxonomy adopted)

Every piece of game state falls into one of four classes. The rule is constant: the server owns truth; the client owns feel; the GPU owns richness; advisory hints can be wrong without consequence.

ClassExamplesRule
TruthTerrain, actor health and inventory, projectile hits, gold, the activity/mission state, AI decisions, the save, PvP validation, per-tick checksum.The authoritative sim computes it. Clients display it; they may not contradict it. In lockstep mode, every client IS the authority simultaneously (and they all agree because deterministic).
PredictionThe local player's own actor — movement, jetpack, held weapon, just-fired projectiles.The client predicts immediately for responsiveness, then reconciles to the server snapshot. In lockstep mode this collapses to "every client predicts identically because deterministic."
PresentationCosmetic particles, glows, screen shake, audio, gib debris past its gameplay impact, interpolation smoothing.The client does it freely. Machine-to-machine divergence here is harmless and expected — it is outside the determinism island and uses g_RenderRNG (split from g_SimRNG in M1 Block B).
AdvisoryAI hazard maps, pathfinding hints, broadphase candidates, visibility hints, compression hints.Can be computed by anything (CPU, GPU, server, client). Always validated by the truth path before affecting it. Wrong advisories are recovered without divergence.

4.3   What crosses the wire

Three channels, deliberately different. In lockstep mode only the input channel sees traffic (terrain commands and entity state are recomputed locally). In online co-op / PvP / public modes all three carry traffic.

ChannelDeliveryCarries
Semantic commands (server→client)Reliable, ordered (GNS lane 0)Terrain edits, object spawns/deletes, scene changes — the things that change the structure of the world. Small, count-independent. Applied bit-identically because the sim is deterministic (FPU + libm standardization, not fixed-point).
Entity snapshots (server→client)Unreliable (GNS lane 1)Actor / projectile / debris transforms, velocities, hp — the things that move. Prioritized, interest-managed per client, delta-encoded, quantized, inside a bandwidth budget. A lost packet is corrected by the next snapshot. Not used in lockstep mode (every client recomputes).
Input (client→server, client→all in lockstep)Unreliable, redundant (GNS lane 2, high priority)The player's Controller state. Tiny. Sent redundantly so a lost packet never stalls the sim. In lockstep, the input channel is the only channel that needs to be in sync.

Terrain is the exception that defines the design. CC churns terrain every frame; sending pixels is unbounded (§1, §9). Sending the command — “carve radius R at x,y” — is a fixed handful of bytes regardless of blast size, and it lands inside the determinism island so every machine carves identically.

# terrain edits cross the wire as commands, never pixels — reliable, ordered (GNS lane 0)
terrain.carve    { tick=84210, x=1204, y=880, radius=14, tool="HeavyDigger" }
terrain.dislodge { tick=84210, box=[1190,866, 1218,894] }
terrain.settle   { tick=84212, material=7, x=1203, y=902 }
# each command applies bit-identically on every client — the carve math is deterministic (FPU + libm standardization)

4.4   The layered stack

The system, bottom (the deterministic sim) to top (the per-mode netcode adapter), with an always-on observability layer across everything. Each layer is independently verifiable. The pivoted ordering is right to left: foundation first (L0–L3), then transport (L4), then per-mode adapters (L5–L8).

L8
Per-mode netcode adapter
Lockstep (M7), prediction+reconciliation (M8), GGPO rollback (M9), or interest-managed snapshot (M10) — chosen per session. All sit on the same engine; the differences are in the input/state flow above the sim.
Gives: right-sized netcode per latency budget and player count.
L7
Prediction & reconciliation (online modes only)
The client runs its own actor forward from local input every frame, then rewinds and replays against each server snapshot. A mispredict corrects with smooth interpolation, not a snap. In lockstep mode this layer collapses to zero (every client is deterministic).
Gives: zero-feel-latency local control on top of a server-authoritative world.
L6
Entity replication (online modes only)
The server picks a budget-bounded, interest-managed set of moving objects each tick and ships their delta-encoded, quantized state; clients interpolate remote entities a fixed delay behind.
Gives: hundreds of actors and particles synced inside a bandwidth budget.
L5
Terrain channel
Destruction replicated as semantic commands on the reliable-ordered channel, applied deterministically by every recipient. Never pixels.
Gives: bounded terrain bandwidth and a world that stays identical everywhere.
L4
Transport & session
GameNetworkingSockets (Valve, BSD-3, MIT-equivalent for AGPL) behind a thin INetTransport adapter. Encryption (AES-GCM-256), NAT traversal (ICE), lanes (terrain commands / entity snapshots / input each on their own priority lane), IPv6, plus optional Steam Datagram Relay when launched via Steam.
Gives: a solved, maintained pipe with all the features the per-mode adapters need.
L3
Multi-threaded deterministic sim
The sim runs on every available CPU core via the ThreadMan pool, with a deterministic merge at the end of each update phase. The Factorio model: per-worker buffers, sort by MOID, apply in order. Built at M4.
Gives: bit-identical sim output across thread counts (the determinism contract MP needs); ~1.2× sim throughput measured (physics stays serial).
L2
FP-standardized physics core
Atom / AtomGroup / SceneMan penetration / SLTerrain carve / EraseSilhouette — the destruction-decision and atom-collision math kept in float and made cross-platform-identical via FPU + libm standardization (-ffp-contract=off + one bundled libm). The Q40.24 fixed-point approach was rejected — "really no benefit" given Lua-float determinism, and it taxes the hot physics path.
Gives: terrain physics bit-identical across same-arch platforms today (proven GREEN); cross-arch via libm standardization.
L1
Deterministic Lua & mod runtime
LuaJIT built with LUAJIT_SECURITY_STRID=0 (+PRNG=0) so stock pairs() iterates string-keyed tables deterministically, plus per-state seeded math.random and sim-tick os stubs. Engine-side, invisible to mod authors. No pairs() replacement (the sorted/det_pairs patch was dropped).
Gives: the ~53,000-line community Lua corpus becomes deterministic transparently; object-keyed sim tables key by UniqueID.
L0
Determinism foundation
Split sim/render RNG (+ the cosmetic render/audio/effect leaks routed off the sim stream), MOID-ordered sim iteration, wall-clock removed from sim paths, FP contract pinned, and the per-tick SimChecksum state hash (a small built-in integer hash) with per-subsystem breakdown.
Gives: deterministic single-machine baseline. The foundation under all layers above — built + cross-platform GREEN.
obs
Observability & replay — cross-cutting
Always on. Per-tick SimChecksum state hash, first-divergence report with per-subsystem hash breakdown, deterministic replay log, network simulator (latency / loss / jitter injection), the cccp-ctl test CLI + headless -determinism-check mode (the Stage-1 proof harness).
Gives: "is it still in sync?" is a CI gate, not a guess.

4.5   One lockstep tick (M7+)

How the deterministic core + lockstep adapter work together each frame — the counterpart to the old screen-streaming loop in §1.1:

All clients collect local input
Each client samples its player's Controller. No prediction; in lockstep mode every client is authoritative for its own actor.
All clients broadcast input + ack window
Each client sends its input to all others (peer-to-peer or via host). Inputs include the tick number they apply to. Sent redundantly on lane 2 (high priority, unreliable, redundant).
All clients wait for all inputs for tick N
Lockstep barrier: tick N cannot advance until every client's input for tick N has arrived. Bounded wait (~50ms typical LAN); on timeout, missing input is treated as "no buttons pressed."
All clients run one deterministic tick
Every client runs the same sim with the same inputs. Bit-identical output guaranteed by the deterministic core (L0–L3). Multi-threaded merge (L3) makes this fast.
All clients hash the island, gossip checksums
Per-tick SimChecksum state hash gossiped between clients. Any mismatch → immediate first-divergence report naming the tick and subsystem. The match is paused; resync workflow begins.

5  ·  The engine work

5.2   LuaJIT deterministic iteration (M2)

The single highest-leverage fix in the entire plan: make the ~53,000-line community Lua corpus deterministic engine-side, with no mod-author action — and, as shipped, with no patch to the vendored LuaJIT source.

  • As shipped: build LuaJIT with LUAJIT_SECURITY_STRID=0 (+PRNG=0) so stock pairs() iterates string-keyed tables in a deterministic order (LuaJIT keys string tables by string-id; STRID=0 makes those ids allocation-ordered instead of randomized). No pairs() replacement at all — the earlier "sort the keys" / det_pairs idea was dropped (it taxed every iteration and never fixed pointer-keyed tables). Object-keyed sim tables key by UniqueID.
  • math.random — CC already overrides it to route to a per-Lua-state C++ RandomGenerator; the foundation reseeds that generator from g_SimRNG at every activity start, so the sequence is reproducible per activity. LuaJIT's native PRNG is bypassed by CC's existing override — there is nothing to patch in lib_math.c.
  • os.time / os.clock replaced with sim-tick stubs (0 callsites in vanilla or the mod corpus today — foreclosure).
  • New lua_state SimChecksum subsystem hashes every Lua state's RNG into the per-tick trace.
  • 3-mod corpus regression: VoidWanderers, Mappack, BB+.

All engine-side: LUAJIT_SECURITY_STRID=0 in the LuaJIT build flags (PR 5); Source/Managers/LuaMan.cpp (math.random + os stubs, no LuaJIT source patch); Source/Entities/Activity.cpp (the per-activity reseed); Source/Network/SimChecksum.* (lua_state subsystem). Shipped as PR 5 (STRID=0) + PR 6 (Lua) in the foundation.

5.3   Cross-platform FP — FPU + libm standardization (Q40.24 fixed-point REJECTED)

This subsection describes an approach that is not in the shipped foundation. Q40.24 fixed-point was rejected per Causeless's review ("really no benefit" given that Lua float math determines cross-platform determinism regardless of how physics is handled). The chosen and proven path is FPU + libm standardization: keep the physics in float, standardize on one bundled libm, and compile with -ffp-contract=off + /fp:precise everywhere. Same-architecture cross-OS bit-identity is already verified GREEN on Windows + Linux + macOS; a later PR bundles libm to close the cross-arch / Rosetta gap. The Q40.24 code stays in modernization-effort only and is never reapplied. The detail below is retained as a record of the explored approach.

Explored-but-rejected: convert the destruction math to Q40.24 (int64_t) fixed-point.

  • New: Source/System/FixedPoint.h — a Q40.24 (24 fractional bits, int64_t storage) math library: operator overloads, a 128-bit multiply intermediate, Newton-Raphson sqrt, LUT sin/cos/atan2, and a parallel FixedVector. (Q24.8 / Q16.16 are 32-bit and overflow on squared impulse magnitudes — see M3_PLAN.md §3.2.)
  • Modified: Source/Managers/SceneMan.cpp — the penetration decision math in WillPenetrate/TryPenetrate/DislodgePixel (the squared-magnitude test, the retardation sqrt-divide, the spray vectors). The Bresenham stepping and the terrain bitmap writes are already integer — untouched.
  • Modified: Source/Entities/SLTerrain.cpp — carve / EraseSilhouette decision math.
  • Modified: Source/Entities/AtomGroup.cpp + Source/System/Atom.cpp — the collision-response arithmetic, converted in place (no refactor of the Travel control flow).
  • Per-subsystem checksum: terrain + the new carve_math bit-identical single-machine and Windows↔Linux x86.

Outside the determinism island regardless of FP approach:

  • Actor AI scoring (target priority, path costs) — non-deterministic float drift is acceptable here because outputs feed back through the deterministic Controller layer (the Controller-sync boundary, ADR-018).
  • Camera/rendering math — outside the island.
  • Audio mixing — outside the island.

Touch-points: Source/System/FixedPoint.h (new); Source/Managers/SceneMan.cpp:433-688; Source/Entities/SLTerrain.cpp; Source/Entities/AtomGroup.cpp.

5.4   Multi-threaded sim with deterministic merge (M4)

The Factorio model adapted to CC. Per-worker buffers, sort by MOID at merge, apply in order.

  • Make MovableMan::SyncedUpdate boundary airtight (currently opt-in via RequestSyncedUpdate(); M4 makes it mandatory for sim-state mutation).
  • Per-worker buffers in ThreadMan — threaded Lua/AI work writes to its own buffer, never to shared state directly.
  • Deterministic merge at end of update phase — sort all worker-output mutations by MOID, apply serially.
  • CI extension: same per-tick checksum at 1, 2, 4, 8, 16 thread counts. This is the acid test. Factorio's FFF-415 bug is what this gate catches.

Measured performance impact: ~1.2× sim throughput at 16 Lua states, plateauing near 1.2× by 8 states (M4ThreadStress, 40-actor scenario). The 4–8× figure earlier in this plan was a planning estimate; the measured gain is structural — physics (MovableMan::Travel()) runs serial, so only the AI/script phase parallelizes, and by Amdahl's law a partial parallelization caps the gain near 1.2–1.4×. M4's primary deliverable is not throughput but the deterministic threaded sim — bit-identical output across thread counts — which MP requires regardless.

Touch-points: Source/Managers/ThreadMan.cpp/.h; Source/Managers/MovableMan.cpp (SyncedUpdate); per-worker buffer API design.

5.5   Cross-platform float verification

As shipped: cross-platform bit-identity is verified directly — the native Windows + Linux + macOS builds run the determinism scenarios (the headless -determinism-check mode + cccp-ctl harness, PR 9) and produce identical per-tick checksums, with the --threads 1,2,4,8 matrix proving multi-core == single-core on each. That is the result that is GREEN today; it does not depend on a WASM reference.

  • CI matrix (PR 10, in progress): the 11-scenario sweep + thread matrix + cross-platform trace + TSan + perf baseline + positive control, so a leak/uninit/ordering regression can never pass silently again.
  • The integer-only SimChecksum hash is bit-identical cross-platform by construction, so the checksum itself is never a source of cross-platform mismatch.
  • Remaining cross-arch / Rosetta FP gap is closed by libm standardization (a later PR), not by a WASM oracle.

A WASM build (from the box2d-emscripten branch) as an additional reference target remains an optional future idea, but it is not the cross-platform mechanism and is not on the foundation's critical path.

5.6   Server spine + GNS transport (M6)

What the original ADR-015 M1 was — now ships after the deterministic foundation is in place. The headless server runs the deterministic sim with no window; GNS replaces RakNet.

6  ·  The mod surface

Cortex Command's ~53,000 lines of community Lua and twenty years of .rte mods are the fork's biggest asset. The pivot is good news for mod compatibility, not bad.

Mod hash sync — routine

Every client in a session must run an identical mod set, or the simulations describe different games. On connect, client and server exchange a content hash of the loaded module set; a mismatch is refused with a clear, specific message naming the offending module. Bounded engine work, built in M6.

Mod determinism — solved invisibly in the foundation

Building LuaJIT with LUAJIT_SECURITY_STRID=0 makes stock pairs() iterate string-keyed tables deterministically at the engine level; math.random() already routes through per-Lua-state seeded RNG. Every mod that uses pairs(), math.random(), etc. becomes deterministic with no mod-author action — existing code works, just deterministically. The remaining gap is real sim systems keyed by object pointers and iterated order-dependently (the automover node graph, BunkerBreach reinforcements) — fixed by keying on UniqueID (a later PR), not by any pairs() trick. Mods doing tostring(obj) / sparse-# / GC-timing in sim may need adjustment — a small minority.

The consequence for scope: the pivoted plan is better for mod compatibility than the original. The original plan was forgiving in M1–M4 (server-auth means mod non-determinism didn't matter) but tightened brutally at M5 (lockstep PvP would have needed every mod deterministic). The pivot front-loads the engine-side fix so every subsequent milestone has deterministic mods by default. Mod authors don't need to learn about a "deterministic mode" — the engine just is deterministic.

7.3   Mod-hash mismatch handling — the design

This is the most player-facing piece of the determinism contract. Per §6, every client must run a bit-identical mod-set to keep lockstep / rollback / replays bit-identical. The mod-hash handshake (built at M6) detects mismatch; this section covers how the UI handles mismatch — gets the player into the match instead of bouncing them.

Protocol. The server announces a canonical mod-set when the client begins handshake:

  • Per mod: (name, version, content file-hash, mod.io_id_or_null, manual_install_url_or_null)
  • Client compares against its own installed mods and produces five buckets:
    • MATCH — mod present, hash identical → ready
    • MISSING-AVAILABLE — required mod not installed, available on mod.io → auto-subscribe
    • WRONG-VERSION — installed but version differs, mod.io has canonical version → auto-update
    • MISSING-MANUAL — required mod not on mod.io → user installs manually with provided URL
    • CLIENT-EXTRA — mod installed but not in server's canonical set → offer to disable for this session

Auto-Sync flow: subscribe to MISSING-AVAILABLE mods via mod.io API → update WRONG-VERSION mods to the canonical version (mod.io version pinning) → disable CLIENT-EXTRA mods for this session (preferences saved so they re-enable for SP) → restart the game (mods load at startup; hot-load is not supported) → auto-rejoin server. Manual flow: show URL + instructions for MISSING-MANUAL cases; user closes game, installs manually, relaunches, retries connection.

Security model (load-bearing):

  • Auto-download only from mod.io. mod.io is a moderated channel with content review; servers announcing required mods can only point clients at mod.io IDs for auto-install — they cannot push arbitrary Lua to clients. This is a hard requirement — serving arbitrary mods from a server would be arbitrary-code-execution as a feature.
  • Hash verification on load. After install, the client re-hashes the files and confirms match to the canonical hash before joining. Catches tampering, transport corruption, and mid-flight mod-author updates.
  • Version pinning. The canonical mod-set pins specific versions, not "latest". A mod-author update between server-host's install and player's install does not break the hash; the player gets exactly the version the server has.
  • CLIENT-EXTRA cosmetic mods. Open question: do we let players keep "cosmetic-only" client-side mods active during MP (custom HUD, custom shader)? Conservative answer for the first MP ship: no — strict match, all extras disabled for session. Loosening this is a post-PvP-ship design problem (would need a verified "this mod only writes to g_RenderRNG" check that does not exist today).

Implementation surface: extends the existing Source/Network/ModioStorageService.cpp mod.io API integration with a hash-compare step, plus a new MultiplayerLobbyMenu screen built on the legacy Allegro GUIControlManager (§7.5). The mod-hash handshake protocol itself sits at M6; the resolution UI ships at the first MP user-visible milestone.

7.5   GUI toolkit decision — legacy now, modernize later

9  ·  Validation — proving sync without watching it

Netcode that is “tested by playing” is not tested. This plan is built so sync is proven by machine — which is why M0 built the measurement apparatus before any networking existed, and M1 extends that apparatus before any further determinism work touches the sim.

8.1   The per-tick checksum is the oracle

Every tick, SimChecksum computes a small built-in integer hash (FNV-1a / splitmix64, not crypto) of the determinism-island state with per-subsystem breakdown — integer-only so it is bit-identical cross-platform by construction. Any two runs (across runs, machines, threads, platforms) that diverge are caught instantly, and the subsystem breakdown isolates where.

checkpoint = {
  tick    = <sim frame>,
  hash    = <SimChecksum hash of the determinism-island state>,
  subsystems = {
    terrain   = <hash>,
    actors    = <hash, MOID-ordered>,
    particles = <hash, sim-relevant only>,
    sim_rng   = <state of g_SimRNG>,
    lua_rng   = <hash of per-state RNG seeds>,
    controller = <hash of input state>,
  }
}
# when two peers' checkpoints disagree, the harness emits:
divergence = {
  first_tick = 84213,
  peers      = { host: <hash A>, client_2: <hash B> },
  subsystem  = "terrain" | "actor:1843" | "rng" | ...,
  detail     = <diff of subsystem state>,
}

10  ·  What not to do

  • Don't ship pixels. Terrain crosses the wire as semantic commands, never bitmap deltas. Naive pixel replication is what the removed code did and what Teardown abandoned in 2021 — its bandwidth is unbounded.
  • Don't rebuild screen-streaming. Per-player server-side video is dominated by Steam Remote Play and Parsec, which already do it for free.
  • Don't trust the client. The server is authoritative for everything that matters in online modes. Client input is validated against the per-tick checksum. In lockstep mode every client is authoritative simultaneously — and they all agree because deterministic. The old code's habit of accepting client-sent state is the anti-pattern, not the model.
  • Don't skip M1. Determinism is the foundation under every netcode mode. Without M1's per-tick checksum + RNG split + iteration order, none of M2–M10 can be validated.
  • Don't patch LuaJIT in M1. That's M2. The agent picking up M1 stays in C++.
  • Don't add networking code before M6. M1–M5 are foundation. NetworkServer.cpp / NetworkClient.cpp stay untouched until M6.
  • Don't ship Steam Remote Play as a stopgap. User direction (2026-05): users can run Remote Play themselves; shipping it as engine support signals false progress.
  • Don't widen the determinism island faster than the checksum. Every system fenced into the island must be checksummed and CI-gated before the next one. An unverified island silently rots.
  • Don't put cosmetic systems in the island. Particles using g_RenderRNG, glows, audio, screen shake are Presentation — they may diverge freely. Forcing them deterministic is wasted work and needless risk.
  • Don't let one host carry an unbounded match in lockstep mode. In lockstep, every client carries the match (good!) — but the slowest client sets the tick rate. M4's multi-threaded sim is what keeps even older hardware on the bus.

11  ·  Why we pivoted — the reasoning

The original ADR-015 plan (state-replication co-op M1–M4, determinism retrofit M5, rollback PvP M6) was a reasonable engineering choice — it optimized for "ship co-op fast." This pivot trades that optimization for a different one: "ship the best possible multiplayer." The reasoning, in detail:

11.1   The Teardown recantation

The Voxagon blog post the wiki originally cited as architectural blueprint includes a passage that the original wiki reading missed: "For the longest time (and for good reasons), floating point operations were considered unsafe for deterministic purposes. That is still true to some extent, but the picture is more nuanced than that. I have since learned a lot about floating point determinism, and these days I know it is mostly safe if you know how to navigate around the pitfalls... Early on, I dismissed the idea of full determinism for the entire engine (a view I have since reevaluated), so it needed to be a hybrid approach." The blog ends: "It has been a useful learning experience, one to make me think deeply about simplified approaches to multiplayer implementations, which we're now trying out in the new engine."

The shipped Teardown hybrid was a compromise made under time pressure. The Teardown team is moving past it. cortex-modern was on track to implement yesterday's solution.

11.2   The corefall lock

The sibling project corefall, sharing this designer and a closely-related problem space, locked the per-mode netcode architecture as a P0 commitment on 2026-05-06 (DR-052). The corefall direction is built on the same evidence base cortex-modern has access to. The original cortex-modern plan was the only one of the two that deferred determinism.

11.3   The Factorio precedent

Factorio ships at ~500 kbit/s/client with thousands of entities under pure deterministic lockstep. The threading-determinism bug from FFF-415 shows the failure mode is known (CPU-count-dependent results) and the fix is published (force deterministic merge order). The techniques are tractable; CC's existing SyncedUpdate boundary is already half the work.

11.4   The performance ceiling

The original plan's state-replication architecture caps actor count at "what one host CPU can simulate." For a destructible-pixel-physics game where actor count is the headline feel, that cap is real and binding. The pivoted plan's lockstep mode uncaps it: every client runs the full sim in parallel, with M4's multi-threading adding a measured ~1.2× per-client. 4-player lockstep + ~1.2× threading ≈ ~5× raw sim throughput vs state-replication on a single threaded server — and it scales with player count, which a single server does not. That's the dimension the user explicitly asked to remove from the compromise list.

11.5   The cost (honest)

The pivot delays first MP user-visible ship by approximately 6 months. M0–M6 are now foundation work before any player can join another player. The risk concentration is up front: if M2's LuaJIT patch fails or M4's threading retrofit reveals deeper issues, the plan needs replanning. The original plan front-loaded value (co-op shipped at M4) and back-loaded risk (lockstep PvP at M6 carried all the determinism debt). The pivoted plan front-loads risk and back-loads value (LAN co-op SHIP at M7, online co-op at M8, PvP at M9).

The bet is that the foundation, once built, is permanent — and that "the best multiplayer CCCP can have" is worth 6 months of compounded compromises avoided.

11.6   The fallback

If any M1–M5 milestone reveals an unsolvable blocker, the fallback path exists: revert to the original ADR-015 plan from that point. M1 Block A (CI determinism scaffold) is value-positive regardless. M1 Blocks B-D are mechanical and have value in single-player stability. M1 Block F (CI gate) is value-positive regardless. Even partial M1 work is not wasted — it tightens up the existing sim. The pivot is reversible.

11.7   The architecture not chosen — AI Controller-sync

A different architecture surfaced in upstream-dev review (2026-05) as a path that would have sidestepped most of the determinism plumbing: keep AI fundamentally non-deterministic, but design the MP layer so AI never touches synced game state. Each player owns a subset of AI agents, runs that subset's AI locally, and only the resulting Controller outputs sync across the network — the sim then needs to respond deterministically to Controllers, a strictly weaker requirement than full determinism. This is a real alternative considered after M1–M4 had shipped, and worth recording.

Bandwidth surprise — lockstep is cheaper on the wire, not more expensive. The intuition that "AI on every client wastes resources" is true for CPU and false for network. In lockstep, AI's output never traverses the wire because every client computes the same output from the same inputs; only player inputs flow (~16 bytes/tick/player, so a 4-player session sits around 30 kbit/s plus periodic checksums — the Factorio reference). In Controller-sync, every AI-driven actor's Controller must be broadcast per tick from its owner; a 4-player session with 200 actors at 60Hz approaches ~3 Mbit/s/client — linear in actor count, vs. lockstep which is flat. On typical home internet (5–20 Mbit/s upload), Controller-sync caps the playable roster size; lockstep does not. The CPU/bandwidth tradeoff is real but it goes the opposite direction of intuition.

Why we did not pick it. Controller-sync fits server-auth co-op (M8) and public hosting (M10) naturally, but it cannot support the other two committed modes: LAN lockstep (M7) requires every client to compute the same sim end-to-end, and Controller-sync clients each compute partial state; GGPO rollback PvP (M9) re-simulates past frames during rollback, and non-deterministic AI re-simulated produces different outcomes → cascading desync. Determinism is non-negotiable for both. Secondary advantages also fall out of the determinism path and would require extra work in Controller-sync: deterministic replays from inputs alone, anti-cheat via per-tick SimChecksum hashes, reproducible procgen, zero AI input lag, and a clean authority story for neutral / wild / dropped-player units. ADR-016 committed to all four modes (M7–M10) because each serves a real player need the others cannot.

The cost we accept. Code inside the sim island must follow determinism rules — no wall-clock reads (use g_TimerMan.GetSimUpdateCount()), no environment-seeded RNG (use g_SimRNG), no ML inference in the inner loop (non-deterministic across hardware by default). For CC specifically these constraints are mild — current AI is hand-written Lua with no ML, sim already uses tick counts, and mod-side RNG already routes through per-Lua-state seeded math.random post-M2. Cosmetic effects (audio, particles via g_RenderRNG, post-process, UI animations) carry no constraint — the wall is around the sim island only.

The two paths are not mutually exclusive going forward. If we ever drop M7 + M9 from scope, Controller-sync becomes the simpler architecture (the pivot stays reversible per §11.6). And ML AI or other non-deterministic techniques can be layered on top of our deterministic foundation by running them server-side and broadcasting deterministic Controllers into the sim — that is Controller-sync applied to one subsystem only, on a base that supports the full mode matrix.

11.8   The Controller-sync rejection was wrong — flipping per upstream-lead 2026-05-25 review

Recorded as ADR-018. The architectural commitment in §11.7 (lockstep + GGPO requires full sim determinism, therefore reject Controller-sync) was incorrect on the "Controller-sync cannot support lockstep or rollback" claim. Causeless's 2026-05-25 Discord clarification reframes Controller-sync in a way that makes it the right architecture after all.

What Causeless clarified (verbatim). "The reasoning behind the Controller-sync idea is more for allowing expensive operations (like pathfinding requests) to be async. Async operations are pretty much fundamentally opposed to determinism — but if we add a boundary between the calculation and the simulator-y execution, then we have something deterministic. In theory those operations should be deterministic, as physics is run single-threaded — AI isn't deterministic, but the plan there was that AI should never touch game state. If we wanted that, the solution would likely be to have the AI have its own Lua states, separate from the deterministic ones."

The reframing. Controller-sync does not mean "sync arbitrary per-actor state instead of inputs." It means: the deterministic boundary is the Controller wire, not the entire AI pipeline. Each machine runs its own AI (with async pathfinding, in its own non-deterministic AI Lua state pool) for actors it owns. The AI produces Controllers. Controllers are the only thing that crosses the network. The sim downstream of Controllers is deterministic via M4A's Path E enforcement — same code, same Controllers, same sim outputs across machines.

Why this supports lockstep AND rollback (§11.7 was wrong on this). Lockstep just means "every machine advances tick N only when it has all players' Controllers for tick N." Whether those Controllers come from "inputs" or "AI on owner's machine" doesn't matter to lockstep mechanics. Rollback means "snapshot sim; replay with received Controllers when prediction was wrong." Same: Controllers are the input to sim regardless of source; rollback re-execution uses received Controllers + deterministic sim downstream. The original §11.7 rejection conflated "Controller-sync" with "sync arbitrary state" — that was the wrong mental model.

What changes in the plan. See ADR-018 for the formal record:

  • M4A pathfinder serial-epilogue is never reapplied to revamp trunks. Causeless's clarification: pathfinder is expected to be async per-machine; the Controller boundary handles cross-machine sync. The serial-epilogue was solving a problem Controller-sync makes moot.
  • M4A Race A architectural fix is never reapplied. Same reason.
  • M7 lockstep co-op syncs Controllers, not full sim state. Compact + deterministic.
  • M8 online rollback co-op implements separate AI Lua states (Causeless's stated design intent realized): AI in non-deterministic AI pool per machine; sim in deterministic shared pool. Block E of M8.
  • M9 PvP rollback reuses M8's rollback machinery on the Controller-sync boundary.

Bandwidth re-analysis. The §11.7 bandwidth table compared "lockstep inputs only ~30 kbit/s" vs "Controller-sync ~3 Mbit/s at 200 actors". That analysis assumed Controller-sync meant broadcasting every actor's full state per tick. In the corrected architecture, Controller-sync broadcasts only Controllers (compact per-tick player intent state, ~50 bytes/Controller), and only for player-owned actors (AI-driven actors don't have synced Controllers — each machine generates them locally for their own actors). Bandwidth is closer to lockstep's ~30 kbit/s/player than to the 3 Mbit/s the original analysis showed. The bandwidth concern that drove the §11.7 rejection doesn't survive the corrected model.

What CPU cost remains. Each machine runs full sim plus AI for its own actors. CPU scales with full sim (not "owned roster only" as §11.7 incorrectly suggested for Controller-sync). This matches the lockstep CPU profile — both architectures have every machine running the full sim. The difference is: lockstep requires deterministic AI for all actors (cross-machine identical); Controller-sync allows non-deterministic AI per machine because cross-machine sync is at the Controller boundary downstream of AI.

This is the upstream-mergeable architecture. Causeless's stated upstream design intent is exactly Controller-sync + separate AI Lua states. What M7–M9 ships under this architecture is upstream-mergeable in principle — that's the architectural credibility we get from the flip.
