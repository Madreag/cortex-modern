Networking

Multiplayer

Cortex Command's networked multiplayer was removed in January 2025. This page is the honest, full-spectrum analysis of bringing it back — every option from "ships tomorrow" to "rebuild the engine" — built from a read of the actual code, the removal history, Corefall's netcode design, and the wider netcode landscape.

Status — under active investigation; nothing is being deleted

The networking code (~5,900 lines) is retained as the reference implementation. The Tier-1 cleanup task that proposed deleting it is on hold until a multiplayer direction is chosen. ADR-011 (which had accepted the removal) is superseded by ADR-013, which reopens the question.

What Cortex Command had

Networking was retrofitted onto the 2001-era Crush2D engine and shipped only with the 2019 open-source release — the commercial game never had public networked play. The model was server-authoritative screen-streaming, confirmed from the source:

  • The server runs the entire simulation. It renders a separate per-player 8-bit frame, compresses it into rectangular "boxes" (LZ4 / LZ4-HC, with delta compression), and streams it. Clients are thin display terminals — they send only input (controller, mouse) and never simulate anything.
  • Cost: 6–10 Mbit/s per client and roughly 0.75 of a CPU core per client, on top of the simulation itself. Frames streamed at 30 fps. Hard 4-player cap.
  • Transport was RakNet (reliable UDP + NAT punch-through). RakNet was abandoned by its owner (Oculus/Facebook) around 2014 and is unmaintained.

It worked on a LAN and was playable, but it was bandwidth-brutal, latency-poor, single-threaded-bottlenecked, and never tested on Linux. Upstream removed it (commit 91fe85dd8, PR #179, "RIP Multiplayer 2019-2025 / Don't miss it, write something working instead").

Why it will not just switch back on

The removal did not delete the four networking files — it commented them out of the Meson build. But it also stripped ~700–1,000 lines of integration hooks out of FrameMan, UInputMan, PostProcessMan, SceneMan and ActivityMan. Un-commenting the build lines produces an immediate compile failure — the APIs the network code calls no longer exist.

Worse, the model itself is now obsolete: screen-streaming needs a per-player 8-bit rendered frame, and FrameMan has since migrated to SDL3 / 32-bit / OpenGL — that 8bpp render path is gone. The old code is a useful reference, not a revivable artifact. Reviving the old model verbatim is weeks of work just to compile, and far more to make playable on the modern renderer.

The core constraint — why this is genuinely hard

Cortex Command's simulation is single-threaded, non-deterministic (floating-point, per-pixel atom physics, unordered particle iteration), and CPU-saturating even in single-player. No networking cleverness removes that. It rules out the cheap, elegant models — deterministic lockstep and rollback both require a bit-identical simulation, which CC's engine is the opposite of. Every realistic option is therefore either a streaming model (host does everything) or a state-replication model (server is authoritative, clients predict) — not lockstep.

The options — four tiers, honest cost

TIER 0   Stream it with Steam Remote Play / Parsec

Not netcode at all — the host runs the game and streams video+input to guests, the same idea as CC's old multiplayer but using Valve's or Parsec's mature H.264/HEVC codec and relay network instead of a homegrown 30 fps LZ4 stream. Steam Remote Play Together needs one Steamworks API call to opt in; Parsec needs zero code and players already use it. Up to ~3–4 guests, host bears all load, latency-sensitive — but it is strictly better than what CC shipped, and it works today.

Effort: trivial (one API call) · Risk: none · The honest near-term answer.

TIER 1   Modernize the screen-streaming model

Rebuild CC's own streaming multiplayer properly: restore the stripped hooks, swap dead RakNet for SLikeNet (a maintained RakNet fork, near drop-in) or Valve GameNetworkingSockets (free Steam relay, solves NAT), replace the homegrown frame compression with real video encoding (libavcodec / H.264), and add a per-player render pass to the modern SDL3 renderer. Result: usable internet friends-play. Still thin clients, still host-CPU-bound, still ~4 players — the model's ceilings remain.

Effort: medium (~1–3 months) · Risk: medium · Largely superseded by Tier 2 — an interim, not a destination.

TIER 2   A real state-replication architecture — the Teardown model

The genuinely good outcome. A server-authoritative design: the server runs the sim; clients send input, run client-side prediction for their own actor, and reconcile. The key trick — proven by Teardown for voxel destruction — is to replicate terrain destruction as deterministic commands ("carve radius R at (x,y)"), not pixel bitmaps, which means only CC's terrain-modification math must be made deterministic (fixed-point), not the whole physics engine. Entities (actors, projectiles, debris) sync via a prioritized snapshot stream. Transport: GameNetworkingSockets or ENet. This is how Terraria, Starbound and LieroX work; it does not need a determinism rewrite, and it pairs naturally with a co-op campaign.

Effort: high (~6–18 months, the flagship-scale build) · Risk: high but bounded — the recommended real target.

TIER 3   Deterministic lockstep / rollback — rebuild the engine

The "perfect" netcode (tiny bandwidth, every client simulates from inputs) demands a bit-identical, deterministic simulation: physics rewritten in fixed-point, every RNG seeded and ordered, deterministic container iteration, fast state save/restore. This is exactly what Corefall gets for free by being built deterministic-first — and Corefall's own specs cite CC's MovableMan.cpp and Atom.cpp by name as the anti-patterns. Retrofitting it onto CC is a multi-year, near-total engine rewrite. Noita — a near-identical per-pixel engine — ruled multiplayer out for exactly this reason.

Effort: years / effectively a new engine · Risk: extreme · Not recommended — this is Corefall's domain.

What the comparable games teach

Noita — the cautionary twin. Same per-pixel non-deterministic engine; its developers ruled out multiplayer entirely. Worms, Factorio — deterministic lockstep, beautiful and cheap, but designed in from day one; not retrofittable. Terraria, Starbound, LieroX — the realistic 2D-sandbox answer: an authoritative host, entity snapshots, terrain sent as patches. Teardown — the blueprint: it networked full voxel destruction by making only the destruction math deterministic (fixed-point) and leaving everything else to server-authoritative eventual consistency. Corefall — shows the determinism-first ceiling: QUIC transport, server-authoritative online co-op, GGPO-style rollback PvP, MMO shards — all of it downstream of a determinism foundation CC does not have and cannot cheaply acquire.

Recommendation

Ship Tier 0 now. Wire up Steam Remote Play Together — one API call — so players have working co-op immediately, and label it honestly as game-streaming, not netcode. This alone beats what CC had.

Make Tier 2 the real multiplayer project. Server-authoritative state replication on the Teardown model is the genuinely good, genuinely achievable outcome — and it does not require the engine rewrite that lockstep would. It is flagship-scale (6–18 months) and it should be sequenced with the Campaign: a co-op campaign is the real prize, and the campaign work also pays down the AI and mission systems multiplayer will lean on. Tier 1 is an optional interim if networked play is wanted sooner; skip it if Tier 2 can be committed to directly.

Do not attempt Tier 3. A determinism rewrite is a multi-year new engine — it is what Corefall already is. Reference it; don't reproduce it.

Keep the old code. The ~5,900 lines stay as the reference for Tier 1/2. RakNet can be dropped whenever Tier 1/2 picks its replacement transport; until then it is harmless dead weight, not a deletion emergency. The standing decision is ADR-013.
