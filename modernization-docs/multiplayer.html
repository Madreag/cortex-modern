Networking

Multiplayer

Cortex Command's networked multiplayer was removed in January 2025. This page is the committed plan to bring it back, in full: how the old netcode worked from a direct read of the source; why it cannot simply be switched back on; the architecture being built in its place; the C++ engine work in detail; what it means for existing mods; the milestones from here to a shippable co-op game and on to competitive PvP; and how every step is validated automatically. It is written to be built from — an engineer or an AI coding agent should be able to read this page and start.

The headline

Networked play was one of Cortex Command's most-wanted features and one of its worst-executed: the 2019 open-source release shipped a server-side screen-streaming model so bandwidth-brutal and laggy that upstream deleted it in January 2025 — the changelog reads “the existing multiplayer implementation was terrible and broken.” Players still improvise around the gap with Steam Remote Play, Radmin VPN and raw IP entry. ADR-013 reopened the question; the investigation is complete; the decision is made.

cortex-modern will rebuild multiplayer as server-authoritative state replication — the model Teardown shipped in March 2026 for a harder destructible-physics game — staged so working co-op ships early and a determinism island grows under it toward competitive PvP. This is a committed flagship, recorded as ADR-015, and it is sequenced to ride the AI overhaul's engine work (ADR-014).

1  ·  How Cortex Command's multiplayer worked

Before rebuilding it, see it clearly. Everything below is from a direct read of the networking source still in the tree: Source/Managers/NetworkServer.cpp/.h, NetworkClient.cpp/.h, Source/System/NetworkMessages.h, the commented-out Source/Activities/Multiplayer*.cpp, and the vendored external/sources/RakNet. The shape that emerges explains both why it was removed and why the replacement is a rebuild, not a revival.

1.1   The model — server-side screen-streaming

Networking was retrofitted onto the 2001-era engine and shipped only with the 2019 open-source release. It was not netcode in the modern sense — it was remote rendering. The server ran the entire simulation and, for each connected client, rendered that client's viewport into a private 8-bit framebuffer, compressed it, and streamed the picture. Clients were thin display terminals. The per-frame server loop:

Server RunGameLoop → one fixed sim tick
The server runs the whole simulation — MovableMan::Update, terrain, every actor and particle — once, for everyone. There is one authoritative sim.
Server NetworkServer::m_BackBuffer8[player]
For each client, the server renders that player's screen into a private 8-bit BITMAP — a full per-player render pass on top of the simulation.
Server LZ4 compress → boxes / lines
The frame is diffed against the previous one (m_UseDeltaCompression), split into rectangular boxes sized under the ~1500-byte MTU, LZ4-compressed, and optionally interlaced to halve bandwidth at the cost of visible degradation.
Server BackgroundSendThreadFunction → RakNet
A dedicated std::thread per client ships ID_SRV_FRAME_* packets over RakNet, with NAT punch-through. Terrain edits go separately as ID_SRV_TERRAIN.
Client NetworkClient → decompress → blit
The client decompresses the boxes and blits them straight to its screen. It simulates nothing. It is a video player.
Client MsgInput → ID_CLT_INPUT
The client sends back only input — mouse position, buttons, the packed InputElementState bitfield. Nothing else ever leaves the client.

The cost was what you would expect of streaming a video feed per player: 6–10 Mbit/s and roughly 0.75 of a CPU core per client, on top of the simulation, at a 30 fps encode rate, with a hard c_MaxClients cap. Even the terrain half was the worst possible design — MsgTerrainChange ships a rectangle of raw bitmap bytes (X, Y, W, H plus a compressed pixel blob), not the meaning of the edit. It worked on a LAN; it was miserable over the internet.

1.2   Why it will not just switch back on

Upstream's removal (commit 91fe85dd8, PR #179, “RIP Multiplayer 2019-2025”) did not delete the networking files — but reviving them is not an option, for three independent reasons:

What the removal didWhy a revival is blocked
MultiplayerGame.cpp and MultiplayerServerLobby.cpp are commented out of Source/Activities/meson.build.The activity layer no longer compiles or links. Un-commenting it is the smallest of the problems.
~700–1,000 lines of integration hooks were stripped from FrameMan, UInputMan, PostProcessMan, SceneMan and ActivityMan.The APIs NetworkServer / NetworkClient call no longer exist — un-commenting the build produces an immediate compile failure.
The renderer moved to SDL3 / 32-bit / OpenGL.Screen-streaming needs a per-player 8-bit rendered frame. That render path is gone. The model itself is obsolete.

The old code is a useful reference — the protocol shape, the message-ID set, the connection and NAT handling, the list of integration points — not a revivable artifact. Its terrain handling is a worked example of what not to do (§9). RakNet itself is abandonware (last release 2014) and is retired with it.

2  ·  The core problem — determinism

There are only two ways to keep two machines showing the same game. You can ship the state — every object's position, every frame — which costs bandwidth and needs an authority to arbitrate. Or you can ship the inputs and have every machine recompute the state, which is nearly free on the wire but demands that every machine computes bit-identically. That property is determinism, and it is the hinge the whole plan turns on.

Cortex Command is non-deterministic — in six ways
  1. Floating-point math that differs across CPU, compiler and optimization level (fused multiply-add, x87 80-bit intermediates, fast-math reordering).
  2. Unordered iteration — MovableMan walks its actors, items and particles in registry order, not a stable, content-defined order.
  3. RNG ordering — CC does have a single global generator (g_RandomGenerator in RTETools.h, seeded once at boot by SeedRNG()), but it is seeded from the environment and consumed by threaded code in no fixed order.
  4. Wall-clock influence in places that should be tick-driven.
  5. ~53,000 lines of community Lua, whose pairs() table iteration has no defined order in the Lua 5.1 / LuaJIT dialect.
  6. A multithreaded Lua / AI / MOID-drawing path on the ThreadMan pools — thread scheduling is nondeterministic by default.

None of this was ever a bug. Single-player never cared. It only becomes a problem the moment a second machine has to agree.

The key idea — the determinism island

You do not need the whole simulation deterministic. You need a determinism island: a bounded, explicitly-fenced part of the tick that is bit-identical and checksummed every tick, so any divergence is caught the instant it happens. Everything outside the island — rendering, audio, cosmetic particles — may differ freely from machine to machine.

The island can be small (just terrain edits — this is what Teardown shipped) or total (the whole gameplay tick — this is what Factorio runs on). Its size is the master dial of this whole plan. State replication needs only a small island; lockstep PvP needs a total one — and the plan is built to grow the island from one to the other (§7). State replication and lockstep are not rival architectures; they are the same architecture at two island sizes.

3  ·  The approach

The investigation under ADR-013 scored the full option space against one question: what actually works for a 2D game with per-pixel destructible terrain, thousands of fast particles, a non-deterministic simulation, and a twenty-year mod ecosystem. Seven approaches, scored:

3.1   The option space

WASM determinism harness●●●●●Adopted as an enabler. Running the sim in WebAssembly gives cross-platform bit-identical floating point for free. Pulled in at M5 to grow the island.

Naive state / bitmap replication●●●●●Rejected. Shipping terrain pixels and every object's state every frame. This is what the removed code did; Teardown tried it in 2021 and it “choked the connection.”

3.2   The decision — settled

Server-authoritative state replication, staged. One machine owns the simulation — a player's host, or a headless cortex-server. Clients send input, locally predict their own actor for responsiveness, and reconcile against the server's authoritative snapshots. Other actors and debris arrive as a prioritized, interest-managed snapshot stream. The crucial move: terrain destruction is never sent as pixels — each edit is a semantic command (“carve radius R at x,y”) on a reliable channel, and only that one subsystem is made deterministic. This is Terraria's authority model with Teardown's terrain trick.

It is staged because that is free: state replication and lockstep share most of one architecture, so shipping co-op first (M1–M4) wastes nothing — the same server, transport, terrain commands, prediction and reconciliation are exactly what PvP rollback (M6) is later built on. Co-op ships years before PvP and de-risks it. The determinism island simply grows (M5) in between.

3.3   What the comparable games prove

Teardown — the blueprint

A fully-destructible voxel physics game — a harder problem than CC — that shipped multiplayer in March 2026. Its 2021 naive attempt (sync voxel data) “choked the connection.” The shipped model: destruction replicated as a deterministic command stream on a reliable channel, everything else state-synced unreliable with eventual consistency, host-is-server, 12 players, 20 Hz, client-side prediction. That is exactly this plan.

Terraria — the authority model

Authoritative server, clients are clients, the world is server-owned and synced. It “seems simple” because Terraria's simulation is simple — a tile grid that changes rarely. CC's terrain changes every frame from every bullet and settling particle, so CC cannot send tiles; it must send commands. Same architecture, harder content — hence the determinism work.

Noita — the cautionary twin

The same per-pixel non-deterministic engine; the studio never shipped multiplayer. The community's true-co-op mod is openly buggy; the popular one sidesteps world sync entirely (separate worlds, shared items). Per-pixel world replication is unsolved by brute force — replicate commands, not pixels.

Factorio — the lockstep ceiling

Deterministic lockstep, ships only inputs, a desync forces a full resync. It works because it was built deterministic — and it is still hard (a threading-determinism bug hid in the code for years). It is proof the M6 ceiling is real and reachable, and proof that threading is where determinism bites.

Corefall — the determinism-first sibling, and what this plan borrows

The sister project Corefall is what this looks like when the engine is built for it from line one: a Rust engine with one authoritative server binary, per-mode netcode (lockstep for LAN, prediction + snapshot interpolation for online co-op, rollback for PvP), all on a CI-enforced determinism-island contract. cortex-modern cannot be deterministic-first — but it can adopt the contract: f32-or-fixed-point sim math, ordered iteration, one seeded RNG, no wall-clock, a per-tick checksum, a deterministic threaded merge. Corefall's value here is not code — it is a proven specification of what “deterministic” means, ready to apply. The strategic question of whether deep PvP/MMO play is cortex-modern's job or Corefall's is settled by ADR-015 in favour of building it here, co-op first.

4  ·  The target architecture

This is the system being built. It is one authoritative simulation, three classes of data with three different authority rules, and a layered stack from the wire up to the player's hands.

4.1   The authority model

Every piece of game state falls into one of three classes. The rule is constant: the server owns truth; the client owns feel; nothing else may diverge that matters.

ClassExamplesRule
TruthTerrain, actor health and inventory, projectile hits, gold, the activity / mission state, AI decisions, the save.The authoritative server computes it. Clients display it and may not contradict it.
PredictionThe local player's own actor — movement, jetpack, the held weapon, its own just-fired projectiles.The client predicts it immediately for responsiveness, then reconciles to the server snapshot — correcting smoothly on a mispredict.
PresentationCosmetic particles, glows, screen shake, audio, gib debris past its gameplay impact, interpolation smoothing.The client does it freely. Machine-to-machine divergence here is harmless and expected — it is outside the determinism island.

4.2   What crosses the wire

Three channels, deliberately different — the single most important design fact on this page:

ChannelDeliveryCarries
Semantic commands (server→client)Reliable, orderedTerrain edits, object spawns/deletes, scene changes — the things that change the structure of the world. Small, count-independent, must arrive and apply in order. Applied bit-identically because the math is deterministic.
Entity snapshots (server→client)Unreliable, eventual-consistencyActor / projectile / debris transforms, velocities, hp — the things that move. Prioritized, interest-managed per client, delta-encoded, quantized, inside a bandwidth budget. A lost packet is corrected by the next snapshot.
Input (client→server)Unreliable, redundantThe player's Controller state. Tiny. Sent redundantly so a lost packet never stalls the server.

Terrain is the exception that defines the design. CC churns terrain every frame; sending pixels is unbounded (§1, §9). Sending the command — “carve radius R at x,y” — is a fixed handful of bytes regardless of blast size, and it lands inside the determinism island so every machine carves identically.

# terrain edits cross the wire as commands, never pixels — reliable, ordered
terrain.carve    { tick=84210, x=1204, y=880, radius=14, tool="HeavyDigger" }
terrain.dislodge { tick=84210, box=[1190,866, 1218,894] }
terrain.settle   { tick=84212, material=7, x=1203, y=902 }
# each command applies bit-identically on every client — the carve math is deterministic

4.3   The layered stack

The system, bottom (the wire) to top (the player's hands), with an always-on observability layer across everything. Each layer is a separate, independently-verifiable piece — which is what makes the milestone plan in §7 possible.

L6
Prediction & reconciliation
The client runs its own actor forward from local input every frame, then rewinds and replays against each server snapshot. A mispredict corrects with smooth interpolation, not a snap.
Gives: zero-feel-latency local control on top of a server-authoritative world.
L5
Entity replication
The server picks a budget-bounded, interest-managed set of moving objects each tick and ships their delta-encoded, quantized state; clients interpolate remote entities a fixed delay behind.
Gives: hundreds of actors and particles synced inside a bandwidth budget.
L4
Terrain channel
Destruction replicated as semantic commands on the reliable-ordered channel, applied deterministically. Never pixels.
Gives: bounded terrain bandwidth and a world that stays identical everywhere.
L3
The determinism island
A fenced, checksummed region of the tick that is bit-identical across machines. Seeded at the terrain-edit math (M2); grown toward the whole tick (M5).
Gives: the foundation — small island = co-op, total island = PvP.
L2
Authority & session
The authoritative simulation (peer-host or headless cortex-server); connection, lobby, the mandatory mod-hash handshake, anti-cheat input validation.
Gives: one source of truth, and one place to validate every client input.
L1
Transport
Reliable + unreliable channels, encryption, fragmentation, NAT traversal — GameNetworkingSockets or ENet behind a thin adapter, replacing abandoned RakNet.
Gives: a solved, maintained pipe — one swappable seam.
L0
Observability & replay — cross-cutting
Always on. A per-tick checksum of the determinism island, a first-divergence report, a deterministic replay log, and the network simulator that injects latency, loss and jitter.
Gives: the proof — “is it still in sync?” is a CI gate, not a guess (§8).

4.4   One networked tick

How the layers work together each frame — the counterpart to the old model's loop in §1.1:

Client read input → predict → render
The client samples the player's Controller, runs its own actor forward locally (L6), and renders immediately. No waiting on the network for local feel.
Client send input
Input is sent to the server, redundantly, on the unreliable channel.
Server collect input → one authoritative tick
The server gathers every client's input in a fixed order and runs one authoritative simulation tick — including all enemy AI (server-side per ADR-014).
Server emit commands + snapshots
Terrain and structural edits go out as semantic commands (reliable, L4); a prioritized, interest-managed entity snapshot goes out per client (unreliable, L5).
Client apply commands → interpolate → reconcile
The client applies terrain commands deterministically (identical result), interpolates remote entities from snapshots, and reconciles its predicted actor against the server's truth.
Server checksum the island → divergence report
Server and clients hash the determinism-island state every tick. A mismatch raises a first-divergence report naming the tick and subsystem (L0). In co-op this catches bugs; in M6 PvP it is the anti-cheat and the rollback trigger.

5  ·  The engine work

This is the C++ side, in enough detail to build from. It is substantial — but most of it is bounded and mechanical, and the one genuinely risky part (determinism) is fenced and measurable.

5.1   The server spine

An authoritative server must run the simulation with no window. The good news, from a direct read of Source/Main.cpp: the loop is already structured for this. RunGameLoop() runs a fixed-timestep accumulator — while (g_TimerMan.TimeForSimUpdate()) { … sim … } — and only then calls g_FrameMan.Draw(). The sim/draw split exists. What is coupled is the manager initialisation (WindowMan, GLResourceMan, FrameMan are constructed unconditionally) and a few render calls reached from inside the sim block.

  • Headless mode. Add a -server argument to HandleMainArgs() (which already parses -editor, -module) and a headless variant of RunGameLoop() that runs the sim block and skips FrameMan::Draw / WindowMan / post-processing.
  • Sever the render dependency. Make InitializeManagers() construct a server subset, and stub or guard the in-sim render calls (g_FrameMan.Update(), g_MovableMan.CompleteQueuedMOIDDrawings()) under headless.
  • One binary. A player hosting is the server running in-process beside their client; cortex-server is the same code with the client half switched off. Host-from-menu and dedicated server are one codebase.
  • Transport. Retire RakNet. Integrate GameNetworkingSockets (Valve — free relay, solves NAT) or ENet behind a thin INetTransport adapter, so the choice stays a single swappable seam.
  • Session. Connection, lobby, and the mandatory mod-hash handshake (§6).

Touch-points: Source/Main.cpp (RunGameLoop, HandleMainArgs, InitializeManagers); Source/Managers/WindowMan, FrameMan, GLResourceMan (headless guards); Source/Managers/NetworkServer.* / NetworkClient.* (rebuilt); Source/System/NetworkMessages.h (new protocol); external/sources/RakNet (removed).

5.2   Terrain replication & the terrain determinism island

The old MsgTerrainChange ships bitmap bytes. The replacement ships semantic commands, and the terrain-edit math is made deterministic (fixed-point) so each command applies identically on every machine. This is the seed of the determinism island.

  • Replace the bitmap-delta message with a command set — carve, dislodge, settle, scene-change — on the reliable-ordered channel.
  • Make the terrain-edit path deterministic: SceneMan::WillPenetrate (≈ line 433), TryPenetrate (≈ 544), DislodgePixel (≈ 688), and SLTerrain's carve / EraseSilhouette path — fixed-point arithmetic, no float drift.
  • Hash the terrain grid every tick (Source/System/Hash.h already provides a hashing utility) and feed it the per-tick checksum.

Touch-points: Source/Managers/SceneMan.cpp (penetration / dislodge / terrain registration); Source/Entities/SLTerrain.cpp (the FG/BG terrain bitmaps, carve, erase); Source/System/NetworkMessages.h; Source/System/Hash.h.

5.3   Entity replication & client prediction

Actors, projectiles and debris sync as state, not commands — because there are too many and they move every frame. For co-op this needs no entity-sim determinism: the state is replicated, not recomputed. (That is why co-op needs only the small terrain island; M6 PvP is what needs the rest.)

  • Snapshot stream. Each tick the server selects a bandwidth-budgeted, interest-managed (per-client camera) set of movable objects and emits their state — position, velocity, aim, hp — delta-encoded against the last acknowledged snapshot and quantized.
  • Interpolation. Clients render remote entities a fixed delay behind “now”, interpolating between snapshots, so packet loss and jitter never show as teleporting.
  • Prediction & reconciliation. The client predicts its own actor from local input each frame; when a server snapshot arrives it rewinds to the acknowledged tick and replays local input forward, correcting smoothly under a threshold and snapping over it.
  • Server-side AI. Enemy and squad AI run only on the authoritative server — the AI overhaul is already designed server-authoritative-friendly.

Touch-points: Source/Managers/MovableMan.* (the MO registry, iteration order, Update); Source/Entities/MovableObject.* and subclasses (MOSRotating, MOPixel, Actor, AHuman, ACrab, ACraft) — a snapshot serialise/apply surface; Source/System/Controller.h (input into the prediction loop).

5.4   The determinism retrofit

Growing the island (M2 seeds it, M5 completes it) means making the simulation bit-identical, source by source. Each row is marked mechanical (well-specified, checksum-verifiable, cheap for an AI coding agent) or risky (irreducible uncertainty — the real cost).

The AI overhaul is cortex-modern's first committed build, and it adds a row of new C++ simulation systems — an incremental pathfinder, influence maps, a per-actor blackboard, a perception API, an adaptive scheduler, utility and behaviour-tree kernels, persistent orders that serialise into .ccsave. Every one is new simulation state a networked build must sync. Those systems should be built to the determinism-island contract now — ordered containers, single-precision, one seeded RNG, no wall-clock, a deterministic threaded merge. Built clean they cost nothing; retrofitted later they are pure determinism debt. And the AI overhaul's M0 apparatus — the decision-event channel, replay capture, the headless scenario runner, CI — is most of the multiplayer sync harness already (M0 here): build the observability and per-tick-checksum harness once, and both flagships share it.

6  ·  The mod surface

Cortex Command's ~53,000 lines of community Lua and twenty years of .rte mods are the fork's biggest asset. Multiplayer touches them in two ways — one routine, one the genuine hard part.

Mod hash sync — routine

Every client in a session must run an identical mod set, or the simulations describe different games. On connect, client and server exchange a content hash of the loaded module set (the engine already hashes bitmaps — BitmapHash in NetworkMessages.h — and ships Source/System/Hash.h); a mismatch is refused with a clear, specific message naming the offending module. Bounded engine work, built in M1.

Mod determinism — the hard part

State-replication co-op (M1–M4) is forgiving: the server is authoritative, so a mod that is internally non-deterministic still works — the server's result is the only one that counts. Lockstep PvP (M6) is not. It needs every machine, running every mod, to compute identically — and pairs() over a Lua table has no defined order. The fix (a deterministic table iteration, M5) is engine-side and covers the whole corpus at once, but it is the plan's named risk.

The consequence for scope: co-op asks almost nothing of mods — hash sync and nothing more. That is a large part of why co-op is M1–M4 and PvP is M6: the milestone that ships first is the one that barely touches the mod ecosystem. The compatibility apparatus the AI overhaul builds — a CI mod corpus, Void Wanderers included — is reused here to prove, every build, that the mod set still loads and runs across the network.

7  ·  The plan — milestones to completion

How this plan is scoped

Sequenced by dependency and gated by validation, not by calendar time. The build is executed by AI coding agents, for which the cost of a task is not its human-hours; the meaningful units are what must exist first and how we know it is done. Every milestone states what it depends on and the exact, machine-checkable condition that closes it. An agent picking up this build starts at M0. Each milestone is a complete, shippable improvement: M0–M4 deliver working co-op; M5–M6 extend it to competitive PvP. The build always contains a working, better state than the milestone before.

8  ·  Validation — proving sync without watching it

Netcode that is “tested by playing” is not tested. This plan is built so sync is proven by machine — which is why M0 builds the measurement apparatus before any networking exists. A networked simulation has one enormous advantage as a test target: determinism makes correctness a checksum.

8.1   The per-tick checksum is the oracle

Every tick, the server and every client hash their determinism-island state. If two hashes differ, the simulations have diverged — and a per-subsystem hash breakdown isolates where. “Is it still in sync?” stops being a judgement call and becomes a CI gate.

checkpoint = {
  tick    = <sim frame>,
  island  = "terrain" | "whole-tick",     # the island has grown by M5
  hash    = <BLAKE3 of the determinism-island state>,
}
# when two peers' checkpoints disagree, the harness emits:
divergence = {
  first_tick = 84213,
  peers      = { host: <hash A>, client_2: <hash B> },
  subsystem  = "terrain" | "actor:1843" | "rng" | ...,   # per-subsystem hash breakdown
}

8.2   The test regime

Every test runs headless against the M0 network simulator, in CI, on every change:

sync-drift    --clients 4  --scenario breach   --duration 60s   # assert per-tick checksums match; report first-divergence tick
latency       --add 200ms  --loss 5% --jitter 50ms              # assert the match completes with no permanent divergence
packet-loss   --loss 0..25%                                     # find the resilience boundary
soak          --clients 4  --duration 1h                        # bandwidth + stability over a long run
interest      --clients 8                                       # assert off-screen entities are absent from the snapshot stream
replay-verify --bundle run.mpr --runs 100                       # assert all 100 replays reproduce the same final checksum
prediction    --duration 60s                                    # assert the mispredict-correction rate stays below the UX threshold

8.3   What the harness measures

MetricWhat it catches
First-divergence tickWhether, and exactly where, two simulations stopped agreeing.
Bandwidth per clientWhether terrain stayed commands-not-pixels and interest management is working.
Mispredict-correction rateWhether client prediction feels smooth or rubber-bands.
Terrain-checksum match rateWhether the determinism island holds under sustained destruction.
Replay reproduction rateWhether the sim is genuinely deterministic (M5) — 100/100 or it is not done.
Soak stabilityEmergent failures — slow desync, leaks, drift — that a 60-second test misses.

8.4   Where the human stays

The machine proves sync; it cannot prove fun. The irreducible human roles are three: authoring the test scenarios and setting the thresholds; spot-checking the saved replay of any divergence the agent could not resolve; and the final feel judgement — does co-op play well, not just stay in sync. The machine checks against the bar; the human sets the bar.

9  ·  What not to do

  • Don't ship pixels. Terrain crosses the wire as semantic commands, never bitmap deltas. Naive pixel replication is what the removed code did and what Teardown abandoned in 2021 — its bandwidth is unbounded.
  • Don't rebuild screen-streaming. Per-player server-side video is dominated by Steam Remote Play, which already does it for free. The stopgap is Remote Play; the build is state replication.
  • Don't trust the client. The server is authoritative for everything that matters. Client input is validated against the per-tick checksum — the old code's habit of accepting client-sent state is the anti-pattern, not the model.
  • Don't start with lockstep. Lockstep / rollback needs a total determinism island. It is M6, reached by growing the island — not a cold start. Co-op via state replication needs only the small terrain island and ships first.
  • Don't skip the harness. M0 comes first, always. Netcode you cannot checksum cannot be built to a finish line — and it is the same harness the AI overhaul already builds.
  • Don't widen the determinism island faster than the checksum. Every system fenced into the island must be checksummed and CI-gated before the next one — an unverified island silently rots.
  • Don't put cosmetic systems in the island. Particles, glows, audio and screen shake are Presentation — they may diverge freely. Forcing them deterministic is wasted work and needless risk.
  • Don't let one host carry an unbounded match. The host runs the whole sim; past a handful of players that is the wall. Player-count scale is gated on roadmap T3-01, not on wishful thinking.
Definition of done

Multiplayer is delivered in two proven stages. Co-op is done — and shippable — when:

  • Two or more players complete a co-op campaign mission across the internet, through NAT, with no manual networking setup, at 50–200 ms latency.
  • The terrain determinism island holds — the terrain checksum matches tick-for-tick — through sustained destruction, under injected latency, loss and jitter.
  • Bandwidth per client stays within budget under peak load; a one-hour soak run shows no permanent divergence; the mod corpus loads and stays in sync.

The full plan is done when, additionally:

  • The whole-tick determinism island reproduces bit-identically across Windows / Linux / macOS, and a recorded match replays to the same final checksum 100 times out of 100.
  • A PvP arena match runs at the player-count target with sub-perceptual input latency, rollback recovering cleanly from injected delay and loss, and the anti-cheat rejecting impossible inputs.
  • Every shipped match is explainable and re-playable: a divergence names its tick and subsystem; a replay reproduces the match.

It is specific, it is measured by machine, and it does not move.
