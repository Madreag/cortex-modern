ADR-001 Fork strategy — cortex-modern + modernization-effort Accepted

2026-05-16

Context

We need an independent working repository to modernize the engine without disrupting upstream, and a clear, named starting point.

Decision

Fork cortex-command-community/Cortex-Command-Community-Project to Madreag/cortex-modern. The official repo is tracked as the upstream git remote; our fork is origin. All initial work happens on branch modernization-effort, cut from development @ 41e6b7010.

Consequences

We can pull upstream changes via git fetch upstream and still open PRs back upstream later. The working branch is modernization-effort.

ADR-002 Keep LuaJIT 2.1 — do not migrate to Luau or Lua 5.4 Accepted

2026-05-16

Context

The engine is on LuaJIT 2.1 (Lua 5.1.4 dialect, frozen language). Luau (typed Lua) and Lua 5.4 are tempting modern targets.

Decision

Stay on LuaJIT 2.1. Bump it to the current rolling release for the CVE-2024-25176 fix, but keep the runtime.

Consequences

We retain JIT + FFI performance and do not fracture the existing mod ecosystem — ~53K LOC of community Lua is all 5.1-dialect. The real scripting liability is luabind, not LuaJIT (see ADR-003).

ADR-003 Replace luabind 0.7.1 with sol2/sol3 Proposed

2026-05-16

Context

luabind 0.7.1 is abandoned, Boost-dependent, blocks toolchain upgrades, and forces build hacks (no PCH, re-enabling C++17-removed features).

Decision (proposed — pending an effort spike)

Migrate the Lua binding layer to sol2/sol3. Use the stalled upstream sol3 branch as a reference for the shape of the work, not as a merge base.

Consequences

Removes the worst dependency and the Boost requirement. ~5,100 LOC of bindings + the execution core. Main risk is binding-semantics / ownership parity. Tracked as T2-02.

ADR-004 Modernization is incremental and mod-compatible by default Accepted

2026-05-16

Context

Upstream is a very small team with documented mod-compatibility paralysis; large breaking PRs sit for years and rot. We must not reproduce that failure mode.

Decision

Every change ships as a small, independently-mergeable unit. Any change to the mod-facing INI/Lua surface that breaks existing mods requires its own ADR and a migration path. [ARCH] items are sliced into shippable increments before work starts.

Consequences

Slower headline progress, but work actually lands and stays mergeable. This is the governing principle for the whole Roadmap.

ADR-005 Do not duplicate upstream's active branches Accepted

2026-05-16

Context

box2d-emscripten, gpu-renderer, emscripten-port and interpolated-render-redux are active upstream branches (commits Feb–Apr 2026).

Decision

Do not start competing implementations of Box2D physics, the next-gen renderer, or the web port. For physics multithreading (T3-01), prefer aligning with or contributing to the Box2D effort. We may revive stalled, un-owned branches (sol3, hot-reloading).

Consequences

Avoids wasted effort and merge conflicts. Focuses our work on genuinely un-owned gaps.

ADR-006 Render interpolation is the first flagship engine change Proposed

2026-05-16

Context

We need an early, user-visible, low-controversy win to validate the contribution workflow before tackling anything heavier.

Decision (proposed)

After Tier 1, T2-01 (render interpolation) is the first non-trivial engine change. It is visible (smoother motion), self-contained, and mod-compatible.

Consequences

Establishes the contribution pattern (small branch → PR). Risk: an interpolation alpha must be threaded through every Draw path; teleports and scene-wrap need special handling.

ADR-007 corefall cross-pollination — note now, act later Proposed

2026-05-16

Context

Madreag/corefall is a parallel game project in early development. The two efforts share concerns — 2D physics, rendering, a modding/data pipeline — and may benefit from two-way idea and tech transfer.

Decision (proposed)

Do not couple the two projects technically right now. Revisit once corefall has a defined engine and architecture. Until then, simply keep shared concerns in mind when making structural decisions here.

Consequences

No action now. A future ADR will decide on any concrete sharing (a shared library, lifted patterns, or nothing). This entry exists so the relationship is not forgotten.

ADR-008 Fork-first development — upstreaming is opportunistic, never a gate Accepted

2026-05-16

Context

Upstream (CCCP) merges PRs very slowly — some sit open for years. Gating our progress on upstream review would stall the effort indefinitely.

Decision

cortex-modern is the primary product. All work happens continuously on the modernization-effort integration branch (features via short feature/* branches, merged in at our own review bar). development is kept as a clean mirror of upstream/development and is never committed to directly. Upstreaming is optional and downstream: to offer a feature we cut a pr/* branch from upstream/development, cherry-pick that feature's commits, and open a small self-contained PR — only when we choose to. We never block ongoing work waiting on upstream, and we sync upstream/development into the integration branch regularly to avoid drift.

Consequences

We are never blocked on the maintainers; upstream merges become a bonus, not a dependency. The cost is our own review discipline and periodic upstream syncs. This resolves the former "Upstreaming" open question.
