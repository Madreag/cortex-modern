Foundation · Modernization · Side Tracks

Engine Modernization

The engine work that underpins all three flagships (AI, Multiplayer, Campaign) plus the parallel side tracks that multiply the ceiling on what those flagships can do. This page is the master plan for how MP main-spine work (M1–M10) interweaves with rendering, threading, physics, Lua, and build/platform modernization — including how we harvest from the upstream branches (interpolated-render-redux, gpu-renderer, box2d-emscripten) at full speed without coordination. Written so an engineer or AI coding agent reading this can pick up any milestone or side track and start.

Status — 2026-05-18

MP M0 (observability harness) shipped. All five engine subsystems and five side tracks are now planned in this document. Active plan timeline on index.html; multiplayer.html is the MP main-spine plan; D:\Projects\M1_PLAN.md is the ultra-detailed M1 execution plan ready for an AI coding agent.

The master plan in one paragraph

Five engine subsystems need modernization for the no-compromise multiplayer architecture to land: rendering, threading, physics, Lua, and build/platform. The MP main spine (M0–M10 in multiplayer.html) handles the determinism-critical subset directly — the Lua patch (M2), fixed-point atom physics (M3), deterministic threaded sim (M4), WASM cross-platform anchor (M5), GNS transport (M6). Everything outside the determinism island — render interpolation, GPU cosmetic offload, the Camera/RenderBatch abstraction — runs as parallel side tracks (T-RENDER-INTERP, T-RENDER-GPU, T-WASM-BUILD, T-COSMETIC, T-VALIDATION) that coordinate with the active upstream branches without blocking MP. The result: online co-op (M7) ships on a deterministic core with multi-threaded sim and render interpolation — the best possible architecture — and the side tracks deliver single-player wins (~1.2× sim throughput at M4 measured, WASM web build at M5, smooth high-refresh rendering when T-RENDER-INTERP lands).

The headline

cortex-modern is not building MP in a vacuum — we're building it on top of the engine modernization work the community has already partially done. The 2019–2026 upstream branch list contains five branches with real engine value: interpolated-render-redux (Causeless's active retry of render decoupling), gpu-renderer (HeliumAnt's 60-70%-done renderer rewrite, dormant since 2026-03-28), box2d-emscripten (a substantially-working WebAssembly port, dormant since 2026-04-02), sol3 (a reference for the future luabind→sol2 migration), and the original interpolated-render (abandoned 2024 but useful for lerp primitives). None of these are mergeable as-is. The pattern: coordinate where the author is active (Causeless), harvest selectively where dormant (HeliumAnt, box2d-emscripten), avoid wholesale merge of any of them.

1  ·  The five subsystems being modernized

Each subsystem has a current state, a modernization target, and an answer to the question "is this in the MP main spine, or a side track?" The split is determined by one question: does this affect the determinism island? If yes, main spine. If no, side track.

RENDER
Rendering pipeline
Current stateSDL3 + OpenGL + 8-bit palette context still entrenched. FrameMan writes to a software 8bpp BITMAP, then GPU-blits via shader. raylib still in tree.
Determinism?OUT of island (cosmetic). Uses g_RenderRNG per M1 Block B.
MP-critical?No — render perf multiplies actor ceiling but doesn't gate correctness.
Where it landsSide tracks T-RENDER-INTERP + T-RENDER-GPU + T-COSMETIC.
Modernization target: render-frame-rate decoupled from sim tick rate (interpolation at 144Hz over 60Hz sim), Camera/RenderBatch abstraction from gpu-renderer harvested selectively, GPU compute for cosmetic systems (particles, screen flashes). 8-bit palette decoupling is a separate Tier-3 issue and not on the MP critical path.
THREAD
Threading model
Current stateThreadMan pool exists; SyncedUpdate boundary in MovableMan is designed-in but opt-in. MovableMan::Travel() runs serial. // TODO: Fix HitMOs issue!! in source.
Determinism?IN island. Threading without determinism = Causeless's lost branch (glitchy, killed determinism).
MP-critical?YES — threading is the actor-count multiplier. Without it, the lockstep ceiling collapses.
Where it landsMain spine M4.
Modernization target: per-worker buffers, deterministic merge by MOID at end of update phase (the Factorio model + Causeless's "buffered Lua callback" idea). ~1.2× sim throughput on modern CPUs (measured) — physics stays serial, so only the AI/script phase parallelizes. The real value is the deterministic threaded sim, required for MP.
PHYSICS
Atom physics core
Current stateFloat math throughout Atom, AtomGroup, SceneMan penetration. AtomGroup::Travel commented "trainwreck"/"dumpsterfire" in source. Per-pixel Bresenham collision.
Determinism?IN island — the core of the destructible terrain that defines CC's identity.
MP-critical?YES — terrain replication as semantic commands depends on the math being bit-identical across machines.
Where it landsMain spine M3.
Modernization target: Q24.8 fixed-point math for the destruction path. Bit-identical by construction across all platforms. Per ADR-005, the upstream lead explicitly rejected switching to Box2D — CC's atom physics is identity, not a swappable engine. Fixed-point keeps the design while making it deterministic.
LUA
Lua runtime
Current stateLuaJIT 2.1 vendored at external/sources/LuaJIT-2.1/. pairs() iterates in hash order (non-deterministic). math.random per state but seeded inconsistently.
Determinism?IN island — ~53K LOC of community Lua iterates tables and rolls RNG every tick.
MP-critical?YES — without deterministic Lua, the mod corpus diverges across clients.
Where it landsMain spine M2.
Modernization target: patch LuaJIT pairs() to iterate sorted-by-key, seed math.random per-state from g_SimRNG. Engine-side patch, invisible to mod authors. Per ADR-002 we keep LuaJIT (do not migrate to Luau/Lua 5.4) — the binding layer (ADR-003) is a separate concern (luabind→sol3, Tier-3, post-MP).
BUILD
Build & platform
Current stateMSBuild (Windows, primary), Meson (Linux/macOS, secondary). No WASM target shipped (upstream box2d-emscripten proves it's possible). CI on Windows MSBuild only.
Determinism?PARTIAL — compile flags affect FP determinism (M1 Block E). WASM is the cross-platform anchor (M5).
MP-critical?YES — cross-platform MP requires verified-identical builds.
Where it landsMain spine M1 Block E + M5; harvest from box2d-emscripten WASM half.
Modernization target: pinned FP flags (M1), Linux + macOS + WASM CI matrix (M5), WASM build of CC as a web target (independent value — CC playable in browser). The Box2D physics half of that branch is rejected (see ADR-005); we want the WASM half only.

3  ·  The side tracks

Side tracks are engine modernization work that runs in parallel with the MP main spine. They don't gate MP shipping, but they land independent value and multiply the ceiling on what MP can do once it ships. Each side track has explicit dependencies, an effort estimate, and a clear "when do we pair this with MP?" answer.

4  ·  Interweaving with the MP main spine

The MP main spine has 10 milestones (M0–M10). The side tracks above have 5 entries (T-XXX). The interweaving is structured so:

  • Each side track lands during the right MP window (not before its deps, not after its consumers).
  • No side track gates an MP milestone — if T-XXX slips, MP continues. The exception is T-WASM-BUILD which is fused into M5 (it's not really a side track).
  • Side tracks deliver value independent of MP — even if MP shipping pauses, single-player benefits ship at each side-track close.
  • The user (or AI coding agent) can pick up any track at its appropriate window — no track requires a context-load of every other track first.

5  ·  Branch harvest strategy — no waiting, no coordination

cortex-modern is an AGPL fork per ADR-001 and ADR-008: fork-first, upstreaming opportunistic. We have full legal and architectural authorization to harvest any code from CCCP upstream or any community branch under AGPL. We do not wait for upstream authors. We do not coordinate. We ship. Authors who want our work back can cherry-pick from our fork; that's how the fork-and-merge model is supposed to work.

This means: an active branch by Causeless is treated identically to a dormant branch by HeliumAnt is treated identically to an abandoned branch by someone who hasn't logged in for 2 years. The branch is the artifact. Whether the author is active is irrelevant to our pace.

5.1   The harvest decision flow

For each upstream branch with potential relevance to our work:

  1. Study it — read the diff (git diff origin/development...upstream/<branch-name> -- <paths>), the commit messages, the rationale.
  2. Decide:
    • Harvest — if the commits solve our problem, cherry-pick them onto our milestone branch. Credit the original author in commit body. Adapt to our determinism CI gate.
    • Reference — if the design ideas are useful but the implementation isn't, take the design + write fresh code. Document the inspiration source in the PR body.
    • Skip — if neither helps, move on. Write fresh.
  3. Ship — cortex-modern's cadence is ours. No external dependency.

The decision is the agent's. If a branch looks promising during a quick audit, harvest. If it looks like a maze of incomplete prototypes, skip. No discussion with the original author is required at any point.

5.2   Attribution discipline

When harvesting a commit from an upstream branch, the commit body should read:

Block C: stable MOID-ordered iteration in MovableMan

Adapted from upstream/interpolated-render-redux commit 7a2350b80 by Causeless
(2026-05-17, "Ensure MOIDs are always up-to-date"), adapted for the
determinism CI gate added in Block A.

[the rest of the commit message]

This honors AGPL's attribution requirement and the spirit of the fork-first model. No Co-Authored-By: trailers (per CLAUDE.md — all cortex-modern artifacts are solely attributed to the user). The harvested-from line in the commit body is sufficient AGPL attribution.

5.4   The mod community — one-way disclosure, no coordination

The M2 LuaJIT pairs() patch is engine-side and invisible to mod authors. Most mods get deterministic behavior transparently. Three groups of mods do care:

  • Procgen-heavy mods (VoidWanderers): hash-order randomness may have been a feature. After M2, procgen with the same seed produces the same world every time. Good for MP, surprises solo players.
  • Mods using FFI: bypass the Lua API. Rare but exist. May not benefit from the M2 patch.
  • Mods relying on real-time collision response: M4 shifts Lua collision callbacks from "during collision" to "end of tick." Mod behavior changes deterministically — mostly imperceptibly, but documented.

Disclosure plan: after M2 closes and after M4 closes, draft a forum/Discord post explaining what changed and why. One-way disclosure, not negotiation — the engine work has shipped on our fork already by then; mod authors who care can adapt. We do not seek pre-approval; we communicate post-fact and accept regression reports.

5.5   If an upstream author returns mid-stream

Scenario: we harvest from HeliumAnt's gpu-renderer, ship T-RENDER-GPU, and three weeks later HeliumAnt returns to GitHub and starts committing to gpu-renderer again. What happens?

  • Our work is shipped — on cortex-modern, on modernization-effort, in production. It's not going back.
  • If HeliumAnt's new commits are good — we can harvest those into a follow-up milestone, just like the original harvest.
  • If HeliumAnt's direction diverges from ours — we stay on our path. cortex-modern is its own product.
  • If HeliumAnt opens a PR to upstream that conflicts with our fork — we can choose to adopt or stay independent. ADR-008 makes this a fork-side decision, not an upstream-side blocker.

Same applies to Causeless and any other contributor. Their re-emergence does not gate us.

7.1   The value-shipping insight

Look at the "Single-player benefit" column. Each foundation milestone (M1-M5) delivers real single-player value, not "we made invisible foundation work, please trust us." A community member who downloads cortex-modern after M4 closes gets a ~1.2× sim throughput bump (measured) plus a deterministic threaded sim with headroom for more actors. After M5, they get CC in their browser. Even if MP work paused for some reason between M5 and M6, the engine improvements alone justify the work.

This is the architectural answer to "what if we get stuck?" Each milestone has independent value, so being stuck at any milestone still means the codebase is better than before.

8  ·  Risks & fallback paths

"Don't get stuck" was the user-explicit constraint. Each foundation milestone has a fallback path so MP work can proceed even if the milestone's optimal solution proves infeasible. Only M1 has no fallback — if we can't measure determinism, we can't build on it. Everything after M1 is degradable.

8.1   The critical-path argument

Even with all the fallback paths in place, the online co-op MVP at M7 only strictly requires M1 to succeed at its optimal path. Everything else (M2-M6) has a degradable fallback. So if you read this and worry "what if we get stuck," the answer is: complete M1, then choose your battles. Online co-op via M7 can ship even if M2-M6 all hit fallbacks — just with reduced feature completeness.

The optimal path delivers the best possible MP. Each fallback reduces the ceiling but never breaks the bottom: online co-op working perfectly.

8.2   The side-track risk profile

Side tracks have a separate risk profile because they don't gate MP. Failure modes:

  • T-RENDER-INTERP doesn't land: render stays at sim tick rate (60Hz). High-refresh monitors don't see smooth motion. Acceptable.
  • T-RENDER-GPU doesn't land: raylib immediate-mode draw stays in place. Render perf is what it is today. Acceptable.
  • T-WASM-BUILD fails (=M5 fallback): see M5 fallback above.
  • T-COSMETIC doesn't land: particle/post-process stay on CPU. Actor ceiling lower than ideal but still better than today after M4. Acceptable.
  • T-VALIDATION doesn't grow: CI tests stay minimal. Each MP milestone has its own validation regardless. Acceptable.
Engine modernization — definition of done

Engine modernization is delivered in three proven stages.

Foundation done (M1–M5) when:

  • Determinism CI gate is blocking on every PR.
  • Five-platform (Win/Lin/Mac x86/Mac ARM/WASM) checksum verification produces identical results.
  • Multi-threaded sim is bit-identical across thread counts (the determinism gate); throughput measures ~1.2× single-threaded.
  • LuaJIT pairs() patched and the top-20 mod corpus passes regression.
  • WASM build of CC loads and plays a campaign mission in a browser.

Side tracks delivered when:

  • T-RENDER-INTERP: 144Hz monitors show smooth motion (likely lands via Causeless's upstream branch).
  • T-RENDER-GPU: Camera + RenderBatch abstraction in place, sprite draws batched.
  • T-COSMETIC: cosmetic systems CPU usage down 30%+ in stress scenarios.
  • T-VALIDATION: every MP milestone has a cccp-ctl test command verifying it.

MP done when:

  • Online co-op (M7): friends in different cities complete a mission through NAT at 50-200ms RTT.
  • LAN lockstep (M8): 4 LAN clients run bit-identical sim for the entire match at ~500 kbit/s/client.
  • PvP rollback (M9): 4-player arena at sub-50ms input latency with GGPO rollback.
  • (Stretch) Public hosting (M10): 16+ player community-hosted match for 1 hour without divergence.
