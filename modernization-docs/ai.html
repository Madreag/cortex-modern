Foundations

The AI Overhaul

Cortex Command's AI is the game's most-cited weakness — and the one the upstream lead has openly called garbage. This page is the committed plan to replace it, in full: how the AI works today from a direct read of the source; what is broken and why; the architecture being built; the C++ engine work in detail; what it means for existing mods; the milestones from here to completion; and how the result is validated automatically. It is written to be built from — an engineer or an AI coding agent should be able to read this page and start. The target is not a patched-up AI. It is a new one: smart enough to run every unit on the field by default, and genuinely worth playing with and against.

The headline

AI quality is the #1 complaint across Steam reviews, the forums and mod.io, and it has been for twenty years — old reviews still bite (GameSpy: "terrible AI"; NoobFeed: "units will get stuck or mess up or even die due to a flaw in the AI"). The live upstream tracker carries it now: #208 squad logic, #121 post-rework sentries that twitch and aim randomly, #100 squads that can't fire gatling guns. And the project lead, Causeless, said it himself in the dev Discord (2025-08-09): "the AI is such garbage. it's very frustrating. I want to just fucking delete all the path following code."

cortex-modern will not patch around this. It will build the whole architecture — engine and Lua — to a finish line a test suite decides. This is the flagship, recorded as ADR-014.

1  ·  How the AI works today

Before replacing it, see it clearly. Everything below is from a direct read of the AI source on our branch: ~5,830 lines of Lua under Data/Base.rte/AI/, plus the C++ pathfinder, the controller abstraction and the invocation harness. The shape that emerges explains both why the AI is so moddable and why it is so hard to make good.

1.1   The execution pipeline

Every AI actor is ticked through the same seven-step path each sim frame:

C++ Controller::ShouldUpdateAIThisFrame()
Throttle. An actor's AI only runs every AIUpdateInterval sim frames, and actors are spread across frames by ID so the cost is even. There is no emergency interrupt — a falling actor waits its turn like everyone else.
C++ MovableMan::UpdateControllers()
Dispatch. Runs ThreadedUpdateAI across the thread pool — one worker thread per Lua state — then a serial UpdateAI pass. Most AI runs multithreaded.
LUA HumanAI.lua → NativeHumanAI:Update()
A ~10-line entry script hands off to the real controller object. (Crabs, turrets, dropships and rockets each have their own equivalent.)
LUA behaviour coroutines
The dispatcher watches the actor's AIMode and runs up to two behaviour coroutines, drawing on the HumanBehaviors / SharedBehaviors libraries.
LUA Controller:SetState(...)
The behaviour's only output: it sets the actor's Controller — the same buttons and analog sticks a human holds.
C++ Actor locomotion / physics update
The engine reads that Controller and moves the actor — exactly as if a gamepad had sent the input.
C++ PathFinder (background thread pool)
In parallel, path requests the Lua AI raised resolve on a background pool and the result is handed back for the next tick.

1.2   The C++ / Lua split

The single most important fact about CC's AI: the AI never moves an actor. It does exactly one thing each frame — set the actor's Controller, the same buttons and sticks a human holds. The engine then reads that Controller. The AI literally plays the game through the gamepad. That is why it is so moddable, and why so much of it is Lua:

The engine (C++) ownsThe Lua scripts own
The threaded per-frame invocation harness; the Controller input abstraction; the AIMode enum and waypoint storage. Every tactical decision. Which behaviour to run, and when to switch.
Sensing primitives — CastMORay, CastStrengthRay, LookForMOs — and the alarm-event list. Target acquisition, threat scoring, the "have I lost my target?" logic.
Pathfinding: the MicroPather A*, the node grid, the async request API. Path-following, locomotion, the jetpack-jump predictor, stuck handling, digging decisions.
Terrain-change tracking that feeds the pathfinder. All combat — aiming, target leading, fire / hold-fire, reloading, throwing, weapon choice.
The actor's own physics, locomotion gaits and damage model. Squad behaviour, alarm processing, tool / medikit use, gold-digging, brain-hunting.

The implication. The expensive, low-level parts — pathfinding, sensing, threading — are already in C++. The brain — all judgement — is Lua. But the AI is only as good as the senses and tools the engine hands it, and today those are thin. A genuinely good AI needs work on both sides of this line — which is the whole shape of the plan in §5 and §7.

1.3   AI modes — the entire order vocabulary

The C++ AIMode enum (Actor.h) is the AI's whole vocabulary. A player's pie-menu order, an activity's spawn script — all any of them can say to an actor is one of these:

PATROLactorsWalk back and forth between obstacle-bounded extents.
GOTOactorsMove to a waypoint, then revert to SENTRY on arrival.
BRAINHUNTactorsSeek and destroy the nearest enemy brain.
GOLDDIGhumansScan for gold and dig toward it.

Plus two sentinels (NONE, COUNT). Six modes apply to fighting actors. That is the entire set of intentions a player or designer can express — there is no "hold this line", "breach here", "retreat", "rescue him", "mine that vein". Widening this vocabulary is itself a significant part of the overhaul (§5.3).

1.4   The behaviour engine — coroutine soup

Within a mode, behaviour is run by Lua coroutines — not a behaviour tree, not a formal state machine. NativeHumanAI runs two coroutines at once: a main Behavior slot (combat, sentry, gold-dig) and a GoToBehavior slot (movement), so an actor can walk toward a target and shoot at the same time. A behaviour does one frame of work, calls coroutine.yield(), and after every yield checks an abort flag. When the AI wants to drop a behaviour it resumes it once more with that flag set — a cooperative protocol that exists, the source says repeatedly, "to avoid memory leaks".

ShootTargetHumanBehaviorsThe main ranged-combat behaviour — aim, lead, fire decisions, weapon juggling.
SentryHumanBehaviorsGuard: face the likely approach, sweep aim, periodically sharp-aim, return to post.
AttackTarget / ThrowTargetHumanBehaviorsMelee / digger attack; grenade throwing with a ballistic solver.

1.5   Perception — two sets of eyes

CC's AI has two completely separate spotters, and which one an actor gets is decided once, at spawn:

  • LookForTargets — the default. Casts one ray, in a random direction, per AI tick. An enemy can stand in the open and not be seen for many frames in a row. This is not a bug — it is the design for ordinary actors.
  • CheckEnemyLOS — the good one. Enumerates every enemy in a screen-sized box and checks line-of-sight to one each frame, so it reliably sees anything on screen. Only brains, snipers, bosses and high-skill (Nuts difficulty) actors are given it.

So AI competence is bimodal: most enemies you fight are running the random-ray spotter. Hearing is separate — weapons fire and explosions push AlarmEvents that ProcessAlarmEvent range-checks and occludes against terrain. When more than one target is in view, CalculateThreatLevel scores them by distance, whether they are armed, and damage taken.

1.6   Locomotion & path-following

All ground movement runs through GoToWpt. It reads the engine-built path (MovePath), walks toward the next point, and pops points as it arrives. For jetpack actors it runs a genuine trajectory predictor: it estimates thrust, simulates four candidate jump arcs plus a "do nothing and fall" arc, casts obstacle rays along each, and jumps only if a jump beats falling by a margin. If the actor carries a digger and terrain blocks the path, it sweeps the digger across the obstacle.

Its weak point is stuck recovery. A StuckTimer notices the actor has stopped moving — and the "recovery" is to flail: random lateral-direction swaps, a random chance per tick to drop prone, a random chance to refuel. There is no diagnosis, no re-path, no "step back and try another way".

1.7   Pathfinding — the deepest tech debt

Pathfinding is A* over a uniform grid of PathNodes, via the third-party MicroPather library. Edge cost is the strongest material between two nodes; terrain too hard for the actor to dig is multiplied by 1000 — effectively a wall. The pather is "jump-aware" … in theory. In practice:

  • Jump height is faked. Actor::EstimateJumpHeight() returns FLT_MAX — the comment calls it a "Sentinel value that is explicitly checked for within pathfinder code". The pather therefore assumes every actor can jump infinitely high and plans routes the actor's real locomotion then cannot follow.
  • It is not incremental. MicroPather has no incremental update — any terrain change forces a fresh A*. Scene::UpdatePathFinding reconciles changed terrain every 100 ms, capped at 100 nodes per call, and the code itself warns this "can indefinitely block updates if pathing requests are made every frame".
  • It is rebuilt constantly. A pather is created per worker thread and reset on essentially every request. The source carries the TODOs "… (or write our own pather)!" and "… we create a new pather for every thread!".

In a game whose entire identity is terrain that changes every second, a pathfinder that cannot cheaply react to terrain changing is the root cause of more visible failures than any other single thing. It gets its own section: §5.1.

1.8   Squad AI — there isn't any

There is exactly one squad mechanic, and it is not coordination. A squadmate standing near its leader literally copies the leader's controller states — move, jump, prone — and fires when the leader fires. That is the whole of it. No roles. No formation. No spreading out. No deciding who shoots whom. No shared knowledge of the battlefield. "Squad" means "stand near the leader and press the same buttons." When the leader dies, squadmates fall back to a cached waypoint or just stop. This is why squads clump, friendly-fire, and stall on each other — and it is upstream issue #208.

The code's own confession

The clearest evidence the AI needs an overhaul is in the source comments. Verbatim, from our branch:

  • // Sentinel value that is explicitly checked for within pathfinder code. return FLT_MAX; — Actor.cpp, jump height is faked.
  • // TODO: Enhance MicroPather to add that capability (or write our own pather)! — PathFinder.cpp.

  • The comment -- Tell the coroutines to abort to avoid memory leaks appears more than a dozen times across the AI scripts.

This is not a subsystem that needs tuning. It needs an architecture.

3  ·  The approach

There is a mature, well-documented body of game-AI engineering for exactly these problems — GDC talks, the Game AI Pro series, shipped-game post-mortems. The question was never "is this solvable." It was which techniques fit a 2D, fully-destructible-terrain game with a Lua modding culture, and how to build them so the result is genuinely excellent — not adequate.

3.1   The techniques, scored for Cortex Command

TechniqueFitRole it plays in the build
Utility AI / IAUS●●●●●The tactical decision-maker. Score every option by weighted "considerations"; pick the best. Replaces the AIMode-enum dispatch — and every score is a loggable reason.
Influence maps●●●●●The shared spatial world-model. Threat / alarm / friendly-density / danger grids. Biases pathfinding and feeds utility scores. Fixes clumping, over-suppression, self-preservation.
D* Lite + HPA*●●●●●The incremental pathfinder. Repairs only the changed region instead of a full re-A*. HPA* regions for long hauls. Built for exactly this problem.
Behaviour trees●●●●●The behaviour-execution layer. A tick model that maps cleanly onto today's coroutines — wrap each Lua behaviour as a tree leaf. Visualizable. Not a decision-maker on its own.
HTN planning●●●●●The squad / commander layer only. Decompose "hold the brain" into squad goals. Too brittle for per-actor use under per-frame chaos.
GOAP planning●●●●●A sub-planner for bounded sequences — breach-and-enter, dig-to-goal. Destructible terrain invalidates plans too fast for it to be top-level.
Machine learning (RL)●●●●●Offline only — QA and tuning utility weights (§8). Never at runtime: opacity, non-determinism, retraining cost when a mod adds content.
LLMs●●●●●Flavour dialogue and an optional async "coach" only. Never in the tactical loop — latency, cost, determinism, offline play.

No single technique wins. The answer the survey, the shipped-game evidence (Halo, Killzone 2, Horizon Zero Dawn) and our own code all point to is a layered hybrid — each technique doing the one job it is best at. That architecture is §4.

3.2   The architecture decision — settled

Three strategies were possible. The decision is hybrid — and not as a midpoint. The two "pure" options are each actively worse, not merely less ambitious:

[MOD]  Pure Lua — rejected

Fixing only the Lua behaviour layer cannot reach the incremental pathfinder, the influence maps, or a true per-tick reflex. Its ceiling is a tidier version of today's coroutine soup. It is not a smaller version of the goal — it is a lower one.

[MOD][CODE]  Hybrid — chosen

The engine owns the machinery — incremental pathfinder, influence-map grids, a blackboard, the decision-event channel, the utility and behaviour-tree kernels. Lua stays the brain: which considerations apply, what behaviours exist, the leaf actions. This is what every shipped tactical game does — and it keeps Lua, the fork's modding moat, fully intact (§6).

[ARCH]  Pure C++ — rejected

Moving the whole AI into the engine is not faster to a great result — it still has to build every layer — and it deletes the Lua modding ecosystem, CC's single biggest competitive advantage. An un-moddable AI is a documented player complaint (Door Kickers 2). More work, worse outcome.

The governing principle: the engine owns the machinery, Lua owns the judgement. C++ gives the AI fast senses, memory and a pathfinder; Lua decides what to do with them and stays open to modders. The "hardest path" is not a different architecture — it is this architecture, built in full, every layer, to a defined finish line, with nothing deferred.

4  ·  The target architecture

This is the system being built — every layer, in full. A layered stack: fast, dumb, safety-critical layers at the bottom; slow, smart, strategic ones at the top; an always-on debug layer across everything. Each layer is a separate, independently-verifiable piece — which is what makes the milestone plan in §7 possible.

5  ·  The engine work

The architecture is hybrid because most of it is new engine capability. Today the AI is starved — one random ray for eyes, no memory beyond coroutine locals, no map of where danger is, a pathfinder that cannot keep up, and a fixed throttle that cannot react. This section is the C++ side, in enough detail to build from.

5.1   The pathfinder — the deepest change

This is the single largest and most important piece of C++ surgery in the overhaul, and it is not Lua — it is the C++ classes Source/System/PathFinder.cpp/.h wrapping the vendored Source/System/MicroPather/ library. Today that pairing gives a non-incremental A* over a uniform PathNode grid: every terrain change forces a full re-search; a pather is built per worker thread and reset on essentially every request; jump height is the faked FLT_MAX sentinel; the Scene::UpdatePathFinding reconciliation is throttled and can be starved outright. The code's own TODO already states the fix: "write our own pather".

So that is the change — MicroPather is removed entirely and replaced with a purpose-built incremental pathfinder. Four shifts:

  • Incremental search (D* Lite / LPA*). Instead of recomputing a path from scratch, the search keeps per-node state and, when an edge cost changes, repairs only the consistency-affected nodes. A blast that changes thirty cells repairs in microseconds, not a full re-A*.
  • A path becomes a living thing, not a fire-and-forget list. Today a request computes a node list and returns it; the list then silently goes stale. With D* Lite, each actor following a path owns a persistent search whose state is repaired continuously as terrain changes and as the actor advances (its start moves). The actor's path is always current. This is an ownership-model change that ripples into the Actor hooks (§5.3).
  • Terrain changes feed the searches directly. Dirty-terrain regions push edge-cost updates into the live searches that actually touch them; searches elsewhere pay nothing. HPA*-style region abstraction keeps long-haul routes cheap and localises most repairs — and a dig planner sits beside it: given a goal with no walkable route, it returns the minimum-cost excavation that opens one (this is what kills erratic digging).
  • Real, capability-annotated navigation. EstimateJumpHeight() returns a true value derived from the actor's jetpack impulse. Edges are then tagged with the capability they require — walk, jump-height-N, dig-strength-X, needs-jetpack — and the search only uses edges this specific actor can traverse. The path it returns is one the locomotion layer can actually follow, closing the gap that today produces unfollowable routes.

Touch-points: Source/System/PathFinder.cpp/.h (rewritten); Source/System/MicroPather/ (removed); Source/Entities/Scene.cpp (UpdatePathFinding, GetPathFinder); Source/Entities/Actor.cpp (UpdateMovePath, OnNewMovePath, PreControllerUpdate, EstimateJumpHeight).

5.2   The engine systems

Alongside the pathfinder, the engine gains these systems. Each is a bounded C++ addition with a Lua API on top — the engine owns the machinery, Lua drives it.

SystemWhat it is, and what it gives the AI
Influence-map subsystemDecaying scalar grids — threat, alarm, friendly-density, danger-imminent — updated time-sliced and exposed to Lua to read and to register new layers. The AI's spatial awareness.
Per-actor blackboardA typed memory record — target, last-seen positions, current path, ammo, standing order, threat memory — that both C++ and Lua read. Replaces scattered coroutine locals.

5.3   The ripple — what else the engine work touches

An overhaul this deep is honest about its blast radius. Beyond the pathfinder and the new systems, these existing parts of the engine change too — an AI coding agent should expect to touch all of them:

Coordinate with the Multiplayer flagship (ADR-015)

Networked multiplayer is cortex-modern's second committed flagship (Multiplayer, ADR-015), and it is sequenced to ride this AI work. Two things bind the two builds — get them right here and multiplayer inherits them free:

  • Build the AI's new C++ systems to the determinism-island contract now. The pathfinder, influence maps, blackboard, kernels and persistent orders are all new simulation state the multiplayer build must replicate — and, for PvP, make bit-identical. Built clean to the contract — ordered iteration, single-precision or canonical floats, one seeded RNG, no wall-clock, a deterministic threaded merge — they cost nothing; retrofitted later they are pure determinism debt. (A welcome side effect: once that island exists, the AI's own tests can tighten from statistical to exact — §8.3.)
  • The harness is one apparatus. The Multiplayer flagship's M0 is this flagship's M0 — the decision-event channel, replay capture, the headless runner and the per-tick checksum are shared. Build the observability and checksum harness once; both flagships gate on it.

5.4   Why the engine work pays off far beyond the AI

The C++ here is not AI-only cost. It is foundational infrastructure with leverage across the whole game — which is exactly why the deep code changes are worth making rather than patching around:

  • The incremental pathfinder serves everything that moves — AI, the campaign, any future unit, and a player "show me the route" tool.
  • Influence maps drive the campaign's strategic AI, and the danger field can render as a player-facing overlay — a gameplay feature, not just an AI internal.
  • The decision-event channel and replay are the same infrastructure the Multiplayer and Campaign efforts want for their own debugging and after-action review.
  • The blackboard, the perception API and the utility / behaviour-tree kernels widen the Lua surface permanently. Once they exist, a whole class of future AI features — and modder AI — turns from [CODE] into [MOD]. The one-time engine investment keeps paying.

Together these systems are a first-class [ARCH] AI subsystem — the clean home everything in §4 lives in, and a reusable platform the rest of cortex-modern builds on.

6  ·  The mod surface

Cortex Command's modding ecosystem is the fork's biggest asset — twenty years of .rte mods on mod.io, Void Wanderers among them. The overhaul is designed around it, not at its expense.

6.1   The new Lua API

The hybrid split means modders — and we — author the AI's judgement in Lua against a small, declarative API. The engine kernels do the rest. The shape:

-- a CONSIDERATION scores one factor, 0..1 -- the inputs to a decision
ai.consideration("low_health", function(self)
  return curve(self.Health / self.MaxHealth, "inverse")
end)

-- a BEHAVIOUR ties considerations to a behaviour tree
ai.behaviour("seek_medkit", {
  considerations = { "low_health", "medkit_known", "no_threat_near" },
  inertia        = 0.1,            -- resists flip-flopping
  tree           = "trees/seek_medkit",
})

-- a LEAF ACTION is a behaviour-tree primitive.
-- A legacy coroutine behaviour is itself a valid leaf -- the compatibility bridge.
ai.action("equip_digger", function(self) ... end)

-- the AI EMITS events -- the debug overlay and the test harness both read these
ai.emit("decided", { behaviour = "engage", score = 0.81,
                     reason = "threat in range, ammo ok, cover available" })

Modders register considerations, behaviours and actions into their own namespace; the engine's utility kernel scores them and the behaviour-tree kernel runs them. The old per-object ScriptPath hook, the HumanBehaviors / SharedBehaviors tables and the Native* customization points all remain — see below.

6.2   Will this break mods?

The honest answer: no — because mod compatibility is a hard requirement with its own validation, not an afterthought. Existing AI mods fall into three categories, only one of which carries real risk; how each is kept working is the three-layer model in §6.3.

A   Use the stock AI

The vast majority. Custom actors whose .ini points ScriptPath at the stock Base.rte/AI/HumanAI.lua (or Crab, etc.). They keep working — and their actors get the new, better AI for free. Requires only that the entry-point contract is preserved.

B   Ship their own AI

Unaffected. A mod with a fully custom ScriptPath never calls into anything the overhaul changes — it runs its own brain. The ScriptPath hook is a hard opt-out: any mod can always pin its own AI and ignore ours entirely.

C   Extend the stock AI

The risk category. Mods that require NativeHumanAI, override its Create*Behavior factories, or inject custom coroutine behaviours depend on its internal shape. They are kept working by the behaviour bridge — see the compatibility layers below.

6.3   The compatibility layers

A shim can faithfully reproduce an interface — the functions a mod calls, their arguments, their return shapes. It cannot reproduce an outcome: the whole point of the overhaul is that the AI behaves differently — better. A translator translates interfaces, not outcomes. So compatibility is built in three cumulative layers. What makes all three cheap: the old AI is just Lua — 5,832 lines under Data/Base.rte/AI/, not compiled into the engine — so it never has to be deleted.

1 · The API facade

Every rebuilt engine system keeps its old API as an explicit, tested facade. The new pathfinder still exposes CalculatePathAsync and MovePath in the old shape; the AIMODE_* constants survive as aliases the new order system understands; the Controller surface is unchanged. New machinery, old doorways. Built as a discipline within each milestone that touches a system — not as a separate task — and covered by old-API tests so it cannot silently drift. Keeps category A working.

2 · The behaviour bridge

The behaviour-tree kernel ships a leaf-node type that wraps a legacy function(AI, Owner, Abort) coroutine and ticks it under the tree's Success / Failure / Running protocol — a clean, well-understood mapping. The Create*Behavior factories and the HumanBehaviors / SharedBehaviors tables are preserved as shims over the new kernels. Built in milestone M4. Keeps category C working.

3 · The legacy profile

The entire old AI — dispatcher and behaviours, coroutine pattern and all — is frozen and packaged as an opt-in Legacy AI profile, selectable per-actor via ScriptPath. It runs unchanged on top of layers 1 and 2. A mod that depends on the old AI's exact behaviour pins to it and gets it. The new AI stays the default and stays uncompromised; the legacy profile is a transition courtesy with a published sunset. The escape hatch for any mod.

The honest limits
  • A shim keeps a mod working, not better. An actor on the legacy profile runs the old AI; getting the new one means migrating — the author's choice, never urgent.
  • Truly bit-identical behaviour would also need the old pathfinder. The legacy profile runs the old brain on the new pathfinder, so its routes are different — better. The line is drawn there deliberately; MicroPather is not carried forever for the rare mod that depended on bad routing.
  • Layer 3's fidelity rests on layer 1's. The old Lua assumes what each engine call does; the facades must honour the documented contract, not merely the signature.
  • A total conversion like Void Wanderers couples to far more than the AI — activities, the buy menu, the metagame, scenes. This plan guarantees the AI overhaul will not break it; it cannot speak for the rest of cortex-modern's wider modernization.

The corpus, concretely. The CI mod corpus is the local cccp_mods/ directory — Void Wanderers and its author-recommended companions, the Mappack and BB+ (~3,500 files in all). It is a hard, real-world exercise of layer 1: a scan of the corpus shows Void Wanderers drives the AI through the command API (SetAIMode, AddAISceneWaypoint, UpdateMovePath …) ~130 times across two dozen mission and tactics scripts, and the Mappack's activities call it too — yet neither extends the stock AI's internals anywhere. So this corpus leans entirely on the API facade (layer 1) and not at all on the behaviour bridge: it is a category-A/B corpus, and it proves that the command-API facade is the surface the real ecosystem actually depends on. The behaviour bridge and the legacy profile remain the insurance for category-C mods beyond it.

The guarantee — compatibility is measured, not promised. From milestone M4 the validation harness loads and runs that corpus on every CI cycle. The legacy profile is regression-checked against the pre-overhaul behaviour baseline that M0 records before any AI code is touched. If a mod breaks, the failure report names the exact call — and the fix is one of: repair the facade, pin the mod to the legacy profile, or help it migrate. "Does Void Wanderers still work" is a line in the definition of done and a green light on every build — never a guess.

7  ·  The plan — milestones to completion

How this plan is scoped

This plan is sequenced by dependency and gated by validation — not by calendar time. The build is executed by AI coding agents, for which the cost of a task is not its human-hours; the meaningful units are what must exist first and how we know it is done. So every milestone below states what it depends on and the exact, machine-checkable condition that closes it — and none carries a time estimate. Nothing is deferred for being large. An agent picking up this build starts at M0; each milestone is a complete, shippable improvement, and the build always contains a working, better AI than the milestone before. Every new C++ system below is built to the determinism-island contract (§5.3) from the start, so the Multiplayer flagship inherits it free.

8  ·  Validation — proving the AI, without watching it

An overhaul this size is only as trustworthy as its test regime. The plan is built so the result is proven, not vibed — and proven almost entirely without a human in the loop. That is why M0 builds the test apparatus first. The harness is not an afterthought; it is the instrument that lets AI coding agents build the AI at all, because it is the thing that decides, automatically, whether a change made the AI better or worse.

8.1   The AI thinks out loud

Because every decision emits a structured event, tests assert on the cognition stream, not on pixels. The decision-event schema — the thing M0 builds — is roughly:

event = {
  tick      = <sim frame>,
  actor     = <actor id>,
  layer     = "reflex" | "tactical" | "navigation" | "squad",
  type      = "behaviour_selected" | "target_acquired" | "path_failed" | ...,
  chosen    = "engage",
  scores    = { engage = 0.81, retreat = 0.44, regroup = 0.30 },
  reason    = "threat in range, ammo ok, cover available",
  target    = <actor id or position>,
}

You never watch the AI; you read what it decided and why. "Did any actor emit engage against a friendly?" → fail. "Did one emit path_failed and never recover?" → fail.

8.2   The trust scenario suite

Twelve hand-authored scenarios, each a scripted scene + an order + behavioural pass/fail assertions, run headless. They are the spine of the suite:

#ScenarioWhat it proves
AI-01Defend the brain roomHolds position, reacts to alarms, does not abandon the post without an order.
AI-02Breach a doorSelects a breaching tool or a penetrating weapon; does not waste ammo on what it cannot dent.
AI-03Dig to an objectiveEquips a digger, cuts a viable tunnel, does not seal itself in.
AI-04Recover from a collapsed tunnelDetects the stale path and replans / digs / retreats within a deadline.
AI-05Suppress an alarmInvestigates or suppresses only when plausible — does not chase every noise.
AI-06Rescue a downed unitExtracts, covers, or flags it impossible — never idles.
AI-07Avoid a dropship crushClears an obvious landing path when warned.
AI-08Hold formation through a bunkerThe squad keeps useful spacing — no clumping, no stalling on each other.
AI-09Use a medikitHeals when safe; interrupts and defends when threatened.
AI-10Weapon pickupSeeks a nearby weapon when it is genuinely better than the current one.
AI-11Retreat from an unwinnable breachReports the objective impossible instead of looping on it forever.
AI-12Enemy flanks through a new holeUses a route that did not exist until terrain changed — the pathfinder is genuinely live.

Every scenario runs on destructible terrain, with both friendly and enemy AI, and every run records a replay and the full reason log.

8.3   Statistical pass/fail — flaky becomes rigorous

Cortex Command's simulation is non-deterministic, so a test cannot assert exact state. Instead each scenario runs K times and asserts on rates with a confidence bound — "holds the brain in ≥ 95% of runs", "friendly-fire incidents ≤ X per run on average", "no actor stuck > N seconds in ≥ 98% of runs". Non-determinism stops being a problem to fight and becomes a property the suite measures around.

8.4   Self-play, regression & the mod corpus

The new AI is run against itself, against the old AI, and against prior versions of itself — across many maps, many times, unattended. Self-play surfaces emergent stupidity that scripted scenarios miss (mutual stalemate, suicidal rushes, two sides both stuck). New-vs-old win rate is a single number for "are we winning"; new-vs-previous-version catches regressions the moment they appear. From M4 the harness also loads and runs the cccp_mods corpus (Void Wanderers, the Mappack and BB+ — §6.3) every cycle; the compatibility guarantee of §6.3 is a test, not a promise.

8.5   Fuzz & invariant testing

Beyond the twelve authored scenarios, the harness procedurally generates scenes — random terrain, random placements, random orders — and asserts invariants that must hold everywhere: no actor is ever stuck beyond N seconds, no actor ever fires through a friendly, every actor always carries a current reason label, no behaviour tree ever hard-loops or crashes. Fuzzing finds the long tail the authored scenarios cannot.

8.6   The autonomous loop

The harness emits a machine-readable report — per-scenario pass/fail, the full metric set, and a saved replay for every failure. It runs in CI on every change. An AI coding agent works the loop directly: edit the AI → the harness grades it → read the report → iterate, with the failure replays pointing at exactly which decisions went wrong. The harness is the fitness function — it is what makes an agent-driven build of something this large tractable, because "better" is never a judgement call. The same harness doubles as an offline auto-tuner: wrap it in a search over the utility-layer weights and keep the weight-set that scores highest. The human defines which considerations exist; the machine finds the weights.

8.7   What the harness measures

MetricWhat it catches
Objective completion rateWhether the AI actually does the job it was given.

8.8   Where the human stays

The human role shrinks to three things the machine cannot do: authoring the scenarios and setting the pass thresholds; spot-checking the saved replays of failures the agent could not resolve; and the final, irreducible "is it fun" judgement. The machine checks against the bar; the human sets the bar. That is the minimum — and deliberate — human footprint.

9  ·  What not to do

  • Don't rip out Lua. The mod ecosystem is the fork's biggest asset; Door Kickers 2's un-moddable AI is a documented player complaint. The architecture adds structure to Lua — it never deletes it.
  • No LLMs or runtime ML in the tactical loop. Latency, cost, non-determinism (it would break replays and the Multiplayer flagship), offline play, and modding breakage. ML earns its keep in exactly one place — the harness's offline auto-tuner (§8.6) — and never in the runtime loop.
  • GOAP is not the top level. A destructible world invalidates plans every blast. Use GOAP only as a sub-planner for bounded sequences (breach-and-enter, dig-to-goal).
  • HTN is not per-actor. Too brittle under per-frame chaos. It is the squad/commander layer only.
  • Not pure behaviour-tree, not pure utility. Utility decides what; the tree executes how. Either one alone re-discovers the other's problem the hard way.
  • No JPS+, no Recast/Detour. JPS+ assumes static, uniform-cost grids; Recast is a 3D navmesh system. Neither fits 2D pixel-destructible terrain. D* Lite does.
  • Land it milestone by milestone. Not because a large change is hard to write — it is not — but because each milestone must be proven by the harness before the next is built on it. An un-validated build cannot be course-corrected. The milestones are validation checkpoints.
  • Don't skip the harness. M0 comes first, always. An AI you cannot measure cannot be built to a finish line — and "no compromise" means nothing without a test that can prove there was none.
Definition of done

The AI overhaul is complete — and not before — when all of the following hold:

  • The full AI-01..AI-12 trust suite is green at its target pass-rates, on destructible terrain, across every difficulty level.
  • The fuzz harness finds no invariant violation across a large procedurally-generated scenario set.
  • Large-scale AI-vs-AI self-play is stable over long runs and many maps — no stalemates, no emergent passivity, no crashes.
  • A full side runs autonomously and competently with zero player input — and a player can take direct control of any unit and release it with no loss of intent.
  • The new AI is the Base.rte default and the stock AI runs entirely on the new kernels; the community mod corpus — Void Wanderers included — still loads and runs, whether on the new AI or on the preserved opt-in legacy profile.
  • Every shipped decision is explainable: it carries a reason, and it can be replayed.

That is the finish line. It is specific, it is measured by machine, and it does not move.
