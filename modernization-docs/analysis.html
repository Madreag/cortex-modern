Technical Analysis

The engine dissected: five cross-cutting architectural issues, nine subsystems, the dependency audit, and the mod-vs-engine boundary. Findings come from a full read of the ~220K-LOC development branch.

Tag legend

[MOD] Lua / INI / data, no recompile   [CODE] a bounded C++ engine change   [ARCH] a large rework or new simulation core   [DEP] a dependency swap or upgrade   [BUILD] a build-system change

1  ·  Five cross-cutting issues

These are not subsystem bugs — they are architectural properties that touch many systems at once. Everything in the Roadmap traces back to one of these.

1.1   The 8-bit palette — the keystone knot

Everything is 256-color indexed. The single hardest fact in the codebase:

A terrain pixel's byte value is its material ID, which is a palette index. Material, colour and physics all collapse onto one 8-bit number.

  • 256-material hard cap and 256-colour hard cap on all sprites and terrain (banding, no gradients, one shared palette).
  • Terrain is three 8bpp Allegro BITMAPs; SceneLayer literally asserts color_depth == 8.
  • Glow / post-processing detection is a CPU pixel-scan for magic palette indices (117, 98, 120).
  • Blend modes need CPU-built 64 KB colour lookup tables, pruned by a 5-minute timer to stop runaway memory.

Decoupling the material map from the palette index is the pivot point — it is a simulation data structure masquerading as a rendering one, and nearly every 32-bit-colour ambition blocks on it. Highest leverage in the codebase; also [ARCH]-scale and high-risk.

1.2   Single-threaded simulation — the performance ceiling

The GPU renderer already made drawing cheap. The bottleneck is now the simulation, and it runs on one core.

  • MovableMan::Travel() is a plain serial loop over every actor, item and particle.
  • A BS::thread_pool exists and is used — but only for Lua scripts, AI vision rays and MOID-layer drawing. The physics integrator itself is strictly serial.
  • On a modern 8–16 core CPU ~90% of cores idle during the physics phase. A source comment admits it: "...unnecessary when multithreaded-sim-and-render is in."
  • Collision is per-pixel: every object is a bag of "atoms" that Bresenham-walk every pixel of their path, doing 2+ palettized getpixel reads per step. dynamic_cast appears in the hot loop.

1.3   Simulation resolution — locked to pixels

The simulation is locked 1:1 to pixels. There is no sub-pixel physics and no scalable "sim resolution."

  • Object positions are floats, but every collision query truncates to integer pixels — the Bresenham stepper is the integrator.
  • c_PPM = 20.0 (pixels-per-metre) is the only bridge between physical units and pixels, and it is a compile-time constant.
  • You cannot "scale" the simulation resolution — it is a property of the data model (atom offsets authored in pixels, terrain-bitmap dimensions = scene size), not a tunable.
  • Fixed 60 Hz. No continuous collision detection — objects faster than 500 m/s are simply deleted/gibbed instead of tunnelling.

Realistic levers: render interpolation (§1.4) and the Box2D rigid-body path. Genuinely raising sim resolution is [ARCH] and arguably wrong — the pixel grid is Cortex Command's identity.

1.4   No render interpolation

Rendering draws objects at their raw discrete m_Pos. If the monitor is not exactly 60 Hz, motion stutters (positions jump a whole timestep) or frames are redrawn identically. m_PrevPos already exists (used for rest detection) but is never fed to the renderer. Well-scoped [CODE] win — but upstream tried twice and failed: the original interpolated-render branch collapsed under an over-ambitious sim/render thread split, and interpolated-render-redux, despite the name, never wrote any interpolation code at all (see Upstream Branches).

2  ·  Subsystem findings

Rendering

GPU side is done — FBOs, shaders, BigTexture PBO streaming, vertex batching. But the world surface is still CPU-software-rasterized into 8bpp bitmaps: every MO sprite draws via Allegro draw_sprite into a shared indexed buffer, then a Blit8 shader palette-decodes it. Dead code: stubbed CompileShader, commented-out m_Blit8.

Physics / Simulation

Atom-based per-pixel collision; single-threaded (§1.2). AtomGroup::Travel is self-described in comments as a "trainwreck" / "dumpsterfire". MO-vs-MO collision is hard-disabled in the limb-push path (// TODO: Fix HitMOs issue!!). A single-author, AI-assisted box2d-emscripten branch prototypes a Box2D physics layer, but it is an unfinished, dormant spike (see Upstream Branches).

Scripting

luabind 0.7.1 is the worst dependency — so fragile the build cannot use precompiled headers on binding files. The code even works around its call cost by building Lua source strings at runtime and compiling them per call. sol2/sol3 is the modern replacement; LuaJIT 2.1 itself is fine — keep it.

AI

~95% Lua (~5,800 lines in Base.rte/AI/). C++ gives an actor a Controller (the AI "presses the same virtual buttons" a human would), an AIMode enum and async A* pathfinding. Combat is tactically solid (velocity-led aim, hearing senses); squad / strategic AI is shallow — squadmates just copy the leader's inputs. The full overhaul — an incremental pathfinder, influence maps and a decision brain — is the flagship on the AI page.

Audio

Modern-ish FMOD Core: bus routing, a compressor/limiter DSP chain, per-player 3D listeners, a real adaptive-music system (MusicMan / DynamicSong). Gaps: no terrain occlusion (you can't hear gunfire muffled through dirt), no reverb, no sidechain ducking.

Input

Solid SDL3 — 4-player, hot-plug, remap wizard, 1,798-line controller DB. But zero rumble/haptics and no gyro: SDL_RumbleGamepad is never called. Allegro input headers still linger — an unfinished migration.

UI / UX

Two GUI systems: a ~50-file legacy retained-mode toolkit (all menus, BuyMenu, the 6 editors) and Dear ImGui (used minimally, for dev/debug). The PieMenu is genuinely well-built. BuyMenu (2,459 lines), the editors, and the Metagame (a 5,999-line GUI file) are the dated UX.

Networking

The old multiplayer was a screen-streaming model (the server compresses each client's viewport to UDP — not real netcode; hard 4-player cap, unhideable latency). Upstream removed it outright (commit "RIP Multiplayer 2019-2025", Jan 2025): all four networking files — NetworkServer, NetworkClient, MultiplayerGame, MultiplayerServerLobby — are commented out of the Meson build and no longer compile. Only the RakNet library is still built and linked, a pure dead dependency. Reviving multiplayer is under active study — see the Multiplayer page.

Build & Deps

Two parallel, already-diverged build systems (Meson + MSBuild). The vcxproj's PlatformToolset is empty (non-reproducible builds). Linux builds use system libs, Windows uses bundled — different dependency versions per platform. See the audit below.

3  ·  The mod boundary

The central question: what can be done as a mod vs. what needs an engine change. In one sentence:

Modders own instances, behaviour and rules. The engine owns types, properties, the API surface and the simulation core.

The codebase is extremely data-driven — 576 INI files and 53,000 lines of Lua already ship in Data/, proving the surface is huge.

[MOD]  Zero recompile

  • Any new content — weapons, actors, craft, materials, scenes, sounds — as presets of existing types (CopyOf inheritance).
  • Whole new factions (the shipped Ronin.rte etc. are exactly this).
  • All balance / tuning — any property that already exists.
  • Per-entity behaviour via Lua (13 lifecycle hooks).
  • New game modes (GAScripted — a 9-callback Lua contract; 18 modes already ship).
  • Global rules (GlobalScript), new/replacement AI (all Lua), custom HUDs, custom shaders.

[CODE]  Needs a recompile

  • Adding a new INI property to an existing class — there is no custom-property system; an unknown property is a fatal error. (Workaround modders use: runtime SetNumberValue tag maps.)
  • A new C++ Entity type — modders make new presets, never new types.
  • Exposing anything new to Lua — if a method is not in LuaBindings*.cpp, scripts cannot call it.
  • The simulation core, the INI parser, the fixed set of script hooks.

Strategic insight: binding more of the engine to Lua is a one-time [CODE] cost that permanently converts future features into [MOD] territory. Widening the Lua API and adding a real custom-property mechanism are the two changes that most expand what the community can do without us.

5  ·  The process reality

This shapes what is realistic. The upstream project is a very small team — a handful of contributors. development has been frozen since 2026-04-06; all activity is scattered across unmerged, mostly single-author branches (see Upstream Branches). Long-stuck PRs (one core refactor open 2.3 years) reveal the constraints: mod-compatibility paralysis (breaking changes freeze over fear of breaking cccp.mod.io), bus-factor reviewer gaps, and long-lived branches that never land.

Implication: our modernization work must be incremental, mod-compatible, individually shippable, and not dependent on heroic review. Big-bang [ARCH] PRs die in this environment — the branch graveyard proves it.
