    Write a bool's storage byte, not the compiler's opinion of it
    
    A bool whose owner never assigned it holds whatever byte the allocator had, and
    reading that as a bool is undefined. Apple clang 17 exploits it three ways on the
    same source: at -O0 the bool-typed copy masks to the low bit and the writer emits
    0, so an unset setting would be archived as a valid false; at -O2 it emits 100;
    and in the engine's inlined build to_chars takes the single-digit fast path on a
    value it knows is 0 or 1 and emits the byte '0' + 100 = 0x94. MSVC emits 100. So
    both the archive and the refusal that names it depended on the compiler.
    
    A non-template overload taking the reference copies the storage byte with memcpy
    and writes the number it is: no bool-typed load anywhere on the path, which is the
    only portable read of a byte that is not a valid bool. An assigned bool still
    writes 0 or 1, so no archive changes. vector<bool> keeps its own overload because
    it packs bits and its elements have no storage byte of their own.

    Initialise the audio manager's unset members
    
    MuteAudioOnFocusLoss was added next to the three mute flags but never added to
    AudioMan::Clear(), so a boot whose Settings.ini omits the property left it at
    whatever byte the heap handed the singleton. Update() read it every frame and the
    checkpoint writer serialised it, which is how a raw byte reached the reader and
    made a valid save unreadable. The five FMOD handles had the same hole: Clear()
    never set them, so InitializeAudioSystem tested an uninitialised pointer.
