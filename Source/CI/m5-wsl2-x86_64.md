## MPerfBench heavy-AI residual characterisation

`Data/Tests.rte/Activities/MPerfBench.lua` declares itself "not a determinism
scenario" — 150 BRAINHUNT-AIMODE actors at start + six 30-actor reinforcement
waves over 1200 ticks, designed to stress the parallel-AI workers. Path E
closes the Equip* / Attachable race that the Linux + macOS bring-ups identified
as the **primary** MPerfBench residual; the remaining residual races (PathFinder
partial / See-ray future / bullet-spawn on Linux at tick-210; controller bit 4
on macOS at tick-44) surface in this scenario but at high tick numbers.

### Comparison to the prior bring-ups

| Platform | Scheduler | First-divergence tick | Per-subsystem signature | Run-rate |
|---|---|---|---|---|
| Linux | x86-64 (GCC libtbb par_unseq) | ~210 | `actors` / `particles` — PathFinder partial / See-ray future / bullet-spawn candidates | ~80% diverged (1-in-5 sweeps clean) |
| macOS | arm64 (`_LIBCPP_PSTL_BACKEND_SERIAL`) | ~44 | `controller` (bit 4 / MOVE_LEFT, NativeHumanAI.lua:671 keyed off lateralMoveState set by HumanBehaviors.GoProne) | 0% diverged on 5-of-5 sweeps observed, but the macOS agent reproduced a single-run divergence at this signature during bisection |
| **WSL2** | **x86-64 (separate Linux scheduler, AMD Zen 5)** | **982** at lua-states 16; **CLEAN** at lua-states 8 | `controller` (first), then `actors` / `particles` / `carve_math` within 14 ticks; `sim_rng` / `terrain` / `scene` 19–20 ticks after first divergence | **10% (1 / 10) diverged at lua-states 16; 0% (0 / 10) at lua-states 8** |

**Interpretation:** WSL2's controller-first per-subsystem ordering matches the macOS signature, NOT the Linux signature — both expose a controller-bit-N race, with the per-actor controller-state surface (53 control booleans + 6 analog floats per `MovableMan::Update`'s `controller` hash slot) drifting first and the downstream Travel-integrator outputs (`actors` position / `particles` position) falling out 14 ticks later. The first-divergence tick is much later on WSL2 (982 vs macOS's 44, vs Linux's 210), consistent with a race that requires both a specific scheduler interleaving AND the heavy late-tick population (the reinforcement waves at ticks 180/360/540/720/900/1080 mean tick 982 is right after the 5th wave drop, when the actor count is at peak and an `AI.Target` cross-actor read is most likely to collide with another worker's per-actor position write). The macOS agent's hypothesis (HumanBehaviors.GoProne reading `AI.Target.Pos + AI.TargetOffset` cross-actor at `HumanBehaviors.lua:920–921` during `ShootTarget`, then writing `AI.lateralMoveState` at `HumanBehaviors.lua:894/896`, then NativeHumanAI.lua:670–671 keying off it to set `Controller.MOVE_LEFT` on `self.Ctrl`) is consistent with the WSL2 signature.

**WSL2 datapoint adds:** the race is real but rare (10% on a 32-logical-CPU AMD Zen 5 host at lua-states 16), absent at lua-states 8 (10 / 10 clean), and the per-subsystem ordering is `controller → actors/particles → carve/sim_rng/terrain/scene → decisions`. No new candidate location surfaces on WSL2 beyond the macOS hypothesis; this is a third-host empirical confirmation of the same race.

### Why not ablate on WSL2

Per `M4A_PLAN.md` §1.2 non-negotiable #2 and the bring-up directive (read-only on source), audit-only on this branch. The macOS bring-up has already pinned the byte source via instrumented per-actor field dumps at the divergence tick; an independent WSL2 ablation would replicate, not extend, the existing investigation. WSL2's contribution to Phase 3 is the third-scheduler confirmation that the residual is real, scheduler-dependent in its trigger frequency, and follows the same per-subsystem ordering as macOS — strong evidence that the macOS-pinned `GoProne → lateralMoveState → MOVE_LEFT` chain is the right fix target and not just a macOS-specific artefact.

### Results

Run was capped after ~11 min into run 1 of 2 of the 900-tick scenario at
~75% sim-progress (TSan overhead on this binary is roughly 30–40× — full
2-run completion estimate ~25–30 min). The unique-race-signature set is
saturated by run-1's ~70% point: 605 total race reports across 67 unique
signatures.

**No Equip* / Attachable / SetHeldDevice / RemoveAttachable race reported.**
The race classes the macOS bring-up pinned (cross-actor
`Arm::SetHeldDevice` → `Attachable::UpdatePositionAndJointPositionBasedOnOffsets`
chain) do not appear in TSan output after Path E. This is the direct
empirical confirmation that Path E Form 3 closes the contract violation at
the binary level, not just at the per-tick-hash level — TSan would have
fired on the cross-actor read/write race the moment the parallel-AI phase
exercised the Equip* path, and it doesn't.

**No MovableMan::AddActor / AddMO race reported either.** Linux + macOS
documented these as candidate violators in `M4A_PLAN`'s §1.1; on WSL2 the
TSan run does not surface them. Either the workload doesn't exercise them
at lua-states 8 (likely — Equip* dominates the AHuman parallel-AI
mutation surface) or they're already inside the SyncedUpdate channel.

**Filtered noise (expected):** TSan reports many races in `libtbb` and
`std::execution::par_unseq` — these match the suppression list entries
verbatim (Linux + macOS noted the same; `m5-linux-x64.md`§"TSan + this
codebase"). Most surface from the `std::execution::par_unseq` join sites
that TBB-internal synchronisation closes but the TSan shadow model can't
see (TBB on Ubuntu 24.04 is not built with `-fsanitize=thread`).

**New noise observation (not a sim-determinism race):** TSan fires on
`SLTerrain.cpp:229–246` (the per-pixel terrain regeneration loop's cache
of `materialFGTextures` / `materialBGTextures` / `materialColors`) and on
`allegro draw.inl:_putpixel`/`_getpixel`. These are render-side concurrent
writes to texture caches under par_unseq, in the same blind spot as the
PathFinder `AdjacentCost` ↔ `UpdateNodeCosts` race the Linux bring-up
filtered — covered by the `called_from_lib:libtbb.so` line in the
suppression list once the surrounding par_unseq frames are walked. These
do not perturb the sim hash (the `actors` / `particles` / `scene` /
`terrain` checksum subsystems are fed earlier in the tick than the
texture-regen loop). Recommend adding to the filter list as
`race:RTE::SLTerrain::` (or a more targeted prefix once the post-fix
investigation is complete) so future TSan CI runs report signal, not
this noise class.

**Suppression-file gotcha (flagged for the M4A TSan agent):** the original
filter list uses signatures like `race:tbb::detail::r1::` — on this WSL2
host TSan's matcher does not apply this pattern to the TBB-internal races
it reports (which originate at `tbb::detail::d1::` and through
`std::execution::par_unseq` adapters — `d1`, not `r1`). The `called_from_lib`
line catches most via library-name match. Recommended update for the
filter file: `race:^tbb::detail::` (broader prefix) + the `called_from_lib`
entry remains. The race-count change is purely cosmetic — TBB races are
filtered by either line — but the named-prefix line should match what TSan
actually emits.

## Notes (observed, not changed)

- **`cccp-ctl --out-dir` relative-path bug.** Passing a relative path to
  `--out-dir` causes the generated report path to be relative; the child
  binary's CWD is set to `gameBin.parent_path()` (via the V1.3 `CwdGuard`), so
  the relative path resolves under `builddir/` instead of the user's intended
  location, and the binary fails to open the report file (`failed to open
  output: Source/CI/...`). `cccp-ctl test all` doesn't gate on this — it logs
  the failure and moves to the next scenario, so an unwary user gets an empty
  out-dir with no aggregate summary. Workaround: pass an absolute path
  (`--out-dir /absolute/path`). Fix is one line in `Source/CLI/cccp-ctl.cpp`
  `PickOutDir` — `fs::absolute(p)` before `return`. Not modified here per the
  no-source-changes rule of this bring-up; flagged for the cccp-ctl V1.4 lane.
- **`SDL_VIDEODRIVER=offscreen` required on WSL2.** WSLg provides a display
  but every determinism child trying to open a real window contends on the

### Phase 7.2 — `cccp-ctl` `--out-dir` relative-path bug (one-line fix proposal)

Target file: `Source/CLI/cccp-ctl.cpp` on `flagship/m5.5-mp-harness`
(`cccp-ctl` changes belong on the M5.5 lane per the original
brief, not this WSL2 branch). The bug is described in §Notes above;
the formal fix proposal:

**Bug.** `PickOutDir` at `Source/CLI/cccp-ctl.cpp:373-385` returns
`ctx.outDir / (prefix + "-" + timestamp + "-" + attempt)` directly. If
the caller passed `--out-dir <relative-path>` (e.g.
`--out-dir Source/CI/wsl2-baseline-traces`), the returned path is also
relative. The path is then forwarded to child binaries via
`-out <path>`; the child binary's CWD is set to
`gameBin.parent_path()` (= `builddir/` for an in-tree build) by the
V1.3 `CwdGuard` (`cccp-ctl.cpp` line ~280), so the relative path
resolves to `builddir/Source/CI/wsl2-baseline-traces/...` instead of
the user's intended location. The child fails to open the report
(`failed to open output: Source/CI/...`); `test all` does not gate on
this failure and proceeds silently, leaving an empty out-dir with no
aggregate summary.

**Reproducer (current behaviour):**
```
cccp-ctl test all --runs 1 --out-dir Source/CI/some-rel-path
# → empty Source/CI/some-rel-path/; child binaries write under
#   builddir/Source/CI/some-rel-path/ instead
```

**Workaround already documented (current bring-ups):** pass an absolute
path (`--out-dir /absolute/path` or `--out-dir "$(pwd)/path"`).

**One-line fix.** Lock the path before returning, so a subsequent CWD
change in the child has no effect:

```diff
--- a/Source/CLI/cccp-ctl.cpp
+++ b/Source/CLI/cccp-ctl.cpp
@@ -378,7 +378,7 @@ fs::path PickOutDir(const OutputCtx& ctx, const std::string& prefix) {
             for (int attempt = 0; attempt < 1000; ++attempt) {
                 const auto now = std::chrono::system_clock::now().time_since_epoch().count();
                 const fs::path p = ctx.outDir / (prefix + "-" + std::to_string(now) + "-" + std::to_string(attempt));
-                if (fs::create_directory(p, ec)) return p;
+                if (fs::create_directory(p, ec)) return fs::absolute(p);
             }
         }
         return MakeUniqueTmpDir(prefix);
```

`fs::absolute` is no-op on already-absolute paths and converts
relative paths against the *current* CWD (which is the user's CWD,
not the child binary's post-`CwdGuard` CWD). Equivalent fix is
`fs::canonical(p)` if the additional symlink-resolution is desired.
`MakeUniqueTmpDir` (the fallback path) is unaffected — it always
returns absolute paths via `fs::temp_directory_path()`.

**Test plan.** Add to the existing `cccp-ctl` selftest suite:
```
cccp-ctl test all --runs 1 --quick --out-dir relative-test-path
# expect: relative-test-path/cccp-ctl-all-<ts>-0/<scenario>/report.json
#         populated for every scenario
```

Flagged for the cccp-ctl V1.4 / `flagship/m5.5-mp-harness` lane; not
modified here per the no-source-changes rule of this WSL2 bring-up.
