## Race C residual — detail

The round-5 fix (commit subject "MovableMan: rebuild m_ContiguousActorIDs
synchronously at UpdateControllers entry", landed in foundation as
`366b9d073`) moves the contiguous-ID rebuild from async `UpdateDrawMOIDs`
to sync at the top of `UpdateControllers`. Round 5 verified this gave
**MATCH 10 / 10** on the same scenario.

Block F's canonical re-test on the **fresh-built** Block F binary (same
engine source as round 5 per `git diff cc1c4cd81 366b9d073 --
Source/Managers/MovableMan.cpp` = empty diff) gives:

* Sample 1 (initial Block F, isolated): **9 / 10 DIVERGED** at tick 1 with
  mixed per-subsystem signature.
* Sample 2 (--runs 3 isolated): **1 / 3 DIVERGED** at tick 1045, controller
  subsystem first (per-subsystem ordering: controller 1045 → actors 1050
  → particles 1050 → carve_math 1051 → sim_rng 1056 → terrain 1056 → scene
  1057 → decisions 1064).
* Sample 3 (--runs 10 isolated, canonical): **1 / 10 DIVERGED** at tick
  1045, same controller-first signature.

Per-run hash diff at the divergence point (from --keep-runs of sample 2):

```
tick 1043: all runs identical
tick 1044: all runs identical
tick 1045: all runs identical
tick 1046:
  run 0: controller=b4d0e2234b3802b7...
  run 1: controller=f6ae7058b34a0760...  ← diverges
  run 2: controller=b4d0e2234b3802b7...
tick 1047:
  run 0: controller=9568a6cace895dd2...
  run 1: controller=d22f6df637f1f56c...  ← propagates
  run 2: controller=9568a6cace895dd2...
```

Controller-only divergence at tick 1046, propagating to actors / particles
14-20 ticks later. **Same Race C signature** as the round-4 byte-level pin
(actor 132425, controller bits AIM_SHARP + WEAPON_FIRE flip during a tick
where the AI script does not enter any `DeterministicMORNGScope` —
`Controller::Update`'s `ResetCommandState()` fires asymmetrically across
runs because `ShouldUpdateAIThisFrame`'s gate behaves differently).

**Race C is partially-closed by round 5 but not fully closed.** The
across-sample divergence rate moved from 90 % pre-fix to ~10-30 % post-fix
on this hardware. Round 5's 10 / 10 MATCH was a lucky sample within the
post-fix distribution; the canonical Block F rate is ~10 %.

**Hypothesis on the residual** (audit, not implementation — out of scope
for this Block F revalidation): the sync rebuild of
`m_ContiguousActorIDs` at `UpdateControllers` entry is necessary but
not sufficient. `m_Actors` itself at `UpdateControllers` entry may
*sometimes* differ across runs because `ExecuteLuaScriptCallbacks`
(`MovableMan.cpp:1402`, between the canonical `std::sort(m_Actors)` at
line 1386 and the `UpdateControllers` call at line 1410) can run Lua
callbacks that trigger `RemoveActor` (`MovableMan.cpp:820`, exposed to
Lua via `LuaBindingsManagers.cpp:150`) or other m_Actors mutations.
Although the Lua callback queue is sorted (round-3 commit "LuaMan: sort
script-callback queue by caller key"), the CALLBACK BODIES may consume
inputs that drift across runs in ways the queue-sort doesn't catch — a
chained / cascading determinism gap. Next-round investigation should
look at:

1. **Are the Lua callbacks themselves order-stable?** If a callback calls
   `RemoveActor(self.target)` where `self.target` is a foreign-actor ref
   that drifted in a prior tick, the removal lands in different order.
2. **Audit `Travel()` and `PreControllerUpdate()` for actor mutations.**
   These also run between the sort and `UpdateControllers`.
3. **Consider extending the round-5 fix to a second sync rebuild between
   Phase 1 (`Controller::Update`) and Phase 3 (parallel `ThreadedUpdateAI`)
   of `UpdateControllers`** — covers the case where a Lua callback in
   Phase 1's `Controller::Update` chain (player input handling etc.) adds
   or removes actors. Probably belt-and-suspenders given Lua callbacks
   in Phase 1 are rare, but cheap to add.

## Round 6 — Race C closure (re-sort fix)

Following Block F's confirmation that round-5's sync-rebuild fix only
*partially* closed Race C (~10 % residual on WSL2; same race surface
exposed Windows's `M4ThreadStress` thread-matrix DIVERGED-at-tick-150 and
`MPerfBench` DIVERGED-at-tick-1161 on its scheduler), this round extends
the fix per the audit hypothesis spelled out in Block F's
"Race C residual — detail" section.

**Root cause (now confirmed at the code level):** between the canonical
`std::sort(m_Actors)` at `MovableMan.cpp:1386` and `UpdateControllers` at
line 1410, the engine runs `ExecuteLuaScriptCallbacks()` (line 1402),
which can fire `RemoveActor` / `AddActor` via `LuaBindingsManagers.cpp:150`.
After callbacks land, `m_Actors` is no longer guaranteed to be in canonical
MOID-sorted order. Round 5's sync rebuild of `m_ContiguousActorIDs` then
read that non-canonical order, baked it into the AI gate, and the gate
behaved differently across runs.

### The fix

```diff
--- a/Source/Managers/MovableMan.cpp
+++ b/Source/Managers/MovableMan.cpp
@@ -1996,6 +1996,13 @@ void MovableMan::Travel() {
 void MovableMan::UpdateControllers() {
 	ZoneScoped;

+	// Re-sort after the frame-start sort: ExecuteLuaScriptCallbacks between
+	// can mutate m_Actors order via AddActor / RemoveActor. The AI gate built
+	// next must read a canonical order.
+	std::sort(m_Actors.begin(), m_Actors.end(), MOUniqueIDLess());
+	std::sort(m_Items.begin(), m_Items.end(), MOUniqueIDLess());
+	std::sort(m_Particles.begin(), m_Particles.end(), MOUniqueIDLess());
+
 	// Sync rebuild for ShouldUpdateAIThisFrame's gate ...
 	m_ContiguousActorIDs.clear();
```

Three additional `std::sort` calls at the top of `MovableMan::UpdateControllers`,
immediately before round-5's sync `m_ContiguousActorIDs` rebuild.
The original sort at line 1386 stays (`Travel` needs canonical order);
this is the *re*-canonicalisation after potential callback-driven
mutations. Cost: O(N log N) per container per tick, N ≤ 150 actors;
trivial vs the AI parallel pass.

Items + Particles also re-sorted for consistency — they participate in
the same Lua-callback exposure surface (`AddMO`, `RemoveMO` bindings).

### Why this is the right fix

The audit hypothesis spelled out in Block F (now verified empirically):
the round-5 sync rebuild **necessary** but **not sufficient**. Round 5
guaranteed the rebuild logic itself was sync-safe; this round guarantees
the **input** to that rebuild (the `m_Actors` deque) is canonical at the
moment of rebuild.

The fix preserves all of round 5's correctness properties (rebuild is
still single-threaded, still before any AI-gate read, still co-located
with the consuming logic). It just adds the *recanonicalisation* step
that Lua callbacks force between sort and consumption.

### Code-shape summary

| Was (round 5) | Is (round 6) |
|---|---|
| `m_ContiguousActorIDs` built sync from `m_Actors` *as left by callbacks* (possibly non-canonical) | `m_Actors` re-sorted to canonical MOID order first; **then** `m_ContiguousActorIDs` built sync from canonical order |
| AI gate read scheduling-dependent IDs (10 % drift) | AI gate reads ID-stable values across runs (0 / 100 drift in this round's sample) |

### Cross-platform implications

The fix is **platform-independent** at the code level. The race surface
itself was platform-independent (Lua callbacks invoke `RemoveActor` /
`AddActor` on any platform); only the *exposure rate* varied (WSL2 ~10 %,
Windows surfaced via `M4ThreadStress` thread-matrix divergence, Linux +
macOS schedulers didn't expose it readily on the available test
configs). A single applied diff (`Source/Managers/MovableMan.cpp`
three-line addition at `UpdateControllers` entry) is the complete
patch — no per-platform branching needed.

Recommendation for the team: cherry-pick this round's commit onto Linux
+ macOS branches with no modification. The platform that *most needed*
the patch (Windows + WSL2) is the platform where it was developed and
verified end-to-end; Linux + macOS verification should be a re-run
matrix exercise rather than a re-investigation.
